## 4. 现场事故与修复（本轮最重要的发现）

**症状**：`learning_loop_hft_brain` 已注册（日志有 `Added interval task ... every 60 seconds`），
但 `/api/learning/loop/status` 里 `last_tick_at` 恒为 `null`、`metrics` 计数恒为 0 ⇒
界面显示"注册了但不动"。

**根因（日志证据）**：

```
18:06:36 Running job "LearningLoopService._tick_hft_brain" ...
18:07:35 Execution of job "... _tick_hft_brain" skipped:
         maximum number of running instances reached (1)
18:08:10 [DB LeakGuard] pid=49288 origin: learning_loop_service.py:545 _tick_hft_brain
         > backend\services\market_maker\...
```

一次 tick 跑了 **~15 分钟**（手工触发那次实测 `elapsed_ms=191984`），因为：
① `process_outcome` 每笔都要走 MLTO / 复盘官 / `learning_registry` 多后端，**每笔 0.6~1s**；
② `SqlDriver.process` **每笔新开一个 DB session** ⇒ 一整批 200 笔 = 200 个连接，
   `DB LeakGuard` 把 origin 指向本 tick。

而 APScheduler 的 `max_instances=1` 在任务还在跑时**直接跳过**后续每一次触发 ⇒
入口永久停摆（且不会被判失败，因为它从不抛错）。

**修法**（三处，都在 `pp_brain.py` / `settings.py`）：
1. `SqlDriver` 支持**批级 session**（`open()`/`close()`，`_apply_rows` 包一层），
   单笔失败只 `rollback` 本事务 —— 连接数 200 → 1；
2. `_apply_rows` 加**墙钟预算** `MM_PP_BRAIN_BUDGET_SEC`（默认 45s）：到点收工、
   游标按每笔成功推进 ⇒ 不丢进度，下次接着补；
3. `LEARNING_LOOP_HFT_BRAIN_INTERVAL_S` **不再跟随 `PAPER_FAST_TRIAL` 缩到 60s**，
   固定默认 300s（`MM_PP_BRAIN_LIMIT=200` + 45s 预算下每次都能从容跑完）。

**修复后实测**：

```
hft_brain count=1 ok_rate=1.0 last_ms=11806
last_extra: {"ok":true,"scanned":1,"ingested":1,"failed":0,"skipped_rows":0,
             "budget_exhausted":false,"elapsed_ms":11709,
             "cursor":{"ts":1791627807.34,"id":60311},
             "ingested_total":260,"skipped_total":0}
inlet: health=warn | ingested=260/261 | pending=1 | interval=300s
health: loop_hft_brain ok thr=0.5h | hft_inlet_cursor ok thr=1h（已进 260・跳过 0・失败 0）
```
