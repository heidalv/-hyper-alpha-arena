# 根治 GLM 持续不稳报告（2026-09-16 调研轮12）

> 用户诉求：「找到 GLM 持续不稳的根因并解决」。
> 结论：**根因不是一个，是三层叠加**，全部已定位并修复；修复后 GLM 调用成功率恢复、失败归零。

---

## 根因链（每一层都有现场证据）

### 第 1 层：sidecar 每请求泄漏监听器 → 崩溃 → 靠"每 8 次重建"规避
- 上游 `opencode serve` 每个请求在内部事件总线上挂监听器且不摘除，累积到 EventTarget 默认上限（10）即报
  `MaxListenersExceededWarning: Possible EventTarget memory leak detected. 11 event listeners added to [yZ]`，
  随后进程崩溃（历史 8/16、9/5 多次实锤，注释记录"~11 次请求必崩"）。
- 桥接层对策是 `OPENCODE_RECYCLE_EVERY=8`：**每 8 次调用杀进程重建**。
- 代价即"持续不稳"：GLM 用量 ~780 次/24h ÷ 8 ≈ **每天约 97 次重建**，每次 20~40s 不可用
  （实测 `14:53:30 killed → 14:54:07 恢复`=37s；`14:59:45 → 15:00:05`=20s），
  sidecar 任务日志累计 **587 次 `opencode server listening`**。落在窗口内的调用直接
  `WinError 10061 目标计算机积极拒绝` 或 ReadTimeout。

### 第 2 层（真凶）：sidecar 进程里**没有 ZAI key** → GLM 每票 3 秒鉴权失败
直连 bridge 拿到完整返回体，`parts: []` 且 info.error 写着：

```
responseBody: {"error":{"code":"1001","message":"Authentication parameter not received in Header, unable to authenticate"}}
metadata.url: https://api.z.ai/api/coding/paas/v4/chat/completions
```

`opencode.json` 的 zai provider 是 `options.apiKey = {env:ZAI_CODING_PLAN_API_KEY}` ——
**key 必须来自 sidecar 进程环境**，而启动脚本日志一直打印 `ZAI key present=False`：
原实现用 `Set-Item Env:` 逐行注入 `.env`，实测**一个键都没进去**（不是 key 缺失，是注入失败）。
于是每个 GLM 请求都无凭据 → 1001 → 空响应 → 该票 ~3 秒失败（MiniMax 顶上），
台账里就是 `zai-coding-plan/glm-5.3* ok=False avg≈3~4s` 与 MiniMax 成功交替的固定模式。

### 第 3 层：鉴权失败触发 30 分钟冷却 → 凭据修好后仍被"罚站"
`model_gateway._note_failure()` 命中 `_AUTH_ERR` 就把传输丢进 `AUTH_COOLDOWN_SEC=1800` 冷却。
15:11 最后一次失败进入冷却 → 15:15 凭据修好 → **直到重启前 GLM 一次都没被再调用**
（台账 20 分钟空窗）。

## 修复（对应三层，全部可回滚）

| 层 | 修复 | 回滚 |
|---|---|---|
| 1a | 新增 `scripts/opencode_patch_maxlisteners.js`，经 `NODE_OPTIONS=--require` 预载（启动脚本），把 EventTarget/EventEmitter 上限设为无限 ⇒ **泄漏不再触发崩溃**（治根，不改 opencode 本体） | 去掉启动脚本里的 NODE_OPTIONS 行 |
| 1b | `OPENCODE_RECYCLE_EVERY` 8 → **60**（0=关闭），重建频率降一个数量级，降级为兜底 | 改回 8 |
| 1c | 新增 `recycle_in_progress()`：轮换期间 `health_check()` 直接判不可用 ⇒ `GlmOpenCodeTransport.configured()` 立即 False，网关**秒切**别的线上传输，不再出现 100~150s 挂起 | 无需（纯改进） |
| 2 | 启动脚本改用 `.NET ReadAllLines(UTF8)` + `SetEnvironmentVariable(..., 'Process')` 注入 `.env`，并**回读校验**打印 `ZAI key present=True len=49` | 无需（原方式本就是坏的） |
| 3 | `ANALYSIS_AUTH_COOLDOWN_SEC` 可配置，默认 1800 → **600**（10 分钟） | 改回 1800 |

## 遗留观察（不阻塞，供你定夺）
1. **GLM 单次耗时仍偏高**：`glm-5.3` 48.9s、`glm-5.3-flash` **148s**（MiniMax 约 11s）。
   现在不再失败，但 flash 档在关键路径（`event_impact`/`midlong_thesis`）上偏慢。
   若要把延迟压下来，方向是让 flash 走更小的上下文/输出上限（`ANALYSIS_MAX_OUTPUT_TOKENS`
   此前被抬到 1e6，与轮7 发现的论题输出上限问题同源），**需你确认**再动。
2. `opencode_sidecar_task.log` 的 `OPENCODE_SERVER_PASSWORD is not set` 警告：sidecar 仅监听
   127.0.0.1，风险可接受；若要加访问口令可另开一轮。
