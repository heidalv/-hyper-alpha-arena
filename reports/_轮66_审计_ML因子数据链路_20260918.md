# ML / factor / data-pipeline audit — Hyper-Alpha-Arena

Read-only. No repo file was created, modified or deleted. Scratch scripts went to `%TEMP%`.
Scope: `backend/services/factor_engine/`, `backend/services/evolution/`, `backend/services/data_center.py`,
`backend/services/kline_*`, `backend/services/market_flow_*`.

## Q1 — `ai_gen_volume_break.py` / `literal_shift_negative`

**The detector is correct; the factor is genuinely look-ahead.** `factors/ai_generated/ai_gen_volume_break.py:27`
is `ret_after = data['close'].pct_change(1).shift(-1)` — at bar *t* the value is the return from *t* to *t+1*.
`lookahead_audit.py:16` (`\.shift\(\s*-\s*\d+`) matches, verdict `blocked`, `factor_loader.py:112-116` skips it.
Blocking it is right. **Other than this one file, no factor in the 242 scanned files uses a literal negative shift**
(verified by scanning `factors/*/**.py`), matching the log (only this filename is ever reported).

**The repeated re-loading is a real performance bug** (findings 9 below).

---

## Q2 — `LearnedWeighting` IC gate

Answer to "is the gate rejecting everything": **no — 25.0 % reject rate.** Deduplicated over 1733 log files
(timestamp-keyed, so rotation copies collapse): **1382 unique training attempts, 346 rejected, 1036 accepted.**

| | n | mean val_IC | median | min | max |
|---|---|---|---|---|---|
| rejected | 346 | −0.1048 | −0.0665 | −0.4618 | +0.0200 |
| accepted | 1036 | +0.2222 | +0.1788 | +0.0201 | +0.9727 |

All attempts: **23.1 % negative**, median +0.123. So IC is **not** chronically negative and the label/horizon is
**not** inverted (the label is correctly aligned: `_forward_return_labels = close.shift(-5)/close-1` on a
positional index, features built from `df.iloc[:i+1]`). The gate is discarding the negative tail of a noisy
distribution — and the accepted tail (median 0.179, 72 runs > 0.5, max 0.973 for a 5-bar 15m crypto return) is
too strong to be real, which points at validation contamination (finding 5).

**More important than the gate:** the learned layer contributes exactly **zero** to live signals
(finding 4). `FACTOR_WEIGHTING_MODE=hybrid` and `LEARNED_WEIGHTING_ENABLED=true` are set, but
`data/promotion_gate_registry.json` pins `ml_learned_weighting` at `stage: "shadow"` → blend alpha 0.0.

## Q3 — staleness

* **Permanently stale:** ≈700 of 801 binance series per period. 170 symbols have *every* binance period older
  than 1 day. Dominated by dead non-crypto tickers (NVDA, MSFT, AAPL, XAU, XAG, CL, CSCO, TENCENT, XPD, XPT)
  that are in `crypto_klines` but not in the trading universe — noise, not a trading defect.
* **Universe:** the 12 live-universe symbols (BTC, ETH, SOL, BNB, VIRTUAL, ASTER, XPL, UNI, XRP, DOGE, SYN, LINK)
  had fresh rows on all periods at measurement. **No universe symbol is permanently stale.** But SYN had an
  **18.3-day** stale episode (`stale=1580398s`), i.e. transient-but-long, and whole-universe 1m stale bursts
  recur every ~10 min (finding 2).
* **Collection gap:** there is a *coverage* gap, not a presence gap — only ~100 "hot" symbols get 1m/3m/5m from
  P0; everything else depends on P1 rotation, so non-hot candidates can never satisfy `is_fresh` and are
  self-locked out of promotion.
* **COTI/MU/SYN** are *not* data-less in klines (COTI/MU/SYN all have fresh binance+asterdex rows), and
  COTI/MU/SYN/PLAY/WIF are **not in the trading universe** (volume-top/research set only). Their
  `数据不完整` flagging is the freshness/rotation issue, not a missing-collection issue. What they have no
  data for is **flow** (findings 6/11).

## Q4 — CVD `records_found=0`

**The reader/writer interface is HEALTHY.** Same table (`market_trades_aggregated`), symbol matched upper-case,
epoch **ms** on both sides, `period` is a string key of `TIMEFRAME_MS` on both sides, no symbol-spelling
variant exists in the table at all, and the displayed `query_range` is UTC only because of
`datetime.utcfromtimestamp` in the log line. **Root cause is (a): the symbols are genuinely never collected** —
the HL subscription throws before the collector records the symbol (finding 6), and COTI/MU are absent from the
flow collector's configured symbol list entirely (finding 11).

## Q5 — freshness-rule interface mismatches

**No UTC-vs-local and no ms-vs-s bug in the freshness rule.** `crypto_klines.timestamp` is `integer` (int4)
holding UTC epoch **seconds**; `stale_sec = time.time() - last` is epoch-vs-epoch; the `if last > 1e12: /1000`
guard is dead code int4 can never reach. `datetime_str` is UTC-naive and only string-sorted/displayed.

One anomaly I chased and **excluded**: `stale=1788454198s` (56.7 years, BTC/1d) appears only on 2026-09-03/04
and is logged from `data_center.py:259`, a **different line number** than the current gate (line 280) — an older
build. Not reproducible in the current code; not reported as a finding.

The genuine time/interface defect on this scope is a **unit bug in the ML loader** (finding 12).

## Findings

### [P0] `trade`-purpose freshness gate voids every explicitly-bounded historical kline read
- **File**: `backend/services/data_center.py:279-285` (gate), `:139-146` (`is_fresh`), `:240-241` (`start`/`end`→epoch)
- **What breaks**: `is_fresh` compares the newest bar **of the requested window** against wall-clock `now`, even
  when the caller bounded the window with `start`/`end`. Any window ending more than `2P+60 s` ago ⇒ `rows=[]`.
- **Evidence** (reproduced myself, venv python, SELECT-only):
  ```
  get_klines("BTC","1d",count=500,start="2026-01-01",end="2026-03-01",purpose="trade")
    -> count=0 first_ts=None last_ts=None
    stderr: [DataCenter] BTC/1d@binance 数据过期 stale=17404860s，trade 用途返回不可用
  same call, purpose="research" -> count=60 first_ts=1767225600 last_ts=1772323200
  ```
  In-tree precedent: `scalp_signal_logger.py:207-213` documents **57,000 lost signal labels** from this rule.
- **Impact**: any bounded-history consumer (walk-forward hooks, factor/backtest windows, "load older bars")
  silently gets 0 rows and treats it as "no data" → wrong labels/inputs.
- **Confidence**: certain (rule + my own live repro). Caller list not exhaustively enumerated.

### [P0] `2P+60` is measured from bar OPEN while `trade` reads require CLOSED bars; no ungated fallback
- **File**: `data_center.py:146`; `:374-379` + `:246-248` (`closed_only`); `kline_realtime_collector.py:660`
  (`KLINE_P0_TIMEOUT_S`=90); `kline_data_service.py:320-329` (hardcodes `purpose="trade"`); `market_data.py:213,220-227`
- **What breaks**: the newest *closed* bar's open ts is inherently `P..2P` old, so `2P+60` leaves only a 60 s
  margin — less than one collection round. The system's own monitor uses **3P**
  (`kline_freshness_watch.py:30-34`); the blocking gate is the outlier. 36 `get_kline_data` call sites inherit it.
- **Evidence**: measured residual slack 1m: 85 s, and at 10:34:41 UTC BTC/1m newest closed = 10:32 → **18 s slack**.
  Chronic whole-universe bursts in `logs/backend.error.log` (throttle 600 s):
  `18:28:55 ETH/1m stale=235 | SOL 235 | VIRTUAL 235 | XPL 235 | UNI 235 | DOGE 236`.
  Downstream money path: `data_readiness_gate.py:152 trading_ready = price_ok and klines_ok`, `:158-175`
  `allow_open_action` → False → `[数据门控] {sym} 禁止{act}`, consumed by `master_execution.py:214`.
- **Impact**: one slow round empties all klines for the whole universe → symbols reported incomplete/degraded
  and opens silently forbidden.
- **Confidence**: certain for code/thresholds/measured slack; likely for how often this actually blocks an open
  (no full decision-cycle replay). Same block sub-bug: `count` is not honoured (asks `count+1`, drops 1).

- **Evidence**: registry `{"ml_learned_weighting": {"stage": "shadow", "blend_alpha": 0.0}}` with

### [P1] The gate's `val_IC` is not an out-of-sample estimate, and its threshold is hard-coded
- **File**: `learned_weighting.py:203-219` (feature selection over the **whole** sample) vs `:232-233` (80/20 split);
  `:254` (`_min_val_ic = 0.02` hard-coded); `activation_service.py:271-291` (`counts=clip(round(wi*2),1,5)`,
  `boosted.index = RangeIndex`), `:276` (`wi = w[-len(aligned):]`)
- **What breaks**: (a) `min_ic_to_include` is applied with `_ic = _x.corr(aligned["__y__"])` computed on
  train **+** the validation tail that is then used to accept/reject the model — the val IC is optimistically
  biased, and with as few as 1-5 surviving features (log lines `features=1,2,3,4,5`) the bias is severe;
  (b) with `DDGDA_ENABLED=true` rows are duplicated 1-5×, so identical bars straddle the 80/20 split and the
  `purge_bars` embargo (which is correctly applied to the train tail) does not cover them;
  (c) `wi = w[-len(aligned):]` is **off by the label horizon** — `aligned` drops the *last* 5 rows (NaN labels),
  so the weights applied are shifted by 5 bars; correct is `w[:len(aligned)]`.
- **Evidence**: accepted val_IC median **0.179**, max **0.9727**, 72/1036 above 0.5 — not plausible for 5-bar 15m
  crypto returns; `_min_val_ic` is a literal while every sibling knob (`LEARNED_MIN_IC`,
  `LEARNED_LABEL_HORIZON`, `LEARNED_PURGE_BARS`) is env-configurable.
- **Impact**: the gate cannot detect overfitting, so the number used to decide whether to keep/replace the model
  is meaningless; the DDGDA weights are applied to the wrong bars.
- **Confidence**: likely for the leakage magnitude; **certain** for the code paths and the off-by-5.

- **Evidence**: `crypto_klines` latest row `timestamp = 1789727820` (= 2026-09-18 10:37 UTC);

  `1970-01-01 00:00:01.787468400+00:00 … 1970-01-01 00:00:01.789726500+00:00`, rows 4500 s apart (= 5 × 15m).
