# 轮99 · 长线趋势单被按日内单对待 —— 止盈止损深度检查与修复

> 用户反馈（2026-09-18）：
> **「深度检查和修复止盈止损，尤其是长线单，他按照日内单对待，这样完全发挥不出长线趋势的作用。
> 长线趋势是滚仓盈利为目的的，你这做成了什么啊」**
>
> 结论：**用户说对了**。根因是一条"长线跳过日内保护"的规则**从未生效**，
> 长线仓一直在跑中短线口径的 ATR 止盈阶梯；同时轮96 的修复把**滚仓**也一起停掉了。
> 提交：`ac907d7`（轮96 四项）· 本轮 `轮99`（趋势车道判定解耦 + 滚仓恢复）

## 二、根因：`_v2_long_managed` 恒为 False

`paper_trading_engine` 里写着：

```python
if _v2_unified_on and not _v2_long_managed:
    # [2026-08-24 long_trend_v2] V2 长线仓跳过统一分段止盈/保本/硬软回撤/追踪
```

而判定是：

```python
_v2_long_managed = long_v2_enabled() and (nature 是长线 or tier == long)
```

`long_v2_enabled()` 读的是**入场闸** `LONG_TREND_V2`：

1. `.env` 里 `LONG_TREND_V2=0` ⇒ **恒 False**；
2. 即使设成 1，主脑接管（`MIDLONG_BRAIN_MODE`）时它还会**再静默否决一次**
   （`long_trend_v2.py` 的 §58 注释自己记录了这个"开关形同虚设"形态）。

⇒ 注释里承诺的"长线跳过"**一次都没生效**，长线仓照样跑：

1. **ATR(1h) 阶梯分批止盈**：`tp1_mult=2.0` / `tp2_mult=3.0` / `tp3_mult=5.0`
   （`REGIME_TP_PARAMS` 按 regime 选参，**没有车道维度**）；
2. 每档后把止损拖到 `entry + 0.8×ATR`（≈成本上方 1%~2%）；
3. TP1 后**软回撤 >2×ATR 直接全平**；TP3 后 `peak − 2×ATR` 追踪；
4. 名义 < $30 时自动降档为**"TP1 触发即全仓清掉"**。

⇒ 长线仓在 +3.8% 就被分批止盈、止损随即贴到成本上方 1%~2%，
一次 2% 级正常回撤即全平 —— **车道声明的 8%/15%/25% 永远到不了**。
这正是 2026-09-18 那 4 笔 `trend_follow` 以 +1.14%/+2.05%/+2.11%/+4.33% 收场的机制。

> 顺带说明：`exit_policy.py:22` 自己写着「分档 TP 保留在 `_run_unified_staged_tp`；
> **本模块只声明档位**」—— 于是"声明 8/15/25%"与"执行 2×/3×ATR"两套口径长期并存，
> 这正是本项目反复出现的"同一件事两套实现"。

## 三、修复

### Fix 1（核心）：把「车道成员身份」与「入场闸开关」彻底解耦

新增 `PaperTradingEngine._is_trend_lane_member(pos, tier, nature)`：

```
车道成员 = tier == "long"  或  nature ∈ (trend_follow, position)  或  E1 仓位(entry_source=trend_e1)
```

- **只由仓位自身的字段决定，与任何开关无关**；
- 成员 ⇒ `_v2_long_managed = True` ⇒ 本函数内 6 处中短线口径保护（统一分段止盈 /
  保本推进 / 硬软回撤 / DSM 追踪 / 固定 TP / ExitPolicy 层 / PEO）**一律跳过**；
- **保留**：爆仓兜底、failsafe SL/TP、`max_hold` 硬层，以及车道自己的
  Chandelier 结构止损与规则失效退出（有测试断言硬层未被 gate）；
- 新增 `_should_run_unified_staged_tp(pos)` 把闸门抽成单一可测入口
  （避免再次出现"注释说跳过、条件写成别的变量"）；
- 每个仓位首次跳过时打一条 INFO（否则"按契约交给 Chandelier"与"保护失效"无法区分）；
- 回滚开关 `EXIT_TREND_LANE_SKIP_INTRADAY`（默认 true，已登记 `KNOWN_FLAGS`）。

### Fix 2：轮96 的 E1 守卫**收窄**（恢复滚仓）

轮96 的第一版是"整个 midlong 管理器跳过 E1"，**过宽** —— 它把**滚仓**一起停掉了
（实测长线平均加仓 0.06 次）。按车道契约精确划分后：

| 动作 | 趋势车道 | 理由 |
|---|---|---|
| 论题规则失效退出 | ✅ 允许 | 车道契约里的"规则失效"出口 |
| **滚仓 / 加仓（pyramid）** | ✅ **允许（本轮恢复）** | 用户明确要求"长线趋势是滚仓盈利为目的的" |
| `tighten_trailing` 收紧追踪止损 | ⛔ 禁止 | 把趋势仓降级成日内仓的元凶 |
| `reduce` 裁量减仓 | ⛔ 禁止 | 车道契约是"失效即全平 / 跟随 Chandelier"，不做千刀万剐（#4659 被减 6 次剩 2.7%） |

回滚/开关与 Fix 1 共用 `EXIT_TREND_LANE_SKIP_INTRADAY`，两处语义一致。

### Fix 3：清掉两条**配置驱动的长期红**测试（顺手）

- `test_factor_signal_comprehensive::TestEndToEndPipeline` 两条：
  `FACTOR_LIVE_ALLOWLIST_ONLY=true` 时 `compute_all_factors` 只返回白名单因子，
  "基础因子集"概念不成立 ⇒ 必然为 0 而长期红。现改为**显式 skip + 说明**
  （并注明该开关由 `base_factors.py:741` 直接 `os.getenv` 读取、**不在 settings 里**）。
- `test_m3_long_lane_cap::test_brain_long_batch_suppressed_when_e1_exclusive`：
  该守卫已被**用户 2026-09-18 裁决撤销**（`mlto_cycle.py:343-346`：
  "分析不许省"，长线批次恢复全频率派发，交易权仍在 E1）。测试改为断言当前裁决，
  并保留"E1 独占判定仍在"的护栏。

## 五、遗留（下一轮）

1. **滚仓的"何时加"仍需标定**：本轮只是把滚仓路径对趋势车道**恢复可达**
   （轮96 误关了它）。实际加仓仍走 `position_manager.evaluate_pyramid` 的 5 层门控，
   与 `MIDLONG_POSITION_MGMT_PYRAMID_DIRECT_PNL`（默认 5%）。趋势车道的加仓节奏
   （金字塔间距、每次比例、与 Chandelier 的关系）需要按历史数据标定，
   `trend_e1_engine` 里那句「权重低于目标不追加（**金字塔另议**，避免追高）」就是这个待办。
2. **E1 的 `exit_policy.tp_stages=[8,15,25]` 现在没有任何消费者**（跳过了 ATR 阶梯、
   E1 自己也不做分档）。要么让它成为真正的分档消费者，要么在声明里写清"仅存档"，
   避免又出现"声明与执行两套口径"。
3. **论文失效退出的 min_hold 覆盖**待查：`thesis_invalidation`/`thesis_should_close`
   在长线仓上出现过 2.8–4.4h 就离场的记录（#4649/#4651/#4643/#4644），
   与 72h 最短持仓不符，需确认该路径是否绕过了 `unified_exit_state_machine` 的保护层。
