# 调研轮48 — 补上 15m **与 1h** 两个周期：日内档 + 1h 挖矿调度

- 日期：2026-09-17
- 用户纠正：「我说的是 **15 分钟和 1 小时缺失**」—— 我此前只盯 15m，漏了 1h。
- 本轮：**1h 的缺失比 15m 更彻底（连调度都没有）**；两者一起补。

---

## 一、1h 的缺失面（比 15m 更彻底）

| 项 | 15m | **1h** |
|---|---|---|
| 因子进化 cron | ✅ `factor_evolution_mid_15m_daily_v7`（06:00） | ❌ **全仓无任何调度** |
| `evolution_scheduler._evo_minutes` 档位 | 有（`"15m": 20`） | **无** |
| 因子库数量 | 20 | 24 |
| horizon 标签 | `scalp`（错标） | **`scalp`（错标）** |
| candidate / active | **0 / 0** | **0 / 0** |
| 创建时间 | 全部 2026-08-16 21:41（一次性） | 全部 2026-08-16 21:35（一次性） |
| 来源 | 只有 `alpha101_lib_scalp` | 只有 `alpha101_lib_scalp` |

证据（本轮实测）：

- `backend/main.py` 只注册 3 个进化 cron：`make_subprocess_task("4h"…)`、`("5m"…)`、`("15m"…)` —— **没有 "1h"**。
- `backend/services/evolution_scheduler.py:1428` `_evo_minutes = {"1m": 10, "15m": 20, "5m": 0, "4h": 30}` —— **没有 1h**。
- 全仓 grep `period="1h"` 的命中**全是行情读取与离线回测脚本**，无一是因子进化。

**而中线车道在消费 1h**：
- 硬契约：`decision_core/data_contract.py:13` `"mid": ["price","indicators_1h","indicators_4h","indicators_1d"]`
- 消费周期：`full_auto/midlong_helpers.py:1815` `("15m","1h","4h","1d")`

⇒ **车道在消费 1h 数据，但 1h 因子一个都没有，连挖矿都没排班。**

机器本身是支持的（所以这是纯配置/调度缺口，不是能力缺口）：
`_PERIOD_SPLIT_DAYS["1h"] = (150, 45, 30)`、`_PERIOD_FWD_BARS["1h"] = 2`（前瞻 2h，与日内持仓节奏一致）。

## 二、结构性根因：因子库是**二元池**，没有"日内"这一档

```python
# scalp_active_factor_set.py
def _is_scalp(rec):   return horizon or "scalp") != "midlong"     # ← 其余全算短线
# midlong_active_factor_set.py
def _is_midlong(rec): return horizon or "scalp") == "midlong"
```

而 `factor_evolution_loop._tag_one_short_horizon` 把 **15m 也归进"短周期"**
（`_SHORT_HORIZON_PERIODS = {"1m","3m","5m","15m"}`）→ 打 `s5m_` 前缀 + `horizon=scalp`
→ **必然落进已判死的短线池**（`SCALP_OPEN_DISABLED=true` / `SCALP_RESEARCH_ENABLED=false`）
→ 15m 因子永远无法进入交易。

同一个 15m 任务，入口叫"**中**周期"（`run_mid_factor_evolution_loop`），
打的标签却是"**短**周期"（`horizon=scalp`）—— 语义在同一段代码里自相矛盾。

## 三、本轮改动（两处补齐 + 语义真源）

### 3.1 新增语义单一真源 `backend/config/cycle_semantics.py`

- 规范档：`INTRADAY = "intraday"` / `TREND = "trend"`
- 周期分档（依据 `_PERIOD_FWD_BARS` 的真实前瞻时长）：
  **日内** = 1m/3m/5m/15m/30m/1h/2h（前瞻 1.5–2h）；
  **长期趋势** = 4h/6h/8h/12h/1d/3d/1w/1M（前瞻 24h–3d）
- `normalize_horizon()`：存量标签等价换算（`scalp`→日内、`midlong`→趋势），
  **故意不映射 `"mid"`** —— 它在代码里同时指 4h（`factor_discovery`）与 15m（`main.py` V7），
  映射只会把歧义固化。
- **只读映射，不改写存量数据。**

### 3.2 打标：`_tag_one_short_horizon` 增加日内分支

`FACTOR_EVO_INTRADAY_PERIODS`（**默认空 = 完全维持现状**）列出的周期改打
`horizon=intraday` + `intra_` 前缀，不再误标 `scalp`。

用**周期列表**而非布尔开关的原因：中线车道实际消费的是 `("15m","1h","4h","1d")`，
只有 15m/1h 该迁；若用布尔开关，1m/3m/5m 会一并被移出短线池，
而中线**不消费**它们 —— 等于制造新的孤儿。

### 3.3 池路由：日内档不进短线池、且被中线池接纳

| 文件 | 改动 |
|---|---|
| `scalp_active_factor_set._is_scalp` | `horizon not in ("midlong", "intraday")` |
| `midlong_active_factor_set._is_midlong` | `horizon in ("midlong", "intraday")` |
| `midlong_active_factor_set._tradable_ast_bridge` | `horizon/timeframe` 不再硬编码为 `"midlong"/"4h"`，改读记录的 `period` |

第 3 项是关键：AST 桥接原本把 `"timeframe"` 写死 `"4h"`，
15m 因子经桥接进中线后会被**改写成 4h**，等于偷换周期。
现在改读 `FactorActiveSet.period`（`load_factor_active_rows` 已返回该字段，`:86`）；
存量记录 `period` 本来就是 `4h`/`NULL` → 回退 `"4h"`，**对存量零变化**。

### 3.4 新增 1h 因子日进化

| 文件 | 改动 |
|---|---|
| `factor_evolution_loop.run_intraday_1h_factor_evolution_loop` | 新增 1h 入口（`period="1h", quick=False`） |
| `main.py` | 注册 `factor_evolution_intraday_1h_daily`，**每日 05:00**（避开 3/4/6 点三档） |
| `FACTOR_EVO_INTRADAY_1H_ENABLED` | 默认 true；置 false 即跳过注册（回滚无需改代码） |
