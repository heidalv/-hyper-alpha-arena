上一轮子代理报告称「`indicators_15m` 在 `backend/services` 下无任何读取方」。
**该结论错误** —— 读取用的是 **f-string 动态拼键**，按字面量 grep 会漏掉：

`backend/services/mlto/qual_layer.py:474-501`：
```python

for tf in kline_tfs:
    ind = ms.get(f"indicators_{tf}")        # ← 动态键，即 indicators_15m
    recent = ind.get("recent_klines") or []
    if len(recent) < 5 and tf in ("15m","1M"):
        recent = _ks.get_klines_from_db(packet.symbol, tf, count=30)   # 兜底直查
    ...
    lines.append(f"[{tf} K线×{len(tail)}]\n" + "\n".join(candle_bits))  # ← 进 LLM 提示词
```

即：**mid 车道的 LLM 提示词里带 `[15m K线×30]` 块**（30 根 = 7.5 小时上下文）。

全库唯一一处字面 `indicators_15m` 是 `midlong_helpers.py:1814` 的注释：
> qual_layer 的 K 线摘要段优先读 indicators_15m.recent_klines

**关键洞察**：SOL/BNB/VIRTUAL/ASTER/XPL 的失败**全部落在 06 时**，而
**06:00 正是 `factor_evolution_mid_15m_daily_v7`（15m 因子进化）的启动时刻**
（实测 06:00:00 启动、07:10:39 结束，阶段1 取数 6770 根/品种 × 9 品种）。
进化任务大量拉取 15m K 线，**与交易侧的 15m 聚合争抢数据通道/连接池**，
导致 06:48–06:49 一批交易侧取数返回 0 根。

11 时那批（UNI/XRP）落在重启窗口（11:06）与整点任务（`factor_online_weight_hourly`）附近。

**FET 的问题不同**：它不是 stale 而是**聚合器拒绝返回**（日志
`[KlineAgg] FET/15m@binance 基准所 K 线过期，且无新鲜所可回退，拒绝聚合返回`），
且从 09 时起每次扫描都失败 → 565 条里 429 条是它，属**日志刷屏 + 无效取数**。
FET 不在 9 币交易 universe 内（是扫描池标的）。

**由此得出的可修项**（未做，留待决策）：
把 15m 进化（06:00）与交易侧取数错峰，或给进化取数走独立限流；
以及给"无新鲜所可回退"的标的加请求冷却，避免每轮刷屏。

## 二、目标② 落地：IC-WFO 的 p 阈值 0.05 → **0.15**

### 2.1 为什么动

轮46 已定论：`oos_p < 0.05` 是**唯一普遍性杀手**（181 条失败币记录 100% 都有 p ≥ 0.05；
IC 达标 62%、衰退 56%，均非主因），41 个晋级候选在 p<0.05 下通过 **0 个**，
与 4h/15m 连续 7 天 `promoted=0` 完全吻合。

**取最保守的有效档 0.15**（敏感度：p<0.10→2、**p<0.15→3**、p<0.20→6 饱和）。

### 2.2 改了什么

`.env`（gitignored，无 BOM、LF 保持、已备份 `.env.bak_wfop_20260917_120004`）：
```
WFO_IC_MAX_P=0.15          # ← 唯一放宽项（原硬编码 0.05）
WFO_IC_MIN_OOS_IC=0.01     # ← 显式 pin，值 = 原生效默认，零变化
WFO_IC_MAX_DECAY=0.50      # ← 显式 pin，值 = 原生效默认，零变化
```
后两个是显式 pin（消除 facts 清单的 MISSING），**判据未放宽**。

`backend/config/env_registry.py` —— **关键发现**：`SYSTEM_PREFIXES` 里的 `"WFO_"`（:40）
管的是另一套校验；`find_unknown_flags` 用的是显式白名单 `KNOWN_FLAGS`（:77-1795）。
所以新键**必须显式登记**，否则 `.env` 一写入就报"不一致"（本轮实测踩到）。
已把三个 `WFO_IC_*` 键登记进 `KNOWN_FLAGS`（并加注释说明这两套机制的区别）。

`docs/RUNTIME_CONFIG_FACTS.md` —— `WFO_IC_MAX_P` 期望值改为部署值 **0.15**（注明代码默认 0.05）。

### 2.3 修复了我自己的一个测试缺陷

部署 0.15 后 `test_settings_declares_the_switch` **失败** —— 它硬编码断言
`S.WFO_IC_MAX_P == 0.05`，把"部署值"当成了"契约"。
这正是契约测试该抓的东西。已改为：

- 断言**声明存在 + 类型为 float**（不锁运行时值）；
- 断言**源码里的代码默认值**必须是 `"0.05"`（用 `inspect.getsource` 守卫），
  这样"默认不变"的契约仍被锁住，而调档不再误报。
