# GLM 慢的深度分析报告（2026-09-16 调研轮13）

> 用户判断：「glm flash 不应该这么慢，应该比 minimax 快很多」。**这个判断是对的**——
> 实测证明慢的不是 flash 的生成能力，而是这条调用路径的结构。

---

## 1. 量化事实（24h 台账 + 受控实验）

### 1.1 同任务对比：GLM 比 MiniMax 慢 8~17 倍
| task | MiniMax-M3 | GLM-5.3-flash | GLM-5.3（非 flash） |
|---|---|---|---|
| midlong_thesis | 9.8s | **163.5s** | 86.7s |
| event_impact | 12.5s | **138.2s** | 74.4s |
| trend_chart_review | 14.9s | **120.7s** | 95.9s |
| anomaly | 13.7s | **119.9s** | 103.0s |

**而且 flash 比非 flash 更慢**（163s vs 87s）——与"flash 应该更快"的常识相反，本身就是异常信号。

### 1.2 不是"生成更多内容"
`midlong_thesis`：GLM-flash 输出 526 tokens，MiniMax 输出 628 tokens —— 输出更少却慢 16 倍。

### 1.3 不是峰时限速
GLM-flash 逐小时统计（24 小时）× 每 token 速率：全天稳定 **4.9~7.7 tok/s**，无峰谷差异
（GLM Coding Plan 的"工作日 14–18 点 3× 计费"只影响额度，不影响延迟）。

### 1.4 受控实验：固定开销 ~10-12 秒，且**与输入长度无关**
| 实验 | input tokens | 耗时 |
|---|---|---|
| 迷你提示（"只输出 {"ok":true}"），默认配置 | **1923** | 11.7s |
| 同上，`tools={}` 全关 | 1923 | 12.8s |
| 同上，极简 `system` | 1927 | 14.0s |
| 同上，**去掉内联 instructions** | **839**（省 1084） | **12.2~17.8s（没变）** |
| agent=build / general（更重的 agent） | 9036 / 8011 | 9.4s / 11.0s |

⇒ 输入从 1923 降到 839（-56%）**延迟毫无改善**；换更重的 agent（9k tokens）也没更慢。
**"每请求约 10~12 秒"是这条路径的地板，与提示长度无关。**

### 1.5 时间花在供应商侧，不在我们的链路
响应自带时间戳：`info.time.created=…652339`、`completed=…666966` ⇒ **模型侧区间 14 627 ms**，
而端到端总耗时 14.7s ⇒ **HTTP/sidecar/桥接开销 < 100 ms**。
同一次 `tokens = {input: 839, output: 7, reasoning: 70}` ⇒ 有效 63 tok/s，
且 `cache: {write: 0, read: 0}` ⇒ **无提示缓存**（每次都全量重算）。

---

## 2. 结构性原因（按贡献排序）

| # | 原因 | 证据 | 影响 |
|---|---|---|---|
| 1 | **每请求固定 ~10-12s 的供应商侧延迟地板** | 839 vs 1923 tokens 均 ~12s；模型侧区间 = 端到端 99.3% | 小任务的全部延迟；大任务的固定底 |
| 2 | **GLM 5.3 是推理模型，永远先"想"** | 响应恒含 `reasoning` 段：迷你提示也要 47~194 reasoning tokens（`parts=['step-start','reasoning','text','step-finish']`） | 每题多出思考阶段；大任务上思考更长 |
| 3 | **opencode agent 的固定脚手架** | `instructions` 内联 `backend/prompts/opencode_analysis_system.md`（4209 B ≈ **1052 tokens**）+ opencode 自带系统提示/环境块 ≈ 另 800 → 基础 1923 tokens | 每请求多 ~1.9k tokens 的输入（成本/额度），延迟上不显著 |
| 4 | **我们自己的 context pack 很大** | 台账 `input_tokens` 是**桥接层用字符粗估**的（`tokens_estimated=True`），真实值远大于它；图审还会带图（多模态 token 更贵） | 大任务 120~163s 的主要变量 |
| 5 | **无提示缓存** | `cache.write=0, cache.read=0`（每次全量重算） | 重复上下文无法复用，放大 #3/#4 |
| 6 | **MiniMax 是直连，GLM 走 opencode** | MiniMax transport 直接 `call_llm_api_sync`；GLM 走 sidecar agent | 两者从一开始就不同赛道：GLM 背 1.9k 脚手架 + 推理阶段，MiniMax 不背 |

---

## 3. 结论（一句话）
**flash 慢的本质是"每请求 ~10 秒的供应商侧地板 + 强制推理阶段 + opencode 脚手架"，
而不是模型生成慢（实测 63~79 tok/s，与 MiniMax 同量级）；提示词裁剪（省 1k tokens）
对延迟无效，只对额度/成本有效。**

## 4. 可选的改善手段（按性价比，需你确认后我再动手）

| 手段 | 预期效果 | 代价/风险 |
|---|---|---|
| **A. 把 GLM 从"每题必调"降为"分歧时仲裁"** | 双票里 GLM 是慢的一方（MiniMax 单跑 10s，双票要等 120~160s）；改成 MiniMax 主跑 + 分歧才请 GLM | 交叉验证覆盖面下降（可从"每题"改为"分歧/高风险题"）；**最有效** |
| **B. 给 GLM 票单独瘦身上下文**（只给它精简 pack，不给全量 K 线/图） | 大任务 120~163s 有望回到地板附近 | 第二票信息量下降，需评估对一致性判断的影响 |
| **C. 去掉 `instructions` 内联（-1052 tokens/次）** | 额度/成本省 ~30% 输入；**延迟不变** | 可能影响 JSON 格式合规（该文件是分析系统提示）；建议先 A/B |
| **D. 让 z.ai 侧确认**：coding plan 是否限速/是否支持关闭 thinking | 若支持关思考，固定地板和推理阶段都能降 | 需你在 z.ai 控制台确认套餐与参数（我这边无法读供应商侧配置） |
| **E. 维持现状**：GLM 作为"慢而稳的第三票" | 零风险 | 关键路径继续被 120~160s 拖累 |
