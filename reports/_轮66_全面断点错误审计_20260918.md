### 对 P1-1 的重新定性（轮73 复核）

原文（子代理审计）称 `ml_learned_weighting` 的阶段「**只能写 shadow，特性永远无法自我晋升**」。
**该结论不成立**，实测证据：

- 晋升链路完整：`full_auto/loops/learning_loop.py:67` 调
  `promotion_scan_service.run_promotion_scan_tick` → 扫描通过后
  `apply_promotion_stage` 落盘；`runtime_governor.py:530` 另有一条 approve 路径。
- 晋升是真实发生过的：`data/promotion_gate_registry.json` 里
  `factor_hybrid_mode` 已是 **`stage="canary"`, `blend_alpha=0.22`**
  （`previous_stage="shadow"`），走的就是同一套机制。
- `activation_service.py:437-438` 那段「只写 shadow」的代码是**注册/降级**路径，
  不是唯一的写入者（原文把这一处当成了全部）。

因此 `ml_learned_weighting` 维持在 `stage="shadow"`（`blend_alpha=0.0`, `dsr=null`）
应读作「**尚未达标**」：学习层对实盘信号贡献为 0 是当前**设计内的**状态，
非 bug。**降级为 P2 / 治理项**。

真正需要修的是它**准入的质量**（即 P1-13）：val_IC 非样本外、阈值硬编码、
DDGDA 上采样使相同 bar 跨切分两侧、以及 P1-10 的单模型跨符号服务
（`_ML_SYMBOLS=("BTC","ETH","SOL")` 共享一个模型实例给所有交易符号）。
即：**问题不在「晋升不了」，而在「一旦晋升，尺度不可信」。**

### P0-1 ✅ 本次已修 — PnL 权威口径丢掉分档止盈的最后一腿

- **文件**：`backend/services/pnl_authority.py:62`
- **问题**：`realized_pnl()` 是自称的「唯一权威已实现盈亏口径」，但对「分档止盈后全平」的仓位
  只返回前面几腿之和。分档止盈把每腿**累加**进 `partial_realized_pnl` 且平仓**不清零**，
  最终那一腿写在 `unrealized_pnl`。
- **证据**（仓位 4672 UNI long，订单账本实测）：

  ```
  23601 buy  124.6558 @6.295140                开仓
  23615 sell  31.1639 @6.537391  pnl=+7.5495   staged_tp1
  23617 sell  23.3730 @6.690109  pnl=+9.2316   staged_tp2
  23618 sell  70.1189 @6.708170  pnl=+28.9612  tp
  合计 = 45.7423  == unrealized_pnl（引擎写入的本笔合计，正确）
  旧 realized_pnl() = 16.7811                    ← 少算 28.9612
  ```

- **全库影响**：已平仓 3520 笔中 **927 笔口径变化**；旧合计 −981.37 → 新 −799.79
  （把 181.58 USDT 亏损虚增）。后果不止显示：净亏的单被判为盈利 →
  亏损归因 `total >= 0` 直接返回「无亏损归因」→ **该触发归因的车道永不触发**。
- **修复**：判定顺序改为「已平仓且 `unrealized_pnl` 非 0 → 用之；否则 `partial_realized_pnl`；
  否则价差复原」。**刻意要求「非 0」**：全库 1271 笔已平仓的 `unrealized_pnl` 为 0，
  其中 1180 笔按价差明明有盈亏，无条件采信会把这批变成 0（比原 bug 更糟）。
  已做全库回归：927 笔变化中「原来有盈亏、现在变 0」= **0 笔**。
- **提交**：`6fc44c8`｜**状态**：已修、已回归、已重建历史报告（340 行）

## 五、可用性发现（本次审计过程实测）

### A-1 ⬜ 后端 HTTP 在 CPU 密集负载下会**长时间不可用**（实测 >10 分钟）

- **现象**：18:33 起 `/api/health`、`/api/period/lanes` 等全部 10-12s 超时；
  同期交易循环仍在跑（日志 20s 增长 5167 字节，CPU 从 1719s→1814s），
  后端进程 223→228 线程、2.9GB 常驻。重启后 30s 内恢复。
- **时序**：后端 18:06 启动、18:24 前一直正常；全量测试（5063 用例）18:24 起跑，10 分钟后开始超时。
- **推断**：GIL 争用/资源抢占（36 核但单进程 228 线程 + 2.9GB）。**未做线程栈取证**，故只报现象与相关性。
- **影响**：交易时段内跑任何重型 Python 任务，Web GUI 与所有 HTTP 依赖的自动化都会失联。

### A-2 ⬜ 反复刷屏的日志（掩盖真实信号）
