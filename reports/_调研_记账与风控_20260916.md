### 1.3 E1 为什么"恒成立"（关键审计发现）

`paper_trading_engine.py:5827-5938` 的 `_recalc_balance()` 是唯一权威重算入口：

```
5902:  order_rpnl = SUM(PaperOrder.pnl)   WHERE account_id=? AND pnl IS NOT NULL AND created_at >= last_reset_at
5909:  order_fees = SUM(PaperOrder.fee)   WHERE account_id=? AND fee IS NOT NULL AND created_at >= last_reset_at
5929:  _funding_pnl = SUM(PaperFundingLedger.payment) WHERE account_id=? [AND settled_at >= last_reset_at]
5933:  bal.realized_pnl     = order_rpnl + _funding_pnl
5934:  bal.total_fee_paid   = order_fees
5935:  bal.frozen_margin    = total_margin
5936:  bal.unrealized_pnl   = total_upnl
5937:  bal.available_balance= bal.initial_balance + order_rpnl + _funding_pnl - order_fees - total_margin
5938:  bal.total_equity     = bal.available_balance + total_margin + total_upnl
```

代数推导：

```
equity = available + margin + upnl
       = (initial + order_rpnl + funding − fees − margin) + margin + upnl
       = initial + (order_rpnl + funding) − fees + upnl
       = initial + realized_pnl − fees + upnl          ← 正是 E1
```

**因此 E1 / E2 是定义式，数学上不可能失败。** 用它们做健康检查等于没有检查。
真正的勾稽必须**跨源**（E7）：把"订单口径"与"仓位口径"对照，差额 **−105.63 USD**，即 **`paper_balances` 采用订单口径，而 `paper_positions` 归档的是另一套数**。任何下游消费者（学习闭环 `learning_loop._paper_position_pnl`、再入场冷却、绩效报表）若读仓位口径就会与账户权益差 2.3%。

历史修复注释（`paper_trading_engine.py:2001-2006`）已声明"closed 仓位的 `unrealized_pnl` 已含 `partial_realized_pnl`，禁止再叠加"——本次审计确认**该约定在 32.9% 的已平仓样本上与其自身订单对不上**（见 §1.5），所以"分不清哪套是真"本身就是缺陷。

### 3.5 平仓路径幂等性（D1 的代码根因）

`close_position()` 的关键代码（`paper_trading_engine.py`）：

```
1810-1831  docstring：承认多腿并存时 .first() 可能平错腿
1837-1842  pos_query = db.query(PaperPosition).filter(account_id, symbol, side, status=='open')
1843-1848  [可选] position_id / trade_nature / strategy_id 过滤
1849       pos = pos_query.first()          <-- 无 with_for_update()，无 ORDER BY
1850-1853  未找到 → return None（仅此一处"已平"保护，且是在查询时点）
...
1966-1971  if trigger_order_id: 取 status=='pending' 的该单
1973-1984  if close_order is None: **新建一笔 market 单**（这就是幽灵单的来源）
1986-1995  close_order.filled_quantity = remaining_size ; pnl = final_pnl ; status='filled'
1997-2006  pos.status='closed' ; pos.unrealized_pnl = final_pnl + partial_pnl_sum
```

**缺陷链**：函数**没有** `SELECT ... FOR UPDATE`、**没有**在加载后复核 `pos.status == 'open'`、**没有**幂等键（如 `close_event_id`）。因此：

1. 两个出场通道在同一事务/tick 内先后进入（例：`4638` 先由 `_apply_exchange_attached_orders` 的 SL 通道（`close_reason='sl'`，`:2668-2676`）平仓，**15 秒后** thesis 通道再次平仓（`close_reason='thesis_invalidation'`））；
2. 第二条通道 `trigger_order_id=None` → 走 `1973-1984` **新建一笔全量 market 单**；
3. 两笔单都被置为 `filled` 且各写一份 `pnl`；
4. `_recalc_balance:5902` 对 `paper_orders` 做 `SUM(pnl)`，**两笔都计入** → 重复计费。

**附带问题**：`close_order.pnl = final_pnl`（`:1990`）**只写最终段**，分批段由 `_partial_close` 的独立订单（`:2342 pnl=partial_pnl`）承担，两者相加才等于 `pos.unrealized_pnl`（`:2006 total_pnl`）。这条约定本身自洽，但**没有任何 schema 级或校验级保证**——这正是 §1.5(b) 28/85 不自洽的土壤。

**机理（已定位到行，含"为什么是路径相关"）**：

1. 常规峰值维护 `_sync_peak_state`（`paper_trading_engine.py:209-250`）**对两个字段用了两套语义**：

```
217-219  cached_peak = self._peak_profit_cache[pos_id] ; db_peak = pos.peak_unrealized_pnl
219      peak = max(cached_peak, db_peak, float(current_upnl))          # USD 口径：单调取大
223      pos.peak_unrealized_pnl = peak
224-227  pos.peak_pnl_pct = max(prev_pct, self._position_pnl_pct(pos, current_price))  # 价格口径：单调取大
```

- `peak_unrealized_pnl` 是**在"当次观测时的仓位规模"下**的 USD 单调最大值（`:219`）；
- `peak_pnl_pct` 是**与规模无关**的价格百分比单调最大值（`:224-227`，`_position_pnl_pct` 只依赖 `mark/entry`，见 `:205-207`）。
- **一旦 `size` 变小（减仓），USD 口径的历史最大值不会被按比例重标**，而 pct 口径照旧推进 → 两者永久失去换算关系（正比于"减仓前的规模 ÷ 减仓后的规模"）。比值 1.22×/1.26×/1.28×/1.38×/1.42×/1.60× 与 6.69×/8.00× 正是各次减仓的规模比。

2. **只有两条路径会重置峰值，其余减仓路径不重置**，因此失真是**路径相关**的：

| 路径 | 代码位置 | 是否重置 peak |
|---|---|---|
| `profit_drawdown_partial`（回撤部分平仓） | `:3545-3553`（注释 `3545`：「重置 peak 为当前剩余仓位的盈亏，防止连锁触发」） | ✅ 重置 `peak_unrealized_pnl` + `peak_pnl_pct` |
| `profit_stage_close`（分段止盈） | `:3600-3604` | ✅ 重置两者 |
| `_partial_close`（含 `staged_tp1`/`staged_tp2`/`trend_weaken:*`/`risk_trim_symbol_cap` 等主流减仓） | `:2306-2375` | ❌ **完全不触碰** `peak_*`、也不清理 `self._peak_profit_cache[pos_id]` |

→ 走 `_partial_close` 的减仓**既不改 USD 峰值、也不失效内存缓存**，于是 `_sync_peak_state:219` 的 `max(cached_peak, db_peak, current_upnl)` 会**继续沿用减仓前规模的 USD 峰值**。

3. **数值反证（4659）**：`peak_unrealized_pnl = 1.9861`，`peak_pnl_pct = 0.02720`，`entry = 77303.79`。
   - 若按**当前** size 0.000141 换算：`0.000141 × 77303.79 × 0.02720 = 0.2970` ≠ 1.9861
   - 若按**原始** size 0.002615 换算：`0.002615 × 77303.79 × 0.02720 = 5.4991` ≠ 1.9861
   - 反推隐含 size：`1.9861 / (77303.79 × 0.02720) = 0.000944` → **既非原始规模也非当前规模，而是某次中间减仓后的规模** —— 即"某次 `profit_*` 路径重置过一次，之后的 `_partial_close` 减仓再没重置过"。

4. `4660` 是另一端的极端：`peak_unrealized_pnl = 0.0` 而 `peak_pnl_pct = +0.00424` —— USD 峰值被清零（重置时浮亏为负、`max(...)` 由缓存/DB 的 0.0 兜底）但 pct 峰值保留为正 → **同一仓位同时处于"从未盈利（USD）"与"曾盈利 0.42%（价格）"两个状态**。

5. `_peak_price_from_pos`（`:303-315`）证实 pct 语义：注释 `:306` 明写「peak_pnl_pct 是**未杠杆的价格 PnL%**」，公式 `long 峰值价 = entry × (1 + peak_pnl_pct)`。因此**应以 pct（或由它反推的 `peak_price`）作为唯一基准**，而当前守卫混用两者。

**后果（资金/收益影响）**：任何"从峰值回撤 X% 就减仓/全平"的守卫（`profit_drawdown_partial` / `profit_drawdown_stage` / `profit_drawdown_full` / `exit_policy:min_roi_decay`）在混用两套基准时：

- 用 `peak_unrealized_pnl − unrealized_pnl` 计算回撤 → 对 `4659` 会得到 `1.9861 − (−0.189) = 2.175`，即"从峰值回撤 2.18 USD"，而真实回撤（同规模口径）只有 `0.297 − (−0.189) = 0.486` → **回撤被高估 4.5 倍，守卫提前触发**（对应历史修复提到的"残仓导致回撤守卫误触发"）。
- 对 `4660`（USD 峰值=0）则相反：回撤恒为负 → **守卫永不触发**。
- 同时 pct 口径仍为正（+0.424%），两条判据给出相反结论 → **同一仓位在同一 tick 内可能同时满足"该保护利润"和"从未盈利"**。
