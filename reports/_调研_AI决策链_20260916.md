### D2 — P0：LLM 失败退避被 `.env` 放大 6 倍，一次失败锁死标的长达 2–4 小时

**问题**：`.env` 把失败退避设为 `7200/14400s`，而代码默认是 `1200/2400s`。`thesis_expiry_s(tier, accepted)` 在 `accepted=False` 时返回**退避值作为该论题的 TTL**，于是失败票会在 2h/4h 内被视为「未过期但不可交易」，期间不重问。

**证据**：
```

2468: MIDLONG_THESIS_FAIL_BACKOFF_MID_S  (代码默认 1200)
2471: MIDLONG_THESIS_FAIL_BACKOFF_LONG_S (代码默认 2400)
# .env 实际值
MIDLONG_THESIS_FAIL_BACKOFF_MID_S=7200      # 6× code default
MIDLONG_THESIS_FAIL_BACKOFF_LONG_S=14400    # 6× code default

# backend/services/mlto/brain.py:126-127（退避即 TTL）
thesis_expiry_s(tier, accepted) = ttl if accepted else fail_backoff
# backend/services/mlto/brain.py:1561
dto.expires_at = _utcnow() + timedelta(seconds=thesis_expiry_s(tier, accepted=dto.accepted))
```
失败率（放大退避的乘数）：

**影响**：51.4% 的论题生成被判 `accepted=False`，每一次都让该 `symbol:tier` 在 **2h（mid）/4h（long）** 内无法重问。以 mid TTL=4h 计算，失败退避 2h 相当于吃掉半个有效期。当前会话 `fa_7e12e7a1b6` 的 mid 论题最后更新是 **2026-09-14 09:14**（long）/ **2026-09-15 08:15**（mid），远超声明的 4h/8h TTL —— 说明大量 `symbol:tier` 长期处于失败退避或未刷新状态。

**建议修复**：

**问题**：`coin_select_scans` 有 **140 行** `status='running'` 永不收敛（无 `finished_at`、无 `duration_sec`），最早回溯到 2026-08-03、最近一次 2026-09-15 14:48；同时 `done` 行中单次最长 `duration_sec=33,575.71`（**9.3 小时**）。另需注意：最近一条 scan 记录是 **2026-09-16 04:36:43**，但候选记录 `coin_select_candidates` 持续写到 **12:38:28** —— 扫描记录与候选记录的写入源已脱节。

```
--  running |  140 |       |          |  2698 |     0 | 2026-08-03 08:25:48 | 2026-09-15 14:48:49
--  failed  |    1 |       |          |    25 |     0 | 2026-08-03 06:45:30 | 2026-08-03 06:45:30
```

### D15 — P2：`AUTO_COIN_ENABLED=false` 的两条调度器行为不一致（D0 的运维面）

> **本节为初版结论的更正**：初稿曾判断「`AUTO_COIN_ENABLED=false` 是死开关，因为 AI 选币日志仍在刷」。**该判断错误，已由日志证据推翻** —— `AutoCoinScheduler` 确实被禁用（8/8 次重启打印 `已被 AUTO_COIN_ENABLED=false 禁用`）；初稿观察到的 488 条 `[AutoCoinSelector] AI 中线候选 sticky(board)` 日志来自 **midlong 循环的中线候选路径**（`auto_coin_selector.py:5673-5810`），**不是**选币调度器的 `run_selection_cycle`。这也解释了为何 mid 车道只有「冻结 sticky」而无真实注入。详见 D0。

**问题（保留为 P2）**：同一次启动中，两个功能耦合的调度器被**相反地**处理 —— 候选生成无条件启动、注入被总闸禁用，且两者都只打印 `INFO`。运维无法从日志级别区分「在跑」与「空跑」。

**证据**：
```

2026-09-16 09:05:06 [INFO] backend.main:1382 - [async] CoinSelectPlatformScheduler 已启动
# 两条都是 INFO；`已被…禁用` 在整个 4.38h 窗口只有 8 行（每次重启 1 行）
```
```

AUTO_COIN_ENABLED=false

#   [AutoCoinSelector] AI 中线候选 sticky(board) session=… picked=['DOT'] … （450 次）
```

**影响**：不直接产生交易损失，但**直接导致 D0 潜伏 11 天未被发现**。任何依赖日志级别做告警的机制都会漏掉这个组合。

**建议修复**：
1. `backend/main.py:1367-1382`：把两条启动日志改为**结构化 + 告警级** —— 当「候选生成启用 AND 注入禁用」时用 `logger.warning` 并带 `reason_code="auto_coin_inject_disabled_but_scan_active"`。
2. 在 ops 健康页暴露「候选生成状态 / 注入调度器状态 / 最近一次成功注入时间」三项对比（当前 `coin_select_adoptions` 最新一行是 2026-09-05，页面上若有此项即可立刻发现）。
3. 让 `AUTO_COIN_ENABLED` 作为**唯一权威总闸**同时管控 `CoinSelectPlatformScheduler` 与 `AutoCoinScheduler`（即 D0 修复第 2 步）。

**回滚开关**：新增 `COIN_SELECT_PLATFORM_ENABLED`（默认跟随 `AUTO_COIN_ENABLED`）；置 `true` 即回到「仅候选生成、不注入」的现行为。
