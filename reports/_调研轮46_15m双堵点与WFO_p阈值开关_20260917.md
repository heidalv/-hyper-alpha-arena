## 二、堵点 A：唯一普遍性杀手是一个硬编码常量

### 2.1 判据现场（`factor_wfo.py:545-549`，改动前）

```python
passed = (
    oos_mean >= _WFO_IC_MIN_OOS_IC     # env 可调，默认 0.01
    and oos_p < 0.05                    # ★ 硬编码，无开关、settings 未声明
    and decay_rate < _WFO_IC_MAX_DECAY  # env 可调，默认 0.50
)
```

三条判据里，**唯一杀死全部候选的那条，是三条里唯一没有开关的那条**。

### 2.2 181 条失败记录的归因

数据源：`alpha_analytics.factor_evolution_log`（16608 行，`phase='wfo'` 41 条，
`reason` 字段带逐币 `oos_ic/p/decay` 原文）。

| 指标 | min | p25 | 中位 | p75 | max |
|---|---|---|---|---|---|
| oos_ic | −0.0853 | −0.0016 | **+0.0192** | +0.0385 | +0.1046 |
| p | +0.0504 | +0.1432 | **+0.2968** | +0.5196 | +0.9961 |
| decay | −1.0000 | −0.0861 | +0.3921 | +1.0000 | +1.0000 |

单条件达标率（对 181 条失败币）：

| 条件 | 达标数 | 占比 |
|---|---|---|
| **p < 0.05** | **0 / 181** | **0%** |
| ic ≥ 0.01 | 112 / 181 | 62% |
| decay < 0.50 | 101 / 181 | 56% |

**关键**：`p < 0.05` 的达标数是 **0** —— 也就是说
**181 条失败记录里没有任何一条是因为"IC 不够"或"衰退太快"而单独失败的，
全部都有"p 不够小"这一项**。IC 和衰退率都不是主因。

### 2.3 模型复现现网（强验证）

按解析出的逐币数值重算"候选层面通过数"（判据 ic≥0.01 & decay<0.5 & ratio≥0.66）：

| p 阈值 | 通过的候选数 / 41 |
|---|---|
| **0.05（现状）** | **0** ← 与线上 4h/15m 连续 7 天 `promoted=0` **完全吻合** |
| 0.10 | 2 |
| 0.15 | 3 |
| 0.20 | **6**（饱和） |
| 0.25 / 0.30 | 6 |

模型在现状阈值下算出 0/41，而实测正是 promoted=0 —— **说明这套解析是准的，不是估计偏差**。

顺带对照"降 ratio"路线（放宽到 3/9 币通过）：ratio 0.66→0.33 只多放 5 个，
0.66→0.50 只多放 1 个 —— **说明问题不是"要求太多币"，而是"逐币 p 门槛"本身**。

### 2.4 口径不一致（这才是可论证的缺陷）

代码注释自己写过（`factor_evolution_loop.py:3205-3210`）：
> 挖掘/评估/DSR 全链都是**面板池化**口径（IC 在多币拼接序列上算），
> 门禁却要求逐币单独显著，**比池化判据严得不成比例**

而 `factor_wfo.py` 同样如此：门禁要求 9 个币**各自** p<0.05，
上游（GP/MCTS 适应度、DSR/PBO、池化 IC）全是拼接口径。
"要求每个子样本都显著"在统计上比"整体显著"严得多，且样本量被切碎后
单币的 t 检验本就难以达到 0.05。

## 三、堵点 B：15m 被路由进已判死的短线池（**比闸门更根本**）

### 3.1 分类代码

`factor_evolution_loop.py:3515-3533`：

```python
_SHORT_HORIZON_PERIODS = frozenset({"1m", "3m", "5m", "15m"})   # ★ 15m 在里面
_SHORT_FACTOR_PREFIX = "s5m_"

def _tag_one_short_horizon(factor, period):
    """短周期因子打 s5m_ 前缀 + source 含 horizon=scalp（与 4h 池隔离）。"""
    if p not in _SHORT_HORIZON_PERIODS: return factor
    factor["factor_id"] = f"s5m_{fid}"          # 15m 也被打上 s5m_ 前缀
    factor["source"]    = f"{src}|horizon=scalp|period={p}"   # 15m 被标 horizon=scalp
```

而同一个 15m 任务的入口却叫"**中周期**"（`:3549-3556`）：

```python
def run_mid_factor_evolution_loop(...):
    """中周期 15m 完整进化入口（V7 三周期正式上线）。
    大周期 4h（03:00）、中周期 15m（06:00）、小周期 5m（04:00）三条独立池…"""
```

**同一段代码里，15m 同时被称作"中周期"和被标成 `horizon=scalp`。**

### 3.2 下游是**二元池**，没有"日内"这一档

| 池 | 判定 | 位置 |
|---|---|---|
| 短线池 | `horizon != "midlong"`（**缺省也算 scalp**） | `scalp_active_factor_set.py:30-32` |
| 中长线池 | `horizon == "midlong"` | `midlong_active_factor_set.py:30,45` |
| 中长线池排除规则 | "s5m_ 前缀（短周期标记）或 source 带 horizon=scalp" | `midlong_active_factor_set.py:138` |

**结论**：因子库只有**两个**池 —— `midlong`（4h/1d）与"其余全部算 scalp"。
15m 被打标 `horizon=scalp` 后**必然进短线池**，而短线池所属的车道已被判死
（`SCALP_OPEN_DISABLED=true` + `SCALP_RESEARCH_ENABLED=false`）。

**所以 15m 有两个独立堵点**：
1. **闸门**（堵点 A）：候选在 WFO 多币闸就被杀（0/41）；
2. **路由**（堵点 B）：即使过了闸门，也会被投进死池，永远不进交易。

**只修闸门不够，只修路由也不够 —— 两个都要修。**

### 3.3 这也给出了目标④的正确形态

用户说真实结构是「**日内 + 长期趋势**」。代码现状是「**midlong + scalp**」二元，
且"日内（15m/1h）"这一档**根本不存在**，被错误地并进了已判死的 scalp。
目标④不是"改名"，而是**新增第三条池/把 15m/1h 从 scalp 里拆出来**。

### 7.4 ★ 修正轮44：「15m 被拒用」不成立于交易 universe

轮44 我据日志里 `UNI/15m stale=1902s` 判定 15m 新鲜度不达标、被 trade 路径拒用。
**本轮实测（2026-09-17 11:56）推翻了该结论**：

交易 universe = **9 个币**（`system_configs.user_trading_pairs`：
BTC/ETH/SOL/BNB/VIRTUAL/ASTER/XPL/UNI/XRP），逐 (symbol × exchange) 实测 15m age：

| 结果 | 组合数 | 说明 |
|---|---|---|
| **age = 674s（11.2 分钟）** | **41 / 45** | 三个阈值（1200/1500/1860）**全部通过** |
| age = 1574s | 2 | VIRTUAL/XPL 的 **bybit**（过 1860，不过 1200/1500） |
| age = 2474s | 3 | VIRTUAL/XPL 的 **asterdex / okx** |

**关键**：**binance 与 hyperliquid 对全部 9 个币都是 674s**。
即 —— **真正要交易的那 9 个币，主流所的 15m 是新鲜可用的**；
`kline_data_service` 本就带多所聚合与新鲜所回退（日志里 `回退到新鲜所 okx` 即是该机制）。

**所以正确表述是**：
- 15m **不是"缺数据"，也基本不是"数据不新鲜"** —— 对交易 universe 而言它可用；
- "22/788 才 <30min"说的是**全市场 927 标的**，而交易只用 **9 个**；
- 采集广度不足影响的是**全市场扫描/选币**，不是"已选中 9 币的择时"；
- 轮44 看到的 `stale=1902s` 是**特定时刻/特定所的瞬时状态**（当时值 1900s，现为 674s），不是常态。

**由此得出的重要结论**：**不必急着扩大 15m 采集广度**。
全 catalog 全量化需要 **247,392 行/天、一年 90.3 M 行 —— 超过当前全库 10 个周期总和（62 M）**，
而收益仅是"给 9 个币之外的 918 个标的补数据"。优先级应低于堵点 A/B。

> 触发条件：若将来放宽选币 universe（`user_trading_pairs` 扩容），
> 15m 广度（12% 覆盖、单标的 18 分钟刷新）会立即成为瓶颈。
