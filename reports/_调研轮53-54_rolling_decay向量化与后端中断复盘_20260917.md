## 一、评估阶段剩余热点：`rolling_decay`

### 1.1 定位

`factor_evolution_loop.py:1395` 每个候选调一次 `build_factor_card(...)`（阶段2→阶段5，
68 个候选）。该卡片内部调两个评估器：

| 调用 | 状态 |
|---|---|
| `evaluate_factor` → `time_series_ic` | ✅ 轮49 已向量化（216×） |
| **`rolling_decay`** | ❌ **自带逐窗循环，未被覆盖** |

`evaluation.py` 的 `rolling_decay` 里有**独立的** `while` 循环：

```python
ics, i = [], 0
while i + window <= len(df):
    ics.append(information_coefficient(f[i:i+window], r[i:i+window], method=method))
    i += step
```

默认 `step=7`、6770 根 ⇒ **≈967 次/币 × 9 币 × 68 候选 ≈ 59 万次 scipy 调用**。
这就是评估阶段 16.5 分钟的主要来源。

### 1.2 改动

`rolling_decay` 复用**已经过等价性验证**的 `_rolling_spearman_batch`。
触发条件严格限定：

```
method == "spearman"  AND  window >= 5  AND  FACTOR_EVAL_ROLLING_FAST 开
```

**为什么必须限定 `window >= 5`**：`window < 5` 时老路径会命中
`information_coefficient` 的 `mask.sum() < 5 → 0.0` 规则，而快路径会算出**真实相关** ——
**不等价**，必须排除。

任何异常 fail-safe 回退老逐窗路径；沿用既有开关 `FACTOR_EVAL_ROLLING_FAST`。

### 1.3 验证

| 项 | 结果 |
|---|---|
| 契约测试 | **7 → 10 项全绿** |
| 等价性 | `window/step = (20,7)/(10,3)/(30,1)/(5,5)` 且含 NaN，**rtol=0, atol=1e-12 全过** |
| 内联实测 | **maxdiff = 1.11e-16**（浮点精度内）；`trend_slope` 完全一致（`-0.0002870542554628575`） |
| 回退断言 | `window<5` 两侧均全 0.0 ✓ |
| **加速比** | **`rolling_decay` 88×**（0.357s→0.0041s）、`time_series_ic` 216.5× |

### 3.2 结论

- **watchdog 机制有效**：5 次连续探测失败后自动拉起，约 2 分钟恢复，无需人介入。
  这反向印证了"故障可见 + 自愈"是通的。
- **触发条件**：**进化收尾（阶段8 在线权重，DB 密集）与新进化启动叠加**，
  把后端压过 watchdog 的 **5s 探测阈值**。
- **根因（已知且未修）**：`evo_runtime.mark_start` 的单飞互斥是**进程内**的
  （`_state` 是内存字典，`FACTOR_EVO_MAX_CONCURRENT` 默认 2 也是进程内计数），
  **跨进程不互斥** —— 所以手工/调度并发起的多个 `evo_subprocess` 会真实并发。

### 3.3 未做的修复（下一轮抓手，需谨慎）

跨进程单飞守卫（锁文件 + PID + 陈旧锁回收）。**本轮未做**，原因：改动位于进化入口的
并发控制路径，必须配等价/并发契约测试，而本轮上下文不足以安全完成 ——
在不写测试的情况下动这条路径，风险高于收益。
