## 一、摘要

Hyper-Alpha-Arena 是一个**功能广度极大**的 AI 驱动加密货币永续合约全自动交易平台，已形成
「数据中心采集 → 三周期 Agent 决策（短线/中线/长线）→ V5 风控门禁 → Paper/实盘执行 →
学习进化反馈」的完整闭环。**核心交易链路（V5 决策核心、风控、数据中心收口）质量较高**，
前端的 Bloomberg 风格深色交易终端设计在同类个人项目中属于上乘。

主要矛盾不在「功能缺失」，而在**工程治理**：

1. **版本控制形同虚设**（整改前仅 2 个 commit、386 条未提交变更）——已在本报告附录 A 中修复；
2. **仓库卫生极差**（约 3.3GB 日志/备份/一次性脚本）——已在本报告附录 B 中修复；
3. **文档与运行时配置漂移**（README 声称的状态与 `.env` 实际开关不一致，见 §3-P0-3）；
4. **下线模块的「僵尸代码」**（DRL、套利 S1/S5/S6、Prompt 进化等已关闭但代码/路由/面板仍在）；
5. **前端类型安全流于形式**（`strict:true` 但显式 `any` 达 378 处）。

## 三、当前问题与解决方案（按优先级）

### 🔴 P0-1（已解决）Git 版本控制几乎为零

**问题**：整改前仓库只有 2 个 commit（Initial commit + 一次密钥清洗），全部业务工作（V5 决策核心、
数据中心收口、套利中心、中长线 Phase 0-5、租户隔离……）躺在工作区里没有历史、没有回滚点。

**解决**：已于 2026-08-13 完成基线提交（见附录 A）。**后续要求**：小步提交（feat/fix/chore），
禁止再次积压；每月至少一次 `git log` 自查。

### 🔴 P0-2（已解决）仓库卫生极差

**问题**：项目根目录 117+ 个 `temp_*/audit_*/check_*` 一次性脚本、约 220MB 旧启动日志、
6 份 `.env.bak.*`；工作区根目录还有 3GB 旧 PostgreSQL 备份目录。这些「排障残留」不删除，
会持续误导后续开发与 AI 工具。

**解决**：已于 2026-08-13 通过 `scripts/cleanup.ps1` 安全归档 245 项 / 3.28GB（见附录 B）。
**遗留**：6 个被运行中后端占用的文件（今天的日志、`temp_recalc_*.py`），停服后重跑一次即可。

### 🔴 P0-3（待解决）文档与运行时配置漂移

**问题**：README/架构文档声明的开关状态与 `.env` 实况不一致，会导致维护者按文档做错误判断：

| 配置项 | README/文档说法 | .env 实况 | 风险 |
|---|---|---|---|
| `DRL_SHADOW_MODE` | 「DRL 已下线，关闭 shadow」 | `true` | DRL 影子预测仍在记录？需确认是否影响性能/存储 |
| `MIDLONG_EXEC_AUTHORITY` | 「默认 trend」 | `mlto` | 中长线实际执行权在 MLTO，与文档描述不符 |
| `ENABLE_PORTFOLIO_RISK` | 架构文档默认 `false` | `true` | 组合风险层实际已启用，文档滞后 |
| `DRL_RETRAIN_AUTO` | 「协调器不再触发重训」 | `true` | 与 README 学习系统章节矛盾 |

**解决方案**：
1. 逐项核实**实际期望值**（以「你想要的运行状态」为准，而不是以哪份文档为准）；
2. 建立单一事实来源：`config/settings.py` 注释 + `README.md` 的「当前运行状态」小节，
   并新增一个 `scripts/check_config_drift.py`——启动前把 `.env` 与声明清单比对，漂移即告警；
3. 每次改开关的流程固定为「改 .env → 同步 README → 提交」，杜绝只改一边。

### 🟠 P1-1（待解决）备份无自动化

**问题**：PostgreSQL 备份目前是 2026-08-09 的一次手动快照（`pg_index_backup_20260809` +
`pg_wal_backup_20260809`，3GB），**没有定时备份、没有保留策略、没有恢复演练**。这是资金相关
系统最不该省的一环。

**解决方案**：
- Windows 任务计划程序每日 `pg_dump` 4 个库 → `postgres_backup/`，保留 7 天；
- 每月一次「恢复到空库验证」演练；
- 备份目录保持 gitignore（现状已忽略），可考虑再加一份异地拷贝（OneDrive/外置盘）。

### 🟠 P1-2（待解决）下线模块的僵尸代码

**问题**：DRL 已下线但 `services/rl/`（10 文件）、DRL 路由、协调器重训逻辑仍在；
套利 S1/S5/S6 已 deprecated 但代码与配置仍在；`ENABLE_EVOLUTION_FEEDBACK` 假开关仍在；
旧 `frontend/`（Vite）冻结但未删除。僵尸代码 = 维护者必须为「不运行的东西」持续付出理解成本，
且存在「被误开」的隐患（`DRL_RETRAIN_AUTO=true` 就是一个信号）。

**解决方案**：做一次「死代码清除」专项（建议单独一个分支）：
1. 用「引用 grep + 路由挂载清单」确认无引用后，删除 DRL 面板/路由/S1S5S6 实现；
2. 保留 README 中的「回滚方式」记录（已有），历史 commit 可回溯；
3. 归档 `frontend/` 到 `legacy/`（或直接删除，历史可恢复）；
4. 清理 3 个 venv / 4 份 requirements 为单一 `pyproject.toml`（uv）。

### 🟠 P1-3（待解决）前端类型安全流于形式

**问题**：`tsconfig` 开了 `strict: true`，但源码里有 **378 处**显式 `: any` / `as any`，
几乎全部集中在数据层（`(p: any) => ...`、`(a: any)`）。类型检查「通过」但形同虚设，
后端改字段时前端不会报错，只能运行时才发现。

**解决方案**：
1. 在 `src/types/` 建立与后端 Pydantic schema 对应的领域类型（Position/Order/Account/TierStatus…）；
2. 给 `hooks/useTradingData.ts` 等数据 hook 加泛型返回类型；
3. 用 `eslint` 规则 `@typescript-eslint/no-explicit-any: error`（新代码强制），存量按页面渐进清理；
4. 目标：核心交易页面（dashboard/live-trading/paper-trading/strategy）清零 `any`。

### 🟡 P2-1（待解决）请求层不一致

同一页面（dashboard）同时存在三种取数方式：`useAccounts()`（React Query hook）、
`useQuery`（裸 fetch）、直接 `fetch`。应统一为 `apiRequest` + React Query，超时/401 刷新/
错误 toast 才能一致生效。

### 🟡 P2-2（待解决）魔法数字与硬编码

`dashboard/page.tsx` 中 `activeAccountId ?? 14` 硬编码账户 ID=14；TopBar 报错轮询写死 30s。
应改为「取第一个 paper 账户，无则显式空态 + 引导创建」。

### 🟡 P2-3（待解决）可观测性与告警闭环不完整

- 告警目前只有飞书通知接了**套利资金费采集器**一个场景；P0/P1 报错只靠前端角标轮询；
- `logs/` 540MB 无轮转策略；
- 缺一个「系统健康总览」页面：各采集器心跳、各闭环最后活动时间、磁盘/内存、PG 连接数聚合展示。

### 🟡 P2-4（待解决）测试覆盖无法证明核心链路

141 个测试文件看似多，但缺少对「三周期决策 → 风控 → 下单」核心链路的前端 E2E，
也未见覆盖报告（coverage）基线。建议：后端核心链路 pytest 覆盖率基线 + Playwright 最小 E2E
（登录 → 仪表盘 → 查看持仓）。

## 四、各功能模块缺什么

| 模块 | 现状 | 缺什么 / 短板 | 优先级 |
|---|---|---|---|
| **数据中心（行情）** | DC_ONLY 已收口；主流币全周期补齐（BTC 1d 1798 天、binance 639 币）；asterdex 429 限流已根治 | ① 冷所短周期（1m/3m/5m）回填**仍未完成**（心跳显示排队中）；② `perp_funding` 仅 Hyperliquid+Gate 双场所，**缺第二场所完整历史**，跨所资金费套利无法完整回放验证 | P1 |
| **短线因子（Scalp）** | 因子路由+类别去重+walk-forward 脚本已落地；V5 频率治理生效 | **最大短板：缺独立的 walk-forward 回测/成本建模基础设施**——因子/阈值调整目前主要靠实盘试错验证；且趋势延续类因子在 5m 上与未来收益负相关，样本（7 天×5 币）不足以定论 | P0（对该策略本身） |
| **中长线（Mid/Long）** | Phase 0-5 已落地（Single Writer、Hub/Regime、持仓发展分析六维） | `trend_follow` 证据可用率 71-75%（4h/1d 指标偶发滞后）；Phase 5 持仓管理模式落地不久，**缺足够运行时长验证**；`MIDLONG_EXEC_AUTHORITY` 实际 mlto 与文档不符 | P1 |
| **AI 选币（VIP）** | 共用看板（短/长线）+ 管理员深度分析 + 手动采纳已上线 | 「闭环反馈 + 门控」设计文档已有（RankEngine），**落地程度未验证**；非 VIP 看不到任何预览，转化路径不完整 | P2 |
| **套利中心** | SDN delta-neutral 端到端打通（真实数据、双腿回滚、资金费计入） | Phase 5 实盘预备**仅留桩、默认硬关闭**；积分估值参数需人工补齐（当前默认「不可估」）；Gate 之外的第二场所资金费历史缺 | P1 |
| **学习进化系统** | 收敛到单一通道 `v5_runtime_gates`（复盘→反馈→NSGA-II→Kelly 夹紧） | **DRL 已下线、Prompt 进化已禁用**——「学习」实际只剩参数级闭环，缺一个替代的「策略级实验」框架（如 walk-forward 竞技场）；闭环健康卡只报时间戳不报效果 | P1 |
| **风控（V5 decision_core）** | 最完整：统一门禁+盈亏比硬约束+单笔风险硬顶 1.5%+Live fail-closed | RiskGate 仍是「串行过滤器」而非统一 `RiskPipeline` 接口（架构文档 P3 延期项）；feature-flags 运行时覆盖**仅当前进程**，重启丢失（易与 .env 漂移叠加） | P2 |
| **前端终端** | 24 页全覆盖，无占位页；设计成熟（见 §五） | 无 E2E 测试；`any` 378 处；mobile/ 未跟进；图表库三套并存史（chart.js/recharts/lightweight-charts）；响应式缺失（写死 min-w-1024px） | P1（类型）/P2 |
| **运维** | 独立数据中心进程、健康端点、kline-sync 门禁 | 备份无自动化（P1-1）；日志无轮转；告警不闭环；无恢复演练 | P0 |

**共性结论**：系统不缺「想法」和「大模块」，缺的是三样基础设施——
**回测验证设施（walk-forward/成本模型）**、**可观测性闭环（健康总览+告警）**、**配置单一事实来源（防漂移）**。

## 五、前端布局与设计评估

### 5.1 总体评价：专业、统一、信息密度高（7.5/10）

设计定位清晰：**桌面交易终端（Bloomberg 风），不是消费级 App**。`globals.css` 用 OKLCH 色彩
定义完整深色主题，交易专用色（profit=青绿涨 / loss=粉红跌 / warning=琥珀）、`tabular-nums`
等宽数字防跳动、涨跌闪烁动画，这些细节说明设计者对交易终端 UI 有真实理解。

### 5.2 做得好的（保持）

1. **信息架构合理**：Sidebar 分 5 组（交易核心/策略配置/交易所/市场&分析/系统）+
   折叠模式 + CommandPalette（Ctrl+K）快捷搜索；
2. **数据密度专业**：仪表盘 8 列 KPI 带、P&L 归因条、三周期状态卡、风险敞口带、
   活跃策略表——一屏看到全局，是交易终端的正确形态；
3. **实时性处理正确**：WS 单例 + 断线自动降级提示（「实时/轮询中」）+ React Query 缓存分层；
4. **状态可视化**：P0/P1 报错角标、WS 连接灯、三周期预算条、持仓多空徽章；
5. **代码分层清晰**：`components/layout`（壳）、`components/ui`（基元）、`lib/stores`（zustand）、
   `hooks`（数据），没有把 800 行组件堆在一起。

### 5.3 问题与改进建议（按性价比排序）

| # | 问题 | 位置/证据 | 建议 |
|---|---|---|---|
| 1 | **类型 `any` 378 处** | 全 src，`strict:true` 被显式 any 绕过 | 领域类型化 + eslint 禁止新 any（§3-P1-3） |
| 2 | **顶栏「搜索框」是假的** | `TopBar.tsx`：纯 div 写「搜索... (Ctrl+K)」，不可聚焦 | 改成真输入框，focus 即唤起 CommandPalette 并联动 |
| 3 | **请求层三种写法混用** | `dashboard/page.tsx`：hook + useQuery + 裸 fetch | 统一 `apiRequest` + React Query |
| 4 | **魔法数字** | `activeAccountId ?? 14` | 空态 + 引导创建账户 |
| 5 | **响应式缺失** | `min-w-[1024px]` | 桌面终端定位可接受，但应明确声明；或对 1280 以下给出缩放方案 |
| 6 | **无障碍** | TopBar 铃铛/退出等图标按钮无 aria-label；span 模拟进度条无语义 | 补 aria-label、progress 语义 |
| 7 | **组件复用** | `MetricCell/TierStat/RiskCell` 定义在页面底部，KPI 卡片多处重复实现 | 抽 `components/trading/`（KpiRibbon/TierCard/PositionTable） |
| 8 | **图表库未收敛** | 历史上有 chart.js/recharts/lightweight-charts 三套 | 收敛到 lightweight-charts（K线）+ recharts（统计）两套 |
| 9 | **内联样式混入** | `style={{ boxShadow, background }}` 与 Tailwind 混用 | 低频动画可保留内联，其余进 CSS 变量/工具类 |
| 10 | **无骨架屏/空态规范** | 加载态多为「加载中...」文字 | 统一 Skeleton + EmptyState 组件 |
| 11 | **无 E2E** | 无 Playwright | 最小链路：登录→仪表盘→持仓 |
| 12 | **mobile/ 名存实亡** | `mobile/` 0.4MB 未跟进 | 归档或删除，避免「假装有移动端」 |

### 5.4 设计方向建议

- 维持「数据优先、深色唯一」的定位（交易终端不需要浅色模式，当前决策正确）；
- 下一步设计重点应放在**决策可解释性可视化**：当前 AI 决策流只显示 reason 文本前 80 字，
  可加「决策时间线 + 门禁通过/拦截原因」视图（后端 BlockReport 已有数据，前端没接满）；
- 三周期卡片可进一步演进为「单屏作战图」：一屏内 K 线 + 周期状态 + 决策流联动。

## 六、架构与技术债

1. **`full_auto_trading_service.py` 未拆分**（约 0.22MB 单体）：架构文档 P3 已列入
   「拆成 decision/risk/execution/defensive/observability 5 模块」，仍未执行；
2. **RiskGate 串行过滤器**未统一为 `RiskPipeline` 接口（同 P3 延期）；
3. **双库认知成本**：PostgreSQL 4 库 + SQLite 历史数据并存，新脚本经常连错库
   （历史 bug 多为「Analytics 会话查主库表」类问题）——建议写进 onboarding 文档并加连接守卫；
4. **`schema_validator`/自动建表**与 Alembic 迁移并存：两条 schema 变更路径，长期应只留一条；
5. **中文/英文文档混杂**（docs 下 40+ 份，命名无规范），建议统一前缀 `YYYY-MM-DD_主题`。
