## 1. FIX-1（P0 正确性）：ICIR 单段退化爆炸

根因：gp_gpu_eval.compute_fitness_from_values 中 ICIR 目标 obj = |mean(case_ics)| / (std(case_ics) + 1e-10)。
当树的有限值只落在 1 个币段（其余段 NaN 或样本 <20 被跳过），case_list 仅 1 元素 → std 精确为 0 →
ICIR = |IC|/1e-10 ≈ 1e8~1e9，碾压正常因子（0.5~3），惩罚项失效，选择退化为「选单币噪声」。

修复：ICIR 目标要求有效案例段 ≥2 且 std 有下界；否则回退全面板 |IC|（与 CPU 路径一致）。

    _case_arr = np.asarray(case_list)
    if objective == "icir" and _case_arr.size >= 2:
        _std = float(_case_arr.std())
        obj = abs(float(_case_arr.mean() / _std)) if _std > 1e-3 else ic_full
    else:
        obj = ic_full

文件：backend/services/evolution/gp_gpu_eval.py:362-366
验收：新增单测：构造「仅 1 币段有效」的树 → fitness ≈ |IC|（非 1e9）；「多段有效」→ ICIR 正常尺度。

## 2. FIX-2（P1 一致性）：CPU 兜底路径与 GPU 路径适应度口径统一

根因：GPU 路径支持 objective="icir"，但 CPU 兜底 gp_miner._fitness_core 恒用 |IC|。
当 FACTOR_GP_OBJECTIVE=icir 时，每代 ~30 棵 CPU 树按 |IC|（0~1）排序、~270 棵 GPU 树按 ICIR 排序，口径不一致。

修复：_fitness_state 增加 objective 与 lens（币段边界）；_fitness_core 按段算 case IC，
objective="icir" 时用与 FIX-1 相同的 ≥2 段 + std 下界 + 回退 |IC| 公式。

文件：backend/services/evolution/gp_miner.py（_fitness_state / _fitness_core）
验收：单测：同树 CPU/GPU 路径得到同尺度 fitness。

## 3. FIX-3（P1 鲁棒性）：挖掘阶段硬预算截断

根因：_evo_budget_sec()（1800s）只截断「阶段7 补挖」；GP 挖掘 6 种子串行可跑 9~15h。

修复：GPMiner.mine() 传入预算截止时间，串行种子循环内每代检查剩余预算，耗尽即停（保留已完成种子候选）。
env FACTOR_GP_BUDGET_SEC 可调（默认 1800）。

文件：backend/services/evolution/gp_miner.py（mine / _run_seed）
验收：单测：注入极小预算 → mine() 提前返回且不抛异常、已产候选保留。

## 4. FIX-4（P1 性能/稳定性）：重挖掘出进程运行（env 门控）

根因：GPU 挖掘的 Python 级编排（逐 step/op 掩码循环，GIL 密集）在 Web 后端进程内运行，
与 uvicorn/APScheduler 争 GIL → 独立进程 6s 的求值在生产进程内 200~500s；同时拖慢 /api/health、
长持 DB 会话、重启即全丢。

修复：main.py 的 03:00/04:00/06:00 cron 改为可配置出进程：FACTOR_EVO_SUBPROCESS=1 时 task_func 用
subprocess.Popen([python, -m, backend.services.evolution.evolution_v7_runner, run, --periods, period])。
出进程天然隔离 GIL/GPU/DB，重启只丢子进程不丢主服务。

文件：backend/main.py（因子进化 cron 注册段）+ 新增 backend/services/evolution/evo_subprocess.py
验收：单测：spawn 配置下 task_func 返回 subprocess 句柄；手动冒烟 runner run --quick。

## 5. FIX-5（P2 正确性）：按周期单飞 + GPU 互斥

根因：evo_runtime.mark_start 全局单飞；4h 跑 9h 期间 5m/15m 日轮被静默跳过。

修复：mark_start 增加 period 维度——按 period 独立单飞，另加 GPU_EVO_LOCK 全局 GPU 互斥。
5m/15m 遇 4h 占 GPU 时排队而非静默丢弃（超时告警）。

文件：backend/services/evolution/evo_runtime.py
验收：单测：mark_start(4h) 后 mark_start(5m) 允许、mark_start(4h) 拒绝；GPU 互斥语义正确。

## 6. FIX-6（P2 数据安全）：挖掘断点续训

根因：无 checkpoint，8.5h 轮次被重启腰斩即全丢。

修复（轻量版）：GPMiner 每完成一个种子即把该种子 best 候选原子落盘
（data/gp_mine_progress_<period>.json，复用 checkpointing.CheckpointManager 原子写）；
mine() 启动时读取已完成种子候选，跳过这些种子继续余下种子。

文件：backend/services/evolution/gp_miner.py + checkpointing.py（复用）
验收：单测：跑 1 种子 → 模拟重启 → 新 mine() 跳过已完成种子、仅补余下。
