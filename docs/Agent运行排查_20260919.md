## 4. 错误与逻辑问题

### 4.1 【最严重】三条任务停跑 14 天，无人发现
`/api/ops/jobs` 实测 `stale=critical`：

| 任务 | cadence | 最后运行 |
|---|---|---|
| `capital_allocate` | cron 05:20 | **2026-09-05 05:20** |
| `e5_shadow_scan` | interval 900s | **2026-09-05 12:40** |
| `e5_shadow_kpi` | cron 09:10 | **2026-09-05 09:10** |

三条都停在 **09-05**（与"主脑改造"同期）。其中 **资金分配 `capital_allocate` 停跑两周**影响面最大。
**没有任何地方在展示 stale 状态** —— 这就是"断链"的代价。

### 4.2 四条任务 `never_ran` 却 `enabled=true`
`agent_param_search`、`agent_timing`、`analysis_timing`、`analysis_weekly_review`
⇒ 调度器认为"启用中"，实际一次都没跑过（`stale=never_ran`、`last=None`）。

### 4.3 `timing` 静默陈旧（16 天）
- `jobs.py:268`：「[2026-09-05] agent_timing 与 analysis_timing 重复，主脑改造后停观察侧，不再注册」→ **停用是主动决策**；
- 但 `/api/agents/status` 仍列出它（`effective_mode=observe`、`last` 指向 09-03），
  `/api/agents/latest/timing` 与 `/api/agents/timing/weights` 仍 **200 返回 16 天前数据**，
  **没有任何字段告诉调用方"这已停用"** → 任何消费者都会把旧数据当现状。

### 4.4 QAA 整族未启用
`/api/qaa/health` = unavailable，`/agents|context|latency` = 503；前端也没接。
⇒ 9 张卡片 Agent 在运行态**不存在**，但代码、卡片定义、调用链都还在（易被误认为"在跑"）。

### 4.5 两套 agent 命名空间互不相通
`/api/monitor/agents/{agent_id}` 对 `anomaly`、`execution_qa` **恒 404**（`agent_runtime_monitor.py:398-400` 只认 9 个运行时 ID），
而 `/api/monitor/agents/logs` 实测返回 **空数组** ⇒ 这两个接口对分析 agent 是"存在但永远取不到数据"。

### 4.6 正文被二次截断（设计性缺陷）
| 位置 | 截断 | 后果（实测） |
|---|---|---|
| `full_auto_routes.py:1188`、`:1275` | `reasoning[:120]` | mid/long 活动流 **83%/68% 的条目顶在 120 字符**；相对主脑 `reasoning_content`（中位 2.8~3.8 千字）**只见约 3~4%** |
| `atas_routes.py:242` | `reasoning[:200]` | 决策理由只见片段 |
| `agent-monitor/page.tsx:1010` | `line-clamp-2` | 再截一次 |

### 4.7 观察模式：**建议被记录但永不生效**
6 个观察型 agent 全部 `effective_mode=observe`。`signal_review` 的最新 `advice` 里已有
`disable_source`（目标 `dual:event_impact`，理由"超额 95% 上界 -42.4bp < 0，显著为负"，`severity=4`），
但 `applied=false`、`apply_note="observe 模式：仅记录不执行"`。
**这不是 bug，而是"分析了却不被采纳"的设计**——但它在 UI 上完全不可见，容易被误读为"agent 在起作用"。

### 4.8 死代码仍在仓库（并被当成消费者）
`backend/static/assets/AgentMonitorPanel-df0adfae.js`（2026-07-22 构建）仍在 `fetch("/api/monitor/agents/overview")`、

## 6. 为什么"一个大滚屏"是错的设计（对应用户判断）

现有唯一滚屏 `LogsTab`（`h-[560px]`、3s 轮询、`/api/system-logs/tail?lines=300`）混着**所有组件**的日志：
在这种视图里，
- 你**看不到某个 agent 的连续分析**（行被别的组件冲散）；
- 你**看不出"谁停了"**（没有期望频率对照，也没有 stale 标记）；
- 你**看不出"谁和谁相连、哪条链断了"**（没有关系视角）；
- 你**更看不出"分析结论是什么"**（正文被截断或根本没接）。

因此正确形态是：**每个 agent 一个独立滚屏 + 按边界分组 + 关系连线 + 每个节点自带"期望 vs 实测"健康位**，
一页可缩放、可拖拽地巡检 —— 具体设计见 `docs/Agent画布模块设计_20260919.md`。
