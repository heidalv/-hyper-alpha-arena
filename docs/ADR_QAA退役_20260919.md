# ADR：QAA v3 卡片编排层**正式退役**

- 状态：**已决定并执行**（2026-09-19）
- 决策人：用户（在"恢复 / 放弃 / 只记档"三选项中选定"明确退役编排层 + 保留进化桥"）
- 影响面：`/api/qaa/*`、`agent_runtime_monitor`、`job_registry` 幽灵行、`qaa/cards.py` 等死代码
- 依据文档：`docs/Agent运行排查_20260919.md`（三份独立只读排查 + 现场实测）

---

## 1. 决定

1. **退役** QAA v3 的"多智能体卡片编排层"：9 张 `AgentCard`（`services/qaa/cards.py`）、EventBus 的
   `register_agent`/`call_agent(s)` 调度路径、`qaa_scheduler` 的 `full_auto` 域、`qaa_legacy_cycle`。
2. **保留** `qaa_evolution_bridge`（进化/参数优化）。它与卡片协议**毫无关系**，只是命名撞车，
   且被 15+ 个生产模块引用（learning backend、evolution_scheduler、promotion_scan、rebate bridge、
   strategy_hypothesis…）。**后续应改名**（如 `evolution/optimizer_bridge`）以消除歧义。
3. **不为编排层保留任何"假活"痕迹**：不返回 503、不虚报健康分、不留幽灵任务。

## 2. 为什么退役（证据，全部为 2026-09-19 实测）

| 维度 | 证据 |
|---|---|
| 开关 | `.env`：`QAA_MODE=ai_first`、`QAA_V3_ENABLED=false`、`QAA_FULLAUTO_SCHEDULE_ENABLED=false`（`ai_first` 并非 QAA 的模式值，取自 `FULLAUTO_FLOW_MODE` ⇒ 等价"关闭"） |
| 启动 | `[Startup] QAA v3.0 已退役，不进主循环 (QAA_MODE=ai_first, QAA_V3_ENABLED=False)`（`startup.py:911-925`，当日 5 次） |
| 入口 | `ai_agent_entrypoint_map.py:166-172`：只有 `QAA_MODE=="qaa"` 才走 QAA；实际走 **`unified_loop_ai_first`（90s tick）** |
| 注册 | `register_qaa_agents` 唯一调用点 `qaa_legacy_cycle.py:134` ← `qaa_scheduler.py:214`（被上面的域开关挡住）；`full_auto_trading_service.py:5564/5584` 的 `_register_qaa_agents`/`_run_qaa_tick` **无任何调用点**（同文件 `:5618` 自注"路由断裂"） |
| 运行态 | 20 个日志文件 `[EventBus][QAA]`/`[QAAScheduler]`/`[FullAuto][QAA]` **0 命中**；`agent_predictions` 无 9 个卡片名；`/api/qaa/health`=unavailable、`/agents|context|latency`=**503** |
| 保留成本 | `agent_runtime_monitor` 对 9 个从未运行的卡片报 **health_score=60 假健康**；`job_registry` 4 条 `never_ran` 幽灵行 `enabled=true`；`backend/static/assets/AgentMonitorPanel-*.js`（2026-07 旧产物）仍在轮询这些空接口 ⇒ **"看着像在跑"比"明确没有"更贵**（本轮排查为此多花三份独立扫描） |
| 替代能力 | 主脑 MLTO（mid/long，`mid_open_authority=llm_thesis`）+ 6 个观察型 Agent（`job_registry` 心跳 + 可信度/评分闭环，anomaly 1624 次运行）+ `unified_loop_ai_first` + 确定性风控 |
| 当前瓶颈不在编排 | `backend/services/gil_watch.py` 实测：**无请求时进程 CPU 中位 ≈99% 单核**，瓶颈是 GIL 排队；再加一层编排只会加重 |

## 4. 回滚步骤（若将来要恢复编排层）

1. 修 3 个已知硬问题（**必须先修，否则恢复即带病**）：
   - `qaa_routes.py` 读 `card.timeout_policy`，而 `AgentCard` 无此字段（真实字段 `max_timeout_sec`）⇒ `/api/qaa/agents` 必抛；
   - `cards.py:166-168` 声明 `timeout_strategy="retry", max_retries=1`，但 `event_bus.py:584` 只把策略名打进日志、**从不重试**；
   - `agent_runtime_monitor` 的 `record_call/record_log/record_llm_usage` **无生产调用者** ⇒ 监控恒空（本次已改为读真实注册表，恢复时需重新接写入者）。
2. 重接入口：把 `register_qaa_agents` 挂回启动路径（`main.py` 或 `full_auto_trading_service`），
   并明确它与**主脑权威链**的边界（谁定开仓方向）——`timing` 被停用的原因就是"与 `analysis_timing` 职责重复"，
   恢复而不划界会重演。
3. 开关：`QAA_MODE=qaa` 且 `QAA_V3_ENABLED=true`；域开关 `QAA_FULLAUTO_SCHEDULE_ENABLED=true`。
4. 灰度：先 `observe`（`AGENT_MODE_*` 保持 observe）观察一周，看 `/api/agent-wall/state` 上这些节点是否真的产出，
   再谈生效。

## 5. 相关但**未决**的一件（不在本 ADR 决定范围）

`qaa_evolution_bridge` 的**实际产出存疑**：`data/qaa_evolution/evolution_history.jsonl` 77.3MB，
最后更新为 **11.4 小时前**，而 `qaa_optimization_cycle` 每 300s 在跑、`job_registry` 里 `last=None`（APScheduler-only）。
"周期在跑"与"产出在写"可能不一致 ⇒ **建议单独核查一次**（本次未查，不在此 ADR 断言其健康）。
