## 0. 结论

**不是某一道闸坏了，而是两个决策管线、四道闸在当前行情下互锁，使中线在两个方向都没有合法开仓路径。**

| 层 | 闸 | 当前为何全否 |
|---|---|---|
| **台账层**（系统自己的审计表） | ① `midlong_short_regime_block` **275 次/48h** | 日线 `up` ⇒ 空头**仅在下行趋势放行** |
| 台账层 | ② `cycle_conflict`（长线强多禁 mid 开空）**106 次/48h** | 长线 tier 方向为多 ⇒ 禁止 mid 反向下单 |
| 台账层 | ③ `watch:*`（等K线收盘/价格冲击/追价/失效）**157 次/48h** | 时机闸，属正常但量大 |
| 台账层 | ④ **`open_execute_false` 321 次，且不记录原因** | **其中 160 次是 mid 做多** ⇒ 位置闸的否决**没有进台账** |
| **执行层**（日志口径 5h21m） | ⑤ 位置闸 `location_gate_veto` **1012 次** | paper 下 24h 分位 ≥70% **硬否决**；实测**全市场分位 80.6–98.4%** |
| 执行层 | ⑥ SL 冷却 **120 分钟** | 侥幸过闸的标的（如 XRP）被 1.5% 上限止损打掉后，同向**锁 2 小时**（`REENTRY_SL_COOLDOWN_SEC_MID=7200`） |

**一句话**：**多头被位置闸否（行情在 24h 顶部 80–98% 分位）、空头被 regime 闸与 `cycle_conflict` 否（日线 up、长线看多）；
只有"日线 chop 拿到让位豁免"或"分位回落到 70% 以下"的极少数窗口能开，且这些仓一旦被 1.5% 上限止损打掉就被同向锁 2 小时。**
（准确口径：**不是 100% 否决**，而是"绝大多数时间、绝大多数标的被否"——见 §1.1 的 13:0x 复读。）

## 6. 次要缺陷（顺带查实，均非根因）

### 6.1 位置闸分位可 >100%（数学上不可能）

统一窗口（§1.3）中 `location_gate_veto` 共 **1012** 次，带分位 **1006** 次，其中 **120 次（11.9%）>100%**：
`103%×70、102%×12、106%×10、118%×8、107%×6、101%×6、110%×6、104%×2`；**最大 118%、最小 41%**。

**成因**：`_range_from_klines():149-155` 取 `[-24:]` 根 1h K 线的 `max(high)`；若序列/缓存
**不含进行中的那根 bar**，现价可高于所用高点。实测 UNI：含当前 bar = 98.4%，**剔除末根 = 102.5%**
⇒ 偏严约 1–4pp（极端 18%）。**影响**：70% 天花板附近会让判定偏严；本次行情下所有币本就 ≥80%，**不是根因**。

### 6.2 `open_execute_false` **不记录原因**（占全部否决的 37%）

| 事件类型 | payload 键 |
|---|---|
| `open_blocked` | `symbol, tier, reason, direction, recommend_open` ✅ |
| **`open_execute_false`** | **`symbol, tier, direction, action`** —— **无 reason**（321/321） |

按 tier×direction 拆：**mid/long 160**、mid/short 91、long/long 56、mid/neutral 14。
⇒ **160 次"中线做多"被否却查不到原因**，而位置闸的否决走的是执行器路径（`midlong_executor._record_fail`），
**不写这张台账** ⇒ 台账里"多头为什么被否"是空的。这是**可观测性缺陷**（与本次复查反复发现的"静默"同族）。

```
   （`[KlineAgg] …基准所 K 线过期…且无新鲜所可回退，拒绝聚合返回`）
   ↓
context_pack._klines 返回空 → brain._kline_ok 报 `K线:4h` / `K线:1d`（需 ≥8 根）
   ↓
missing_blocks_open(["K线:4h"]) == True  ⇒ **hard_miss=True**（硬缺项，非软）
   ↓
consensus_is_tradeable() 第一行就短路：`if hard_miss or …: return False`
   ↓
论题 accepted=False → expires_at = **失败退避 1800s**（而非 TTL 14400s）
   ↓
**这些标的永远没有可执行论题**
```

### 12.2 我尝试的修法与**诚实结果**：在本部署里不生效

**假设**：协调器那条路有 API 兜底（`[Coordinator] …数据库K线过期或不足, 从API实时拉取`），
而 prompt 这条路没有 ⇒ 给 prompt 侧补同样的兜底（复用协调器**同一个**带短 TTL 缓存的实现）。

**实现**：`agent_deep_context._api_klines_fallback()` + `_fetch_klines_for_prompt` 里
`len(rows) < count` 时补数（尾部 `count` 根，保持指标窗口一致；回滚 `PROMPT_KLINE_API_FALLBACK=0`）。
8 条单测通过（含"DB 足够时不得触发 API""回滚开关""API 失败 fail-open 回 DB"）。

**真实集成验证推翻了这个前提**：

```
[Coordinator] API获取K线失败 AVAX/1h: Unable to get K-line data for AVAX.binance:
              DC_ONLY 模式不允许直接访问交易所
```

`MARKET_DATA_DC_ONLY` **代码默认即 true**（`market_data.py:25`），DC_ONLY 下直连被**设计禁止**
⇒ **协调器那条"API 实时拉取"同样是死的**（只记失败再退回陈旧 DB）⇒ 我的兜底无从生效。

**处置（已做）**：把兜底改成 **DC_ONLY 感知**——DC_ONLY 下立即返回空，
**不再发起注定失败的调用、不再刷失败日志**；保留给非 DC_ONLY 部署/将来放开直连时可用。
新增 2 条单测钉这条语义（DC_ONLY 不调用交易所 / 非 DC_ONLY 仍走 API）。

**教训**：我做这个修复前**只看了日志里"有 API 兜底"那一行**，没验证那条路**是否真的通**
⇒ 差一步就交付一个在本部署完全无效的"修复"（与纪律 25「读数工具本身也要验收」同源，
这次是**依赖的兜底路径本身也要验收**）。

### 12.3 结论：B29 的修法在**数据中心采集侧**，不在交易后端

DC_ONLY 的设计就是"数据中心是唯一数据源" ⇒ 交易后端**不可能**自愈陈旧数据。
真正的修法：**让数据中心的 4h/1d 采集覆盖分析universe**。
证据：`kline_sync_heartbeat` 里 `p2_depth` 的 **1d/4h 池只覆盖 13 个标的**
（`src=ccxt_collector symbols=13`），而这些池之外的标的（SUI/PLAY/AVAX/ADA…）**永远拿不到新鲜长周期 K 线**。

⚠️ 这属于**另一个服务（数据中心）的配置范围**，且涉及采集成本与磁盘 ⇒ **需你拍板**，
我不擅自改。可选：(a) 扩展长周期池到分析 universe；(b) 把 midlong 批限制在有完整数据的标的上
（诚实但缩小 universe）；(c) 临时置 `MARKET_DATA_DC_ONLY=false` 放开直连（会改变全局取数路径，
**风险最高，不建议**）。
