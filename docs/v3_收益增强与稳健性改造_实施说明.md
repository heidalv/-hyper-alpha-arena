## Phase 0 · 地基与数据

### P0-1 v2 地基（止血 / edge_ledger / fee_budget / trade_facts / 模拟权益重置 5000）

- **一句话作用**：先把亏钱的车道停掉、把每条车道"净赚多少 bp"记成账、给费用设日预算，让后面的所有改动有可对比的账本。
- **模块**：`backend/services/ledger/edge_ledger.py`（车道边际账本）、`backend/services/ledger/fee_budget.py`（日费用预算）。
- **API**：
  - `GET /api/ops/edge-ledger` 各车道净 bp / PF / 置信区间；`GET /api/ops/edge-ledger/history`
  - `POST /api/ops/edge-ledger/snapshot`、`POST /api/ops/edge-ledger/reconcile`（手动快照/对账）
  - `GET /api/ops/fee-budget` 今日费用 vs 预算
- **验收**：账本能列出全部车道，费用页有数字，模拟权益 5000 起算。

### P0-2 RiskEngine 单入口 + TradingState + LIVE_KILL_SWITCH + 熔断

- **一句话作用**：所有开仓在下单前都经过**同一个**风控入口；出事时一个开关全停。
- **模块**：`backend/services/risk/`
  - `risk_engine.py` —— `pre_trade()` 顺序：精度/名义 → 单仓/总敞口 → 冷却 → **事件避险窗口** → 日配额 → 费用预算 → 连通性 → TradingState/Kill
  - `trading_state.py` —— ACTIVE / REDUCING（只平不开）/ HALTED（全停）；回撤 20% 减半、30% REDUCING；BTC 1h ≥ 8% 或 4h ≥ 12% → REDUCING 24h
  - `kill_switch.py` —— 文件 / API / 飞书命令三入口
  - `circuit_breakers.py` —— 连通性（连续失败 ≥ 3 禁开）、闪崩
  - `daily_quota.py` —— 日开仓配额**单一来源**（runtime_tuning）
  - `event_windows.py` —— 读事件总线：下架 / 监控标签 / 清算级联 → `no_open` 窗口（见 P0-4）
  - `playbook.py` —— 黑天鹅 playbook（降杠杆 1x、撤单、只留浮盈仓、冻结晋升 24h）
- **API**（`/api/ops/risk/*`）：`GET status`、`GET quota`、`POST state`（切 ACTIVE/REDUCING/HALTED）、`POST kill` / `POST release`、`POST black-swan`、`POST window`（手工加避险窗口）、`POST tick`（喂价格做闪崩检测）、`POST command`（飞书命令入口）。
- **开关**：`.env` → `RISK_ENGINE_ENABLED`、`LIVE_KILL_SWITCH`、`RISK_EVENT_WINDOWS_ENABLED`（事件避险，默认 true）、`RISK_EVENT_NEWS_BLOCK`（负面强新闻禁开多，默认 false，待 E5-5 影子验证）。
- **单测**：`tests/test_risk_engine_v3.py`、`tests/test_global_risk_kill_switch.py`（停机单测全绿是 Phase 0 验收项）。

### P0-3 job_registry + /api/ops/jobs + 心跳/失败告警

- **一句话作用**：所有定时任务登记在册，看得见"上次/下次/耗时/失败次数/心跳"，挂了会告警。
- **模块**：`backend/services/ops/job_registry.py`（登记、心跳、看门狗）、`backend/services/ops/alerts.py`（P0/P1/P2 分级，飞书 + Telegram + webhook，去重/限流）、`backend/services/ops/v3_jobs.py` / `v3_jobs_ext.py`（v3 任务注册入口）。
- **API**：`GET /api/ops/jobs`、`GET /api/ops/jobs/{name}`、`POST /api/ops/jobs/{name}/run|enable|disable`、`GET /api/ops/alerts/status`、`POST /api/ops/alerts/test`。
- **开关**：`ALERT_TELEGRAM_BOT_TOKEN` / `ALERT_TELEGRAM_CHAT_ID` / `ALERT_WEBHOOK_URLS`（留空=不启用）、`ALERT_DEDUPE_SEC`、`ALERT_P0_DEDUPE_SEC`、`ALERT_P2_ALL_CHANNELS`。
- **单测**：`tests/test_ops_jobs_alerts.py`。

### P0-5 ModelGateway（MiniMax 直连 / GLM via OpenCode / DeepSeek 仲裁）+ QuotaGuard + 四张账本表

- **一句话作用**：以后所有"让大模型做深度判断"的事（日度简报、周度复盘、事件评估、参数寻优、择时）都走同一个门：两个模型**互不见对方**独立作答 → 程序比对方向/强度/依据 → 有分歧就由第三个模型仲裁 → 得到一个 `consensus_score`；只有 ≥ 0.7 的结论才有资格成为信号，而且每条结论都落表、到期自动打分，模型"说得准不准"有账可查。
- **模块**：`backend/services/analysis/`

| 文件 | 作用 |
|---|---|
| `model_gateway.py` | 三条传输：`minimax`（MiniMax Token Plan，Anthropic 兼容 API 直连）、`glm_opencode`（GLM Coding Plan **只能**经 OpenCode 使用 → 走本地 sidecar，`opencode.json` 新增 `zai-coding-plan` provider + 只读 `analysis` agent）、`deepseek`（现有 `call_llm_api_sync`，租户 `deep_analysis` 用途 → `DEEPSEEK_API_KEY` 兜底）。`call()` 单模型；`dual_call()` 盲评 → `compare_outputs()`（方向一致 0.5 + 强度差≤2 折算 0.3 + 依据重叠 Jaccard 0.2）→ 分歧走仲裁（verdict A/B/merge/neither）→ 共识。降级：主传输不可用 → 仲裁模型顶上当主票（仲裁席位空则"规则仲裁"）；只剩一票 → `degraded`，consensus ≤ 0.6 永不入账；全无 → `skipped` + P2 告警。鉴权失败的传输冷却 30 分钟。 |
| `quota_guard.py` | 预算：深度任务 ≤ 6 次/日/模型、事件评估 ≤ 20、轻量 ≤ 40；上下文 ≤ 60k tokens、输出 ≤ 4k；5 小时窗 ≤ 30、周 ≤ 150（供应商"5h 滚动 + 周配额"的本地保守镜像）；**GLM 峰时**（工作日 14:00–18:00 北京时间，3× 消耗）深度任务自动 `degrade`。成败都计数；用量写 `llm_quota_usage`，重启回读 7 天。 |
| `context_pack.py` | 五层输入包：市场（1d/4h 收益、实现波动、ATR%、RSI、EMA 结构、BTC>EMA200、regime、30d 相关性）、资金面（funding 8h 口径 + 尾部极端、OI/多空比/24h 变化、24h 清算多空、事件总线 24h、**新闻密度/正负比** 作社交情绪代理）、持仓（权益、TradingState、RiskEngine、每仓名义/杠杆/浮盈 R/距止损/剩余 time_limit）、绩效（edge_ledger 最新快照分 tier、信号源命中率、Agent 可信度）、配置（`config_hash` + 开关子集）。带 `data_cutoff_ms` 与 hash，可回放；超预算逐级裁剪。 |
| `schemas.py` | 各任务输出 JSON 契约与校验（`daily_brief` / `event_impact` / `weekly_review` / `param_search` / `timing` / `arbiter`），模型输出不合约 → 该票作废（不修补、不造数）。 |
| `ledgers.py` | 四张表 + 评分：`analysis_runs`（每次调用/共识一行：任务、传输、模型、状态、context_hash、token/耗时、输出、consensus_score、consensus_group）、`signal_ledger`（来源/币/方向/强度/置信/期限；到期回填命中、收益 bp、相对 BTC 超额、Brier）、`agent_predictions`（Agent×kind 预测；direction 类内建评分，其它 kind 注册评估器）、`experiments`（实验卡：假设/改动/预期指标/窗口/回滚条件；proposed→running→evaluating→adopted/rejected/extended/rolled_back）。评分只用 `crypto_klines` 真实价格，拿不到价格等下轮，超 48h 标 `void`。 |
| `scheduling.py` | 非峰时 cron 助手 `off_peak_cron()`（落在峰时自动顺延到 18:05）；p0 注册 `analysis_ledger_scoring`（15 分钟到期评分）与 `analysis_quota_daily`。 |

- **API**（`/api/analysis/*`，写操作沿用 `X-Risk-Token` / 本机放行）：
  - `GET gateway/status` 三条传输配置与健康 + 配额快照；`GET quota`
  - `GET runs?task=&transport=&group=&since_hours=`、`GET runs/{id}`（含 context pack 与同组盲评/仲裁行）、`GET runs/summary?days=7`（含 `daily_brief_days`，Phase 0 "连续 7 天产出"验收指标）
  - `GET signals` / `signals/stats`、`GET predictions` / `predictions/credibility`、`GET experiments` / `experiments/stats`（建议来源采纳率 = 元评分）
  - `GET context-pack/preview?task=&symbols=&layers=` 不调模型，看输入包与 token 估算
  - `POST gateway/test {"transport": "minimax|glm_opencode|deepseek|dual"}` 连通性小样本；`POST score`；`POST experiments`、`POST experiments/{id}/transition`
- **开关（`.env`）**：`MINIMAX_API_KEY` / `MINIMAX_BASE_URL` / `MINIMAX_MODEL=MiniMax-M3`；`ZAI_CODING_PLAN_API_KEY`（只给 sidecar）/ `GLM_OPENCODE_MODEL=zai-coding-plan/glm-5.3` / `GLM_OPENCODE_AGENT=analysis`；`DEEPSEEK_MODEL`；`ANALYSIS_PRIMARY_TRANSPORTS=minimax,glm_opencode`、`ANALYSIS_ARBITER_TRANSPORT=deepseek`、`ANALYSIS_UNIVERSE`；预算 `ANALYSIS_DEEP_DAILY_PER_MODEL=6`、`ANALYSIS_EVENT_DAILY_PER_MODEL=20`、`ANALYSIS_LIGHT_DAILY_PER_MODEL=40`、`ANALYSIS_MAX_CONTEXT_TOKENS=60000`、`ANALYSIS_MAX_OUTPUT_TOKENS=4000`、`ANALYSIS_5H_CALLS_PER_MODEL=30`、`ANALYSIS_WEEKLY_CALLS_PER_MODEL=150`、`ANALYSIS_ALLOW_GLM_PEAK=false`。`LLM_USAGE_REGISTRY` 新增 `deep_analysis` / `event_impact` / `param_search` 用途。
- **sidecar**：`scripts/start-dev.ps1` 新增 `[2b]`：`.env` 有 `ZAI_CODING_PLAN_API_KEY`（或 `OPENCODE_SIDECAR_AUTOSTART=true`）且 :4096 无监听时自动拉起 `scripts/start_opencode_sidecar.ps1`（日志 `logs/opencode-sidecar.log`）。本机 `opencode-ai` 已重装为 1.18.27（原 npm shim 指向的包目录已丢失）。
- **实测（2026-09-03）**：DeepSeek 票 1.6–1.9s 返回合约 JSON；sidecar 已识别 `zai-coding-plan/glm-5.3`，请求到达 z.ai 后返回 **`Authentication Failed`**——本机两把 GLM Key（`~/.claude/settings.json` 与用户环境变量 `ANTHROPIC_AUTH_TOKEN`）对 z.ai 全部四个端点及用量接口均 401，判定 Key 已失效/套餐未续费；MiniMax Key 未提供。当前 `dual_call` 走的是设计好的降级路径（MiniMax 未配置 → DeepSeek 顶替主票；GLM 鉴权失败 → 冷却；单票 → `degraded`，不入账）。**需要你做的**：把有效的 GLM Coding Plan Key 填到 `ZAI_CODING_PLAN_API_KEY`、MiniMax 订阅 Key 填到 `MINIMAX_API_KEY`，然后 `POST /api/analysis/gateway/test {"transport":"dual"}` 看到 `status=ok`。
- **验收**：`tests/test_analysis_gateway.py` 15 项单测全绿（协议：一致→合成、分歧→仲裁 A/B/neither、单票 degraded、顶替、全无 skipped、schema 作废、鉴权冷却、预算/峰时/5h 窗、评分数学、非峰时 cron、输入包裁剪）；真库端到端：信号/预测到期评分用真实 K 线回填、实验卡状态机、`/api/analysis/*` 全部 200。Phase 0 目标"双模型日度简报连续 7 天且成本在预算内"由 Phase 1 的日度简报任务上线后，通过 `GET /api/analysis/runs/summary?days=7` 的 `daily_brief_days` 观察。

## Phase 1 · 主引擎与分析上线

### P1-1 E1 趋势引擎升级 + PositionConstruction 单入口 + ExitPolicy 三重屏障收敛

- **一句话作用**：把 v2 里唯一实测过门的收益源（主流 8 币日线趋势跟踪）做成"回测 / 实盘 / 对账三端同一份规则"的引擎，每天日线收盘后自动决定每个币该持还是该空、持多大、止损放哪；同时把全仓库 8 条各说各话的"仓位该多大"逻辑收口到一处硬帽，把"什么时候出场"收口到每条车道一份声明。

**① E1 规则源与回测复现**

| 文件 | 作用 |
|---|---|
| `backend/services/trend_core.py` | **唯一规则源**（纯函数、无 DB、无前视）：`indicators()`（EMA20/50/100/200、ATR20、60 日实现波动）、`entry_signal()`（`ema_stack`：收盘 > EMA200 且 EMA20 > EMA50 > EMA100；`l1_score` 仅对照）、`run_state_machine()`（逐 bar 持仓状态 + Chandelier = 最高收盘 − 3×ATR20，`stop_ratchet` 可选只上移）、`target_weights()` / `size_one()`（等权 / vol-target 35% / 组合 vol-target，单币帽、单笔风险帽、总敞口帽）。`TrendRules.from_env()` 读 `TREND_*`。 |

**② PositionConstruction 单一权威**（`backend/services/position_construction.py`）

## Phase 2 · 事件策略与执行

### P2-1 E5-2 / E5-3 / E5-5 事件影子车道

- **一句话作用**：把方案方向 4 的三条事件策略做成**影子车道**——同一份规则代码同时驱动 `backtest()` / `shadow()` / `live()`，信号进 `signal_ledger` 由既有评分任务事后结算，**`live()` 恒抛错**直到影子 KPI 过晋升门。

| 策略 | 规则 | horizon | 数据源 |
|---|---|---|---|
| `e5_2_funding_shock` | Δfunding 滚动 z ≥ 3 且 OI 同向增 ≥3% → **拥挤反转** | 4h | `perp_funding`（8h 结算费率）+ `position_structure` |
| `e5_3_liq_cascade` | 滚动清算额 > 历史 P99 且单边率 ≥70% → **反向均值回归** | 2h | `liquidation_ticks` / `liquidation_events`（自适应） |
| `e5_5_news_hedge` | 强度 ≥4（量纲 1–5）且 \|方向\| ≥0.5 → 负面开避险窗 + 短期方向信号 | 6h / 3h | `news_events` |

- **三模式同源**：`EventShadowStrategy.detect()` 是唯一的规则实现，回测与影子调的是同一个函数，杜绝「回测一套、实盘另一套」。`detect_scorable()` 在车道层追加**可评分性过滤**。
- **幂等**：`signal_ledger.id = sha1(策略|币|事件时刻)`。`record_signal` 走 `ON CONFLICT DO NOTHING` 但**冲突时照样返回 id**，所以入账前先查已存在集合，否则每 15 分钟重扫同一窗口会把老事件反复算成新入账。
- **晋升门（方案第七节）**：`N ≥ 30` 且平均超额 95% 下界 > 14bp 往返成本。`kpi()` 输出 `promotion_ready` 为唯一判据；`live()` 在未过门时抛 `NotImplementedError`。

#### 回测结论（2026-09-03，真库）

**E5-2 在 N=490 的样本上没有 edge，这是本阶段最重要的结论。**

| z 阈值 | 事件数 | N(4h) | 平均超额 | 95% CI | 命中率 |
|---|---|---|---|---|---|
| 3.0 | 511 | 490 | +11.5bp | [−27.3, +50.3] | 51.4% |
| 4.0 | 309 | 294 | +17.2bp | [−42.4, +76.8] | 49.3% |
| 5.0 | 223 | 213 | +42.9bp | [−32.6, +118.4] | 47.4% |
| 6.0 | 159 | 154 | −6.6bp | [−96.4, +83.2] | 45.5% |
| 8.0 | 92 | 90 | +3.6bp | [−121.6, +128.8] | 43.3% |

- 所有阈值下 95% CI 都跨 0，命中率随 z 抬高反而**下降**（51.4% → 43.3%），与「越极端越会反转」的假设相反。
- 反向检验（做顺势而非反转）：24h 反向 +57.8bp、命中 54.5%，暗示资金费突变后更像**动量延续**而非拥挤反转，但 CI 同样跨 0，不构成结论。
- **E5-3（N=3）/ E5-5（N=7）样本不足，无结论**。E5-3 的 1/2/4h 三档均为负超额、命中率 0%，方向上同样不支持均值回归假设，需累积样本后复核。

三条策略因此**全部停在影子期**，晋升门自动挡住。这正是影子车道的用途：先让数据说话，再谈资金。

#### 数据底座的三个诚实处理

1. **E5-3 数据源自适应**：`liquidation_ticks` 只有 ~5 小时（WS 刚上线），`liquidation_events` 的 coinalyze 源有 450 个小时桶 / 19.5 天。检出时自动选源——ticks 满 7 天用 30min 桶，否则回退小时桶。**P99 基线与触发值永远取自同一源同一桶宽**，绝不用小时基线去卡 30 分钟的量。两者都不足 336 桶时返回 `insufficient_history`，不降阈值硬凑。
2. **可评分性过滤**：`perp_funding` 有 847 个币，`crypto_klines` 只有 788 个且历史仅 8 个月，近 30 天覆盖达标的仅 112 个。在没有 K 线的币上产信号，`score_due()` 取不到价格 → 48h 后一律判 void。加过滤后回测跳过率从 **83% 降到 4%**，账本里每条都是可评分的。代价是策略只在主流币池上跑，`universe_size` 在回测报告里如实标注。
3. **OI 确认不降级**：`require_oi=true` 时拿不到 OI 就丢弃事件（60 天窗口内 406 次 z 命中因此被丢），不做「无 OI 也算」的妥协。敏感性分析可传参关掉，但 `.env` 默认保持方案口径。

#### 顺带修掉的三个新闻数据 bug

这三个 bug 串成一条链，导致 `news.high_impact` 事件**自上线起一条没产出**，E5-5 本来会是空壳：

| bug | 原因 | 修复 |
|---|---|---|
| `published_at` 全 NULL（5040 行） | 采集器用 `datetime.fromisoformat` 解析 RSS 的 **RFC-2822** 时间串（`'Fri, 14 Aug 2026 21:19:39 +0000'`），必然抛错 | `parse_pub_time()` 按 RFC-2822 → ISO 顺序解析；原始串完好留在 `raw_data` 里，已全量回填 |

| 桥接阈值 7 > 量纲上界 5 | `NEWS_HIGH_IMPACT_MIN` 默认与 `.env` 都是 7，而 strength 量纲是 1–5 | 改为 4；`severity` 分界从 9 改到 5 |

回填结果（`python -m backend.scripts.backfill_news_annotations`）：5040 行全部补上发布时间（0 条解析失败），983 行强度有实质变化，1217 行补上真实币种，236 行达到强冲击（≥4）。

> **E5-5 的前提必须记住**：`news_events` 的标注目前 **100% 来自关键词规则**（`confidence=0.3`、摘要带 `[kw]`），不是 LLM——`_analyze_with_llm` 一直在走降级分支。阈值是当前量纲下的经验值，**接上 LLM 标注后必须用 `backtest()` 重标定，不可沿用**。`annotation_quality()` 会在每次检出时如实报告这一构成。

- **定时**：`e5_shadow_scan`（900s，三策略各扫 24h 窗）、`e5_shadow_kpi`（BJ 09:10 汇总 → `latest_e5_kpi.json`）。到期评分复用 `analysis_ledger_scoring`，E5 不需要自己的评估器。

### P2-2 EventImpact / ParamSearch / ExecutionQA + 实验卡闭环

- **一句话作用**：补上 Agent 群的后三个成员，并把「实验卡」从一张只能写不能结的表，变成**能自己走完一生**的闭环——proposed → running → evaluating → adopted / rejected / extended，判定全部用真实账本数据。

#### 实验卡闭环（本阶段的地基）

此前 `experiments` 表有五要素、有状态机，但**没有任何代码能把 `expected_metrics` 算成数值**，卡片写得再规范也只能永远挂在 proposed。补两个模块：

| 模块 | 职责 |
|---|---|
| `services/experiments/metrics.py` | 11 个指标求值器 + scope 语法解析。`{"metric","op","threshold","scope","min_n","baseline"}` → 真实数值 |
| `services/experiments/lifecycle.py` | 状态推进：自动 start、窗口到期判定、延长与结案 |

**scope 语法**：`source:<name>`（signal_ledger 信号源）、`agent:<id>`（Agent 预测得分）、`exec:<账户或 all>`（paper_orders 执行质量）、`account:<id>`（edge_ledger 净边际）、`global`。
**指标**：`excess_bp` / `excess_lower_bp` / `hit_rate` / `signal_n` / `brier` / `agent_score` / `slippage_bp` / `reject_rate` / `partial_rate` / `fee_bp` / `net_bp`。带 `"baseline": "before"` 时改算「实验窗口 − 紧邻等长基线窗口」的差值。

**三档判定，其中一条语义是刻意设计的**：

| verdict | 含义 | 落地状态 |
|---|---|---|
| `pass` | 全部指标有结论且达标 | `adopted` |
| `fail` | 有结论但至少一项不达标 | `rejected`，`inconclusive=false` |
| `inconclusive` | **至少一项样本不足** | `extended`（重新 running），超 `EXPERIMENT_MAX_EXTENSIONS`（3）次才结案，且标 `inconclusive=true` |

把「没数据」判成「没效果」会误杀好想法，所以这两者在 `result` 里始终可区分：结案的 `inconclusive=true` 表示「没验出来」，`fail` 才是「验过了，不行」。

**安全边界**：`change.apply=false`（观察型，不碰任何生效配置）的卡自动开始；`apply=true`（改配置型）**永远**拒绝自动 start，必须人工 `POST /api/experiments/{id}/start` 带 `force=true`。这条线不会因为 Agent 升到 advise 就被跨过。

**Agent 侧接入**：`base.run()` 新增 `propose_experiment` 分支——advise 模式下把建议落成 proposed 卡（`params` 必须给全五要素，`create_experiment` 会拒收含糊建议），observe 与 dry_run 只记录不落库。这是 advise 模式**唯一**的副作用。

端到端验证（`_ptmp/_exp_loop.py`，真实账本）六条路径全通：达标→adopted、不达标→rejected、样本不足→extended、改配置卡拒绝自动开始、延长超限→rejected 且 inconclusive、多指标混合→fail。

#### 三个 Agent

| Agent | 确定性核心 | 预测 kind | 到期评分口径 |
|---|---|---|---|
| `event_impact` | 读 `event_study` 每日报告，与**上一轮**对比找显著性翻转 | `event_impact` | 只用预测**之后新发生**的事件复核方向，不拿老样本自证 |
| `param_search` | 参数扫描，三道防过拟合关卡 | `param_shift` | 该策略在预测窗口内的真实影子超额下界是否仍过成本门 |
| `execution_qa` | `paper_orders` 的滑点 / 拒单 / 部分成交 / 实际费率 | `exec_quality` | 下一窗口滑点中位数是否仍在阈值同一侧 |

**ParamSearch 的三道关卡**（这个 Agent 的目标不是「找到最优参数」，而是**让每个候选都很难通过**）：

1. **样本外切分**：按时间切 70/30（时间序不能随机切，会泄漏未来）。参数在训练段选，指标在样本外报，只在训练段好的直接丢弃。
2. **多重比较惩罚**：扫 k 组等于做了 k 次检验，用 Bonferroni 把 α 收紧到 α/k，反算 z 值。扫 6 组 z=2.638，扫得越多门槛越高。
3. **实验卡前瞻验证**：即使前两关全过也只产 proposed 卡，由生命周期任务在**未来窗口**复核。历史上好 ≠ 未来有效。

首轮扫描（2026-09-03）：三条 E5 策略的 13 组候选**全部被拦下**。其中 E5-2 在 `require_oi=false` 时样本充足（n=184 / 116 / 91），但训练与样本外超额**全为负**（−68 ~ −204bp），与 P2-1 的「E5-2 无 edge」结论独立互证。

**EventImpact 首轮**：18 个事件类型中仅 `position.oi_jump` 显著（n=345、最优持有 67h、超额 95% 下界 +328bp），其余 16 类样本不足（n < 30）不下结论。报告超过 3 天未更新则标 `stale`，本轮只读不落预测——不拿陈旧结论赌未来。

#### ExecutionQA 揪出的滑点计算 bug

体检本身的结论是好的（滑点中位数 5.0bp、拒单率 0.9%、费率 2.5bp，均在警戒线内），但过程中发现一个**会污染任何执行质量分析**的数据陷阱：

`crypto_klines` 里**同名 symbol 在不同交易所可能是完全不同的资产**——实测 `ON` 在 okx 约 72 美元、在 binance 约 0.23 美元（**372 倍**），`OPENAI` 差 10 倍，`BB` 差 1138 倍。基准价按 symbol 单键索引时会被跨所数据互相覆盖，产出 ±90000bp 的假滑点，把 30 天均值从 5bp 拉到 **42bp**。

两处修正：

1. `_minute_closes` 改用 `(exchange, symbol)` 双键，并按订单自己的 `exchange` 取基准价（滑点本就该相对下单那个交易所的价格）。
2. 判定口径从均值改为**中位数**，另设 `ABSURD_SLIP_BP=5000` 兜底剔除并在 `notes` 里报数量。

修复前后（同一份数据）：

| 窗口 | 修复前均值 | 修复后中位数 | 修复后均值 |
|---|---|---|---|
| 7d | 4.29 | 5.00 | 4.46 |
| 14d | 2.35 | 5.00 | 3.54 |
| 30d | **42.15** | 5.00 | 3.96 |
| 60d | 2.09 | 4.71 | 2.98 |

中位数在所有窗口稳定在 5bp，正是仿真器的固定滑点模型值。这个 bug 不修的话，任何基于 K 线基准价的跨所分析都会偶发地得出离谱结论。

**如实标注的能力缺口**：`paper_orders` 没有 maker/taker 标记（只存在于仿真器内存）、没有下单延迟、没有拒单原因字符串；实盘侧 `trade_facts.source='live'` 的 `fees` 常年为 0。这三项本 Agent 不评估，每次输出都在 `notes` 里说明，不用估算值凑指标。

#### 其它

- **可信度门照常生效**：三个新 Agent `max_mode=advise`，但已评分预测为 0 → 一律被强制降级到 observe。要落实验卡必须先攒够 30 条已评分预测。「没被验证过的 Agent 动不了任何东西」这条对新成员同样成立。

### P2-3 OMS：client_order_id 幂等 + 订单状态机 + maker 追价 + 日对账

- **一句话作用**：补上实盘执行里三个会直接亏钱的缺口——超时不能安全重试、订单中间态是黑洞、入场几乎全吃 taker 费——同时**默认不改现有下单方式**。

#### 三个缺口与对应解法

| 缺口 | 以前 | 现在 |
|---|---|---|
| 超时重试可能双倍开仓 | 不下发 `clientOrderId`，超时后重试/不重试都危险 | **先落 `intent` 拿到幂等键，再作为 `newClientOrderId` 下发**；交易所按此去重 |
| 订单状态黑洞 | 只有 `live_sub_positions` 的 open/closed；崩溃后不知单发没发出去 | `live_orders` 状态机：intent → submitted → acked → partial/filled/cancelled/rejected；失联标 `unknown` |
| 白吃 taker 费 | 入场几乎全是市价（Aster 有局部 maker-first） | `ExecutionAlgo` 通用 maker 追价；追不到再按 `fallback` 补市价 |

#### 状态机（唯一写入口 `transition()`）

```
intent ──submit──> submitted ──ack──> acked ──┬─> partial ──> filled
   │                   │                      ├─> filled / cancelled / expired
   └──> rejected       └──> rejected/unknown  └─> unknown（对账救回）
```

关键语义：
- **intent 必须先于发单**。落库失败 → 拒发单（防止无账本裸单）。
- **unknown 是一等状态**。超时/失联不能猜 filled 也不能猜 rejected，只能标 unknown 交给对账。
- **终态默认不可变**；对账以交易所为准改写时必须 `reconcile=True`，并把原状态写入 `recon.forced_from/to`。

#### 安全默认（真正接管是显式动作）

| 开关 | 默认 | 作用 |
|---|---|---|
| `OMS_RECORD_ORDERS` | **true** | 现有 `_place_order_fresh_client` 路径挂幂等键并落账本，**不改下单方式** |
| `EXEC_ALGO_ENABLED` | **false** | 不接管；打开后改走 maker 追价 |
| `OMS_SHADOW` | **true** | algo 路径走完整状态机但**不发真单** |
| `OMS_RECONCILE_AUTO_FIX` | **false** | 日对账只报告，不自动改写 |

要真正用 maker 追价：先 `OMS_SHADOW=true` + `EXEC_ALGO_ENABLED=true` 验证状态机，再关影子。

#### 对账原则（比仓位对账更细一层）

- 只认领 `is_ours(clientOrderId)` 的交易所订单；手工单单独列 orphan。
- 本地有、交易所无、且超过宽限期 → 标 **`expired`**（绝不是 filled）。
- 状态不一致 → 以交易所为准强制改写（需 `auto_fix=true`）。
- 我方幽灵单（交易所有前缀、本地无）→ 只告警，不擅自建仓。

#### 接入点

- `ExchangeOrder.client_order_id` + `CcxtBaseAdapter.place_order` / `AsterdexAdapter.place_order_maker_first` 下发各家参数名（binance/`newClientOrderId`、okx/`clOrdId`、bybit/`orderLinkId`、gate/`t-` 前缀）。
- `trading_commands._place_order_fresh_client`：下单前 `begin_order`、成交后 `finish_order`；`EXEC_ALGO_ENABLED` 时优先走 algo，失败回退原路径。
- 定时：`oms_stuck_scan`（300s）、`oms_daily_reconcile`（BJ 08:40）。
- API：`GET /api/oms/{status,orders,orders/{cid},reconcile/latest}`；`POST /api/oms/{reconcile,stuck/scan,shadow/execute}`。

- **测试**：`tests/test_oms.py`（20 项：幂等键格式、非法状态转移、对账不把无证据写成 filled、影子模式绝不发单、任务注册）

| **付费数据** | `research/paid_data_decision.py`：BUY/HOLD/SKIP 决策卡 | 不自动订阅 |
| **E5 研究桶** | `strategies/event/research_bucket.py`：过门可写入阶梯 | `E5_AUTO_PROMOTE=false`、`E5_RESEARCH_LIVE=false` |
| **E1 F4 → Aster** | `trend_e1_f4_gate.py`：天数 / drift / 费用 / freeze / kill / 停机单测 | `TREND_E1_LIVE_ASTER=false` |
