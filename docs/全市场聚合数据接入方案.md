# 全市场聚合数据接入方案 — 机构级对手盘数据基础设施

> **版本**：v1.0 | **日期**：2026-07-10 | **状态**：设计稿（待评审）
> **目标**：从单交易所盲人摸象，升级到全市场聚合视角，跟随大机构/大资金，做散户对手盘

---

## 一、问题陈述

### 1.1 现状：单交易所视角的致命缺陷

当前系统的数据来源高度集中在 Hyperliquid 单一交易所：

| 数据类型 | 当前来源 | 问题 |
|---|---|---|
| **鲸鱼数据** | mempool.space + blockchain.info（仅 BTC） | 只看 BTC 链上转账，看不到交易所内大单、跨所搬砖、稳定币流向 |
| **资金流动性** | Etherscan gas（已证伪为合成假数据） | 无法反映真实资金净流入/流出交易所 |
| **订单簿深度** | Hyperliquid 单所 WS | 看不到 Binance/Bybit 的盘口，无法判断全市场买卖压力 |
| **资金费率** | Hyperliquid 固定值（已修复改用 Binance/Bybit） | 仍缺 OKX/Gateio 等所，全市场费率套利视角不全 |
| **清算数据** | Coinalyze（聚合） | ✅ 已是聚合源，但只覆盖清算一项 |

### 1.2 为什么必须升级

用户的核心交易哲学（正确）：

> K线只反映价格历史，不能反映市场全貌。量化分析需要看到**做市商层面、大资金层面**的数据。我们要**跟着大机构和大资金走，做散户的对手盘**。

这要求：
1. **全市场鲸鱼监控**：不是只看 BTC 链上，而是看所有大所在永续合约上的大单开仓、CEX 的稳定币净流入、巨鲸钱包的链上行为
2. **跨所资金流**：资金从哪个所流向哪个所（USDT 充提、跨所搬套利），预示行情方向
3. **聚合订单簿深度**：把 Binance+Bybit+OKX 的盘口合并，看真实买卖墙、冰山单
4. **衍生品全市场指标**：全市场 OI、全市场多空比、清算热力图、资金费率套利空间

单凭一个交易所的数据，**只能看到冰山一角**，会被大资金收割。

## 二、现有基础设施评估

### 2.1 可复用的现成基建（好消息）

| **UnifiedSnapshot** | `unified_data_pool.py:108` | 注入 AI 决策的快照对象，加字段即让三周期策略看到新数据 |

### 2.2 关键缺口

| 无**聚合数据采集框架**（泛化的 funding collector） | 每加一个数据源要从头写 |

### 2.3 可行性验证（2026-07-10 实测，结合项目现状）

> **以下结论均通过代码实测得出，非推测。** 这是设计的地基——任何方案都必须先过这些现实约束。

#### 验证 A：ccxt 多所公共 API 直连 —— ❌ 全部超时（关键阻塞点）

实测用 `ccxt.fetch_order_book('BTC/USDT:USDT')` 直连三所：
```
binance: ❌ NetworkError (api.binance.com 直连被墙)
bybit:   ❌ RequestTimeout (8s 超时)
okx:     ❌ RequestTimeout (8s 超时)
```
**根因**：`ccxt_base_adapter.py:63-72` 创建 ccxt 客户端时 **config 里没有 proxy 配置**。本机网络环境（国内）访问 Binance/Bybit/OKX 必须走代理（`127.0.0.1:1080`），但 ccxt 客户端没透传代理。
**影响**：设计中所有"用 ccxt 多所取盘口/OI/费率"的方案，**必须先解决代理透传**，否则取不到任何数据。
**修正方案**：
- 在 `ccxt_base_adapter.py` 的 config 里加 `aiohttp_proxy` / `proxies`（读 `.env` 的 `BINANCE_HTTPS_PROXY`）
- 同理 `cross_exchange_ws_feed.py` 的 ccxt async WS 也要配 `aiohttp_proxy`
- 这是 Phase 0 的**第一优先**前置任务（不加代理，后面全是空转）

#### 验证 B：L2 订单簿基础设施 —— ✅ 存在，但当前无数据流入

`market_data_hub` 有完整的 L2 基础设施：
```
属性: _l2_store, _store_l2, get_l2, publish_l2_book
get_l2 签名: (exchange: str, symbol: str) -> Optional[L2Snapshot]
```
但实测 `get_l2('hyperliquid','BTC')` 返回 `None` —— 当前没有 L2 数据在内存。
**根因**：L2 数据的唯一写入方是 `arbitrage/cross_exchange_ws_feed.py`（`publish_l2_book`），它只在套利服务运行 + WS 连接建立后才写。若套利未启动或 WS 未连，L2 store 永远空。
**修正方案**：前端盘口 Tab 不能依赖 `get_l2`（可能为空），必须走新建的实时采集端点（带代理的 ccxt 直取），并在 UI 上正确显示"无数据"（而非等待）。

#### 验证 C：现有衍生品 API —— ⚠️ 响应超时（事件循环阻塞）

实测 `GET /api/intelligence/derivatives/BTC` → **超时**（后端健康但该端点无响应）。
**根因**：该端点内部同步调用 Coinalyze/Hyperliquid REST（经代理），阻塞了 FastAPI 同步路由 + 事件循环。这与之前"连接卡住"同一类问题。
**修正方案**：新建的中台 API 必须用**异步路由**（`async def`）+ `asyncio.to_thread` 包装同步调用，或用独立线程池，避免阻塞事件循环。

#### 验证 D：ExchangeClientFactory 路径 —— ⚠️ 文档路径错误

实际路径是 `services/exchange/exchange_factory.py`（非 `services.exchange_factory`）。设计稿引用路径需更正。

#### 验证 E：多所资金费矩阵 API —— ✅ 可复用

`GET /api/rebate/funding-matrix` 已存在且实现完善（`rebate_routes.py:606-711`），含各所费率 + 健康状态。前端 OI/费率 Tab 可直接复用，无需新建。

### 2.4 修正后的数据源能力矩阵

> 基于实测：ccxt 多所直连当前不可用（需先修代理），以下标注的是**代理修复后**的可达性。

| 数据类型 | Hyperliquid | Binance | Bybit | OKX | Gate | Aster | CoinGecko | Coinalyze | 阻塞点 |

## 三、目标数据架构

### 3.1 设计原则

1. **聚合优先**：优先用专业聚合平台（CoinGlass/Glassnode/Arkham），它们天然提供全市场视角，比逐所自采更全更准
2. **复用现有**：基于 UnifiedDataPool 的 `_capture_xxx` 模式扩展，不重建架构
3. **诚实降级**：数据源失败时空缺（标 N/A），绝不合成假数据（刚修的教训）
4. **分级接入**：免费源先上（CoinGecko/Coinalyze 已有），付费源按价值逐步加
5. **统一注入**：所有聚合数据汇入 `UnifiedSnapshot`，三周期策略自动可见

## 四、执行方案（分四阶段）

### Phase 0：代理透传 + 泛化采集框架（2-3天）⚠️ 含关键阻塞点

**目标**：先解决代理阻塞（否则后续全是空转），再把 `multi_venue_funding_collector` 的成功模式抽象成通用框架。

**0.1 代理透传（最高优先，实测阻塞点）**
- **问题**（验证 A 实测）：`ccxt_base_adapter.py:63-72` 的 ccxt config 无 proxy → Binance/Bybit/OKX 直连全部超时
- **改动**：在 config 里加代理（读 `.env` 的 `BINANCE_HTTPS_PROXY`）：
  ```python
  # ccxt_base_adapter.py __init__ 里
  proxy = os.environ.get("BINANCE_HTTPS_PROXY") or os.environ.get("HTTPS_PROXY")
  if proxy:
      config["aiohttp_proxy"] = proxy      # async WS (watch_order_book)
      config["proxies"] = {"http": proxy, "https": proxy}  # sync REST
  ```
- 同样改 `cross_exchange_ws_feed.py` 的 ccxt async 创建处（加 `aiohttp_proxy`）
- **验收标准**：实测 `ccxt.binance().fetch_order_book('BTC/USDT:USDT')` 能返回真实盘口（非超时）

**0.2 泛化采集基类**
- 新建 `backend/services/market_aggregation/aggregate_collector_base.py` — 通用基类
  - `VENUES` 列表配置、`_fetch_one_venue` 并发抓取、`_persist` 幂等写入、健康诊断、诚实空转
- whale_tracker 抽 `_fetch_from_*` 为插件注册（`WHALE_SOURCES` 列表）
- UnifiedSnapshot 加 3 个新字段（`aggregate_market`/`smart_money_flow`/`aggregate_orderbook`）

**验收**：代理修复后 Binance/Bybit 盘口可取；基类能被继承；whale_tracker 改插件式后行为不变。

---

### Phase 1：免费源全量接入（3-5天）⚠️ 依赖 Phase 0 代理修复

**目标**：用免费源把"全市场聚合视角"补齐，让 AI 第一次看到多所数据。
**前置**：Phase 0.1 代理透传必须完成，否则 ccxt 多所采集全部超时空转。

**1.1 跨所订单簿聚合**（`_capture_orderbook`）
- **不能依赖 `market_data_hub.get_l2`**（验证 B 实测：当前 L2 store 为空，只有套利 WS 运行时才有数据）
- 改为：新建 `AggregateOrderbookCollector`，用代理修复后的 ccxt 各所 `fetch_order_book` 实时聚合
- 合并 Binance+Bybit+OKX 盘口 → 计算全市场买卖失衡、跨所价差
- 注入 `UnifiedSnapshot.aggregate_orderbook`

**1.2 全市场 OI/费率聚合**（`_capture_aggregate_market`）
- 开启已有的 `multi_venue_funding_collector`（改 `.env`：`MULTI_VENUE_FUNDING_COLLECTOR_ENABLED=true`）
- 该采集器已有健康诊断 + 诚实空转（offline 时 rows_written=0 不造假），复用其 `/api/rebate/funding-collector/status`
- 新建 `AggregateMarketCollector`：聚合各所 OI → 全市场 OI 分布、费率套利空间
- 数据源：代理修复后的 CCXT 公共 API（免费）+ Coinalyze（已有）

**1.3 CoinGlass 衍生品聚合**（免费基础版）
- 新建 `coinglass_client.py`：清算热力图、全所多空比、OI 聚合
- 注册 CoinGlass 免费 API Key
- 注入 `UnifiedSnapshot.aggregate_market`

**验收**：AI 决策 prompt 里出现"全市场OI"、"跨所费率差"、"聚合盘口买卖失衡"。

---

### Phase 2：聪明钱/资金流向（5-7天）

**目标**：追踪大资金动向，实现"跟随机构做散户对手盘"。

**2.1 交易所稳定币净流入**（`_capture_smart_money`）
- 新建 `SmartMoneyFlowCollector`
- 数据源：CoinGecko（交易所交易量）+ Whale Alert（USDT/USDC 大额转账，免费额度）
- 计算：各交易所 24h 稳定币净流入/出（资金流入所=可能要买，流出=可能要卖）

**2.2 巨鲸钱包行为**（扩 whale_tracker）
- whale_tracker 插件化后新增数据源：
  - `WhaleAlertSource`：跨链大额转账
  - `HyperliquidLargeOrderSource`：Hyperliquid 大单开仓（复用现有 CVD 数据）
  - `BinanceLargeOrderSource`：Binance 大单（WS aggTrade）
- 聚合后注入 `UnifiedSnapshot.smart_money_flow`

**2.3 大户持仓变化**
- Binance `topLongShortAccountRatio`（已有，修复代理后可用）
- Coinalyze 多空比（已有）
- 聚合成"全市场大户多空倾向"

**验收**：AI 能看到"ETH 24h 交易所净流入 +$50M，大户多空比 1.8，鲸鱼净买入"。

---

### Phase 3：付费源按需接入（按预算）

**目标**：用专业数据补齐免费源覆盖不到的维度。

- Glassnode：交易所净流、链上周期指标（最推荐，机构标配）
- Arkham：巨鲸钱包标签识别（知道是哪个机构在动）
- CryptoQuant：BTC 矿工流向、交易所储备

**验收**：数据完整度面板显示"机构级数据覆盖率 >80%"。

---

### Phase 4：对手盘信号引擎（3-5天）

**目标**：把聚合数据转化为**可交易的对手盘信号**。

**4.1 散户情绪反向指标**
- 聚合多空比 + 恐贪指数 + 社交情绪 → 计算"散户拥挤度"
- 拥挤度过高 → 反向操作（散户做多拥挤→寻找做空机会）

**4.2 聪明钱跟随信号**
- 鲸鱼净买入 + 大户增持 + 资金净流入 → "聪明钱看多"信号
- 结合价格位置（低位聪明钱买入=强信号）

**4.3 流动性真空/堆叠检测**
- 聚合订单簿 → 识别大单墙、流动性真空区
- 价格接近流动性堆叠 → 预期磁吸效应

**输出**：`UnifiedSnapshot.smart_money_flow.institutional_signal`，注入三周期策略的 quant_brief 和证据清单。

"""
全市场聚合数据采集基类 — 泛化自 multi_venue_funding_collector 的成功模式。
子类只需实现 _fetch_one_venue，自动获得：并发抓取/诊断/降级/持久化。
"""
class AggregateCollectorBase:
    VENUES: list[str] = []              # 子类配置：["binance","bybit","okx"]
    CACHE_TTL: int = 60                 # 缓存秒数
    SOURCE_NAME: str = ""               # 数据源名（诊断用）

    def collect(self, symbols: list[str]) -> dict:
        """主入口：并发抓取所有venue，聚合返回。失败venue诚实跳过。"""
        results = {}
        with ThreadPoolExecutor(max_workers=8) as pool:
            futures = {
                pool.submit(self._fetch_one_venue, venue, symbols): venue
                for venue in self._healthy_venues()
            }
            for future in as_completed(futures):
                venue = futures[future]
                try:
                    data = future.result()
                    if data:
                        results[venue] = data  # 只存成功的，失败的直接不出现
                except Exception as e:
                    logger.warning(f"[{self.SOURCE_NAME}] {venue} 采集失败，跳过: {e}")
        return self._aggregate(results)  # 子类实现聚合逻辑

    def _fetch_one_venue(self, venue, symbols) -> dict | None:
        """子类实现：从单个venue抓取。失败返回None（不造假）。"""
        raise NotImplementedError

    def _aggregate(self, venue_results: dict) -> dict:
        """子类实现：把多venue结果聚合成统一结构。"""
        raise NotImplementedError

### 5.3 聚合订单簿采集器（示例实现骨架）

```python
# backend/services/market_aggregation/aggregate_orderbook_collector.py
class AggregateOrderbookCollector(AggregateCollectorBase):
    """合并多所订单簿 → 全市场买卖失衡 + 跨所价差。
    复用 arbitrage/cross_exchange_ws_feed 已有的多所 WS 连接。"""
    VENUES = ["binance", "bybit", "okx"]
    CACHE_TTL = 5  # 盘口变化快，5秒缓存
    SOURCE_NAME = "AggregateOrderbook"

    def _fetch_one_venue(self, venue, symbols):
        # 复用 cross_exchange_ws_feed 的 watch_order_book
        client = get_cross_exchange_client(venue)
        books = {}
        for sym in symbols:
            ob = client.fetch_order_book(f"{sym}/USDT:USDT", limit=20)
            books[sym] = {"bids": ob["bids"][:20], "asks": ob["asks"][:20]}
        return books

    def _aggregate(self, venue_results):
        merged = {}
        for sym in self._symbols:
            all_bids, all_asks = [], []
            for venue, books in venue_results.items():
                ob = books.get(sym, {})
                for price, size in ob.get("bids", []):
                    all_bids.append((price, size, venue))
                for price, size in ob.get("asks", []):
                    all_asks.append((price, size, venue))
            # 合并排序 → 计算全市场买卖失衡
            bid_vol = sum(s for _, s, _ in all_bids)
            ask_vol = sum(s for _, s, _ in all_asks)
            merged[sym] = {
                "merged_bid_volume": bid_vol,
                "merged_ask_volume": ask_vol,
                "global_imbalance": (bid_vol - ask_vol) / max(bid_vol + ask_vol, 1e-9),
                "best_bid": max(p for p, _, _ in all_bids) if all_bids else None,
                "best_ask": min(p for p, _, _ in all_asks) if all_asks else None,
                "cross_venue_spread": self._calc_spread(all_bids, all_asks),
            }
        return merged
```

## 八、前端数据中台页面设计

### 8.0 设计原则（铁律）

> **数据拿不到就显示"缺失"，绝不用兜底占位数据。没有就是没有。**

这是整套前端的最高约束，源于用户的核心交易思想：误导性的假数据比没有数据危害大得多——它会让人基于不存在的"信号"做出错误的开仓决策。

**三条硬性 UI 规范（贯穿全页面）**：

1. **来源透明**：每个数值必须标注数据来源（如 `来源:Coinalyze`、`来源:Binance+Bybit`）。用户随时可追溯每个数字从哪来。
2. **状态可视**：每个指标带状态标签 —— ✅实时（绿色）/ ⏳延迟（黄色，超TTL）/ ❌缺失（红色）。
3. **缺失即缺失**：数据源失败时，对应卡片变灰 + 红色"❌ 数据缺失"标签 + 失败原因（如"binance SSL timeout"），**不显示任何数字**。绝不用 0 / 50 / 1.0 这类中性占位值冒充真实数据。

### 8.8 数据流设计

**轮询模式**（非WS，复用 DataCenterView 的成熟模式）：
```
MarketIntelView
  ├── usePageActive() → 仅当前可见 Tab 才轮询（省资源）
  ├── setInterval 5s  → GET /api/market-intel/overview?symbols=选中币种
  │       └── 后端聚合：调用各数据源服务，每项标 available + source
  ├── Tab 切换 → 各 Tab 独立按需加载细分数据
  │       ├── 盘口Tab: GET /api/market-intel/orderbook/{symbol}
  │       ├── OI/费率Tab: 复用 /api/rebate/funding-matrix
  │       └── 鲸鱼Tab: 复用 /api/intelligence/whale/{symbol}
  └── 健康度: GET /api/market-intel/data-health（30s轮询）
```

**为什么用轮询而非 WS**：
- 现有 WS（wsManager）是单连接复用、账户交易快照导向，无市场数据推送通道
- 新建市场数据 WS 推送通道工程量大且非首期必需
- 5秒轮询对盘口足够实时，OI/费率/鲸鱼变化慢，60秒即可
- 参考 DataCenterView 的成熟轮询模式，风险低

### 8.9 后端 API 设计

**新建 `backend/api/market_intelligence_routes.py`**（router prefix `/api/market-intel`）：

| 端点 | 功能 | 真实性处理 |
|---|---|---|
| `GET /overview?symbols=` | 总览：每币多维数据 | 每项带 `{value, source, available, stale}` |
| `GET /orderbook/{symbol}?depth=20` | 多所聚合盘口 | 各所独立标 available，某所失败=该所null |
| `GET /data-health` | 数据健康面板 | 暴露 data_readiness_gate 的 missing/warnings |
| `GET /sources-config` | 读取数据源配置 | 返回各所开关/Key状态/健康 |
| `PUT /sources-config` | 保存配置 | 更新 .env / 内存开关 |

> ⚠️ **可行性约束（验证 C 实测）**：现有 `/api/intelligence/derivatives/BTC` 同步路由超时无响应（事件循环被同步REST调用阻塞）。**新建的中台 API 必须用异步路由**：`async def` + `asyncio.to_thread()` 包装所有同步的 ccxt/REST 调用，或用 `run_in_executor`，避免一个慢请求拖死整个事件循环。这是硬性要求，否则页面会卡死。

> ⚠️ **订单簿数据源约束（验证 B 实测）**：`market_data_hub.get_l2()` 当前返回 None（L2 store 为空，只有套利WS运行时才写入）。**`/orderbook/{symbol}` 端点不能依赖 get_l2**，必须用代理修复后的 ccxt `fetch_order_book` 实时取（Phase 0.1 前置任务），或在 get_l2 为空时降级到 ccxt 实时取。

**响应真实性规范**（所有端点统一）：
```python
# 每个数据项的标准结构
{
    "value": <实际值或null>,
    "source": "数据来源名",
    "available": true/false,    # 是否真实可用
    "reason": null/"失败原因",  # available=false时填
    "fetched_at": 1783656941    # 取数时间戳（前端判断stale）
}
```
**绝不返回假数据**：取数失败时 `value=null, available=false`，前端据此显示红色缺失。

**异步路由实现示例**（避免阻塞事件循环）：
```python
@router.get("/orderbook/{symbol}")
async def get_orderbook(symbol: str, depth: int = 20):
    # ccxt 同步调用包在 to_thread 里，不阻塞事件循环
    results = await asyncio.to_thread(_fetch_orderbook_sync, symbol, depth)
    return results  # 各所独立标 available，失败=该所null

def _fetch_orderbook_sync(symbol, depth):
    """同步聚合多所盘口（在线程池里跑）"""
    out = {}
    for venue in ENABLED_VENUES:
        try:
            client = ExchangeClientFactory.create(venue)  # 已配代理(Phase 0.1)
            ob = client.get_orderbook(f"{symbol}/USDT:USDT", depth=depth)
            out[venue] = {"value": ob, "available": True, "source": venue}
        except Exception as e:
            out[venue] = {"value": None, "available": False, "reason": str(e)[:100]}
    return out
```

**复用现有 API**（overview 内部聚合调用，注意都要包 to_thread）：
- `/api/market/exchange-quotes/{symbol}`（跨所价差）
- `/api/intelligence/derivatives/{symbol}`（衍生品，**补返回 data_sources 字段**）
- `/api/intelligence/whale/{symbol}`（鲸鱼）
- `/api/rebate/funding-matrix` + `/funding-collector/status`（多所费率+健康度，✅ 已验证可复用）
