## 二、总体原则与纪律

1. **分支隔离**：整改全部在 `remediation/2026-08` 分支进行，每整改项一个 commit，验收通过后合并 main。
2. **小步提交**：一个 commit 只做一件事（`feat:`/`fix:`/`chore:`/`docs:` 前缀），禁止混合。
3. **每项必验收**：设计文档中每项均有「验收标准」，未达验收不合并。
4. **可回滚**：每项给出回滚方式；删除类操作一律「先禁后删」——先关开关验证无影响，再删代码。
5. **实盘安全**：任何涉及下单路径的改动（R3 删除 DRG/风控相关引用时）必须在 Live 模式下 fail-closed，并跑 `v5_acceptance_check.py` 回归。
6. **停服窗口**：R2/R3/R6 涉及后端重启，需安排在实盘会话暂停的时间窗执行，执行前记录会话状态、执行后恢复。

### R1 配置漂移治理（P0）

#### 目标
消灭「文档说一套、`.env` 实际另一套」的漂移，建立可自动校验的单一事实来源。

#### 现状证据（2026-08-13 实查）
| 配置项 | README/文档声明 | `.env` 实况 | 漂移性质 |
|---|---|---|---|
| `DRL_SHADOW_MODE` | 「DRL 已下线，关闭 shadow」 | `true` | 文档滞后 |
| `DRL_RETRAIN_AUTO` | 「协调器不再触发重训」 | `true` | 文档滞后 |
| `MIDLONG_EXEC_AUTHORITY` | 「默认 trend」 | `mlto` | 文档滞后 |
| `ENABLE_PORTFOLIO_RISK` | 架构文档默认 `false` | `true` | 文档滞后 |
| DB 账号 | README/脚本写 `db_admin` | `.env` 实为 `laobao` | 文档滞后 |

> 注意：这些不一定是「配置错了」——很可能 `.env` 是**有意**的（如后来重新打开了 shadow）。
> 因此本整改项**不擅自改配置**，而是先「把事实亮出来」，由维护者逐项确认意图后再收敛。

#### 设计

**1）新建事实清单 `docs/RUNTIME_CONFIG_FACTS.md`**（单一事实来源）

结构：一张表，每行一个关键开关：

```markdown
| 配置键 | 声明意图 | 期望值 | 备注 |
|---|---|---|---|
| DRL_SHADOW_MODE | DRL 已下线，shadow 记录已关闭 | false | 2026-06-11 学习系统收敛时决定 |
| MIDLONG_EXEC_AUTHORITY | 中长线执行权走 MLTO | mlto | 2026-08 实测以 mlto 为准，README 待同步 |
```

**2）新建校验脚本 `scripts/check_config_drift.py`**

- 输入：`docs/RUNTIME_CONFIG_FACTS.md`（解析表格）+ `.env`（只读布尔/枚举值，**绝不输出密钥**）。
- 输出：逐行 `OK / DRIFT(文档=x, 实况=y) / MISSING(文档有、.env 无) / UNKNOWN(实况有、文档未登记)`；有 DRIFT 时退出码 1。
- 依赖：复用 `backend/config/env_registry.py` 的 `SYSTEM_PREFIXES` 做前缀过滤，避免误报。
- 用法：
  ```bash
  python scripts/check_config_drift.py          # 全量比对
  python scripts/check_config_drift.py --fix-doc # 只把 .env 实况回写文档（需人工确认注释）
  ```
- 挂接：`dev-start.bat` 启动后自动跑一次（仅告警不阻断）；CI 中设为硬失败。

**3）流程纪律（写入 README「配置管理」小节）**
改开关 = 改 `.env` → 同步 `RUNTIME_CONFIG_FACTS.md` → 同 commit 提交 → 跑 `check_config_drift.py` 确认 0 漂移。

#### 改动文件清单
| 文件 | 动作 |
|---|---|
| `docs/RUNTIME_CONFIG_FACTS.md` | 新建（首版收录 40+ 关键开关，从 .env 提取 + README 声明比对） |
| `scripts/check_config_drift.py` | 新建（约 150 行） |
| `README.md` | 更新「配置管理」小节 |
| `dev-start.bat` | 追加启动后漂移检查行 |
| `tests/backend/unit/test_check_config_drift.py` | 新建（3 用例：OK/DRIFT/MISSING） |

#### 验收标准
1. 脚本对当前状态输出 ≥5 条 DRIFT（证明能发现问题）；
2. 漂移项逐条**人工确认意图**后收敛（改文档或改 .env），重跑输出 `0 DRIFT`；
3. 单测通过；`dev-start.bat` 能看到检查输出。

#### 回滚
删除两个新文件、撤销 `.env`/README 修改即可；本项不改任何业务逻辑。

#### 风险
低。唯一风险是把「有意配置」误判为「错误配置」——因此脚本只报告、不自动改。

> ✅ **执行回填（2026-08-13，commit `4098635`）**

> - 首跑发现并处理 `.env` 3 个重复键（`PROMOTION_MIN_TRADES` 20/50 冲突，按 python-dotenv 实效值 50 去重并记录）；修复过程曾误删 `KLINE_SYNC_EXCHANGES` 一行，已字节级恢复并复验（dotenv 解析 472 键正常）。

### R2 数据库备份自动化（P1）

#### 目标
PostgreSQL 4 库每日自动备份、保留 7 天、有恢复演练手册。

#### 现状证据
- 4 库：`alpha_arena` / `alpha_market` / `alpha_analytics` / `alpha_snapshots`（`.env` 确认，账号 `laobao`）。
- 现仅有 2026-08-09 手动快照（已归档至 `_cleanup_archive`）。
- PostgreSQL 15 已安装（`C:\Program Files\PostgreSQL\15`，`pg_dump` 不在 PATH）。
- 已存在 `postgres_backup/` 目录且已被 gitignore（无需新增忽略规则）。

#### 设计

**1）新建 `scripts/db_backup.ps1`**

```
流程：
  1. 从仓库 .env 解析 4 个 DATABASE_URL（密码打码后仅记日志前缀）
  2. 逐库: & "C:\Program Files\PostgreSQL\15\bin\pg_dump.exe" -h localhost -p 5432 -U laobao -Fc -f postgres_backup\<date>\<db>.dump
     （-Fc 自定义格式，可用 pg_restore 恢复，体积小）
  3. 校验：dump 文件 > 1MB 且 pg_dump 退出码 0，否则标记失败并飞书告警
  4. 清理：删除 >7 天的 postgres_backup\<date>\ 目录
  5. 输出一行摘要 + 写 logs/db_backup.log（带时间戳）
```
- 密码来源：**从 `.env` 读取**（脚本内解析 `DATABASE_URL`），不在脚本硬编码；
- 每周日额外 `pg_dumpall --globals-only`（保留角色/权限定义）。

**2）Windows 任务计划**

```
schtasks /Create /TN "AlphaArena-DailyDBBackup" /TR "powershell -NoProfile -ExecutionPolicy Bypass -File D:\001Alpha\Hyper-Alpha-Arena\scripts\db_backup.ps1" /SC DAILY /ST 02:00
```

**3）恢复手册 `docs/ops/数据库备份与恢复.md`**

含：备份文件说明、`pg_restore` 恢复步骤、**每月恢复演练清单**（恢复到临时库并核对行数）。

#### 改动文件清单
| 文件 | 动作 |
|---|---|
| `scripts/db_backup.ps1` | 新建 |
| `docs/ops/数据库备份与恢复.md` | 新建 |
| `scripts/cleanup.ps1` | 增加 `-BackupDbs` 手动触发开关 |
| 任务计划 | 创建 `AlphaArena-DailyDBBackup` |

#### 验收标准
1. 手动执行 `db_backup.ps1`：4 个 dump 生成、大小 >1MB、摘要日志正确；
2. `schtasks /Query` 可见任务、下次运行时间为明日 02:00；
3. 恢复手册完成，按手册把 `alpha_analytics` 恢复到临时库成功一次。

#### 回滚
删除任务计划与脚本即可，不影响线上。

#### 风险
低。dump 期间数据库短暂只读（4 库数据量不大，实测 <5 分钟）；磁盘占用约 7 天 × dump 体积。

> ✅ **执行回填（2026-08-13，commit `6821bbc`）——部分完成，两项待用户决策**
> - 脚本 + 恢复手册已落地；首次真实运行暴露两个设计时未知的事实：
>   1. **租户 RLS 阻挡**：`alpha_arena`（57 张 RLS 表）/`alpha_analytics`（2 张）用 `laobao` 账号 dump 直接失败；需超级用户 `ALTER ROLE laobao BYPASSRLS` 或建专用备份角色（已写入手册 §1）。
>   2. **`alpha_market` 实测 36GB**（设计时估「4 库不大」是错的）：无 RLS、可 dump 但耗时以小时计；7 天全量保留需约百 GB 级磁盘。`alpha_snapshots`（7.8MB）可直接成功。
> - 脚本已按实测加固：`--lock-wait-timeout` 防锁挂起、stderr 捕获进日志、RLS 失败给出 HINT。
> - 任务计划**暂缓注册**（等角色决策与 market 保留策略确定后一起上线）；恢复演练同步后延。
> - 风险等级由「低」上调为「中」：磁盘预算与 dump 时长需纳入监控（R6 告警闭环联动）。
