# 中长线「为什么不动」透明化设计稿

> 角色：可观测性工程师 + 交易终端产品设计师
> 日期：2026-08-14 ｜ 状态：**设计稿（不改代码）** ｜ 用户反馈：「中长线停止了，是被冻结了么？这个设计不好，完全不知道怎么回事。」

---

## 0. 用户问题还原

中长线当前 0 持仓、长期「不动」，但前端没有任何「为什么」：
- 是冷却？（同向禁开 mid 240min / long 1440min，SL 后 mid 12h / long 48h，连续亏损 ×2/×3）
- 是信号？（TrendAgent score<32 大量 hold、`llm_should_open=false`）
- 是数据？（周线缺失 fail-closed、K 线不足）
- 是门禁？（MTF 否决 / 费率 RR / 组合风控 / 组合预算 / 固定币守卫）

这些状态**全部只存在于后端日志/事件流**，前端不可见 → 用户只能猜「被冻结了」。

## 1. 现状诊断（本次实读代码的证据）

### 1.1 冷却状态：**完全不可查询**（需要最小后端改动）

`backend/services/reentry_cooldown.py`（642 行）：
- 全部状态在**进程内存**：`_state`（per `account_symbol_tier` → `(closed_side, ts, tier, multiplier, effective_cd)`）、`_loss_history`、`_reduce_cooldowns`、`_ai_reverse_last`。
- **没有任何只读查询函数**。唯一能拿到「原因+剩余分钟」的是 `reopen_blocked(account, symbol, action, tier)`——但它有**副作用**：冷却过期时会 `del _state[matched_key]`（自清理），且语义是「对一次开仓尝试的判定」，不是「快照」。
- 冷却数值来源：`TIER_PROTECTION_PARAMS[tier]["cooldown_sec"]` + 环境变量 `REENTRY_LOSS_COOLDOWN_SEC_{TIER}` / `REENTRY_SL_COOLDOWN_SEC_{TIER}`；连亏倍率 `_get_loss_multiplier`（4h 窗口内 ≥2 笔连亏 ×2、≥3 笔 ×3）。
- 另有 DB 耐久冷却 `_durable_reopen_blocked`（回查 `PaperPosition` closed 行）——**这条可以只读查询**。

### 1.2 中长线阻断链路：事件其实都记录了，只是没暴露

`backend/services/full_auto/midlong_helpers.py` `try_execute_independent_agent_open` 中的每个门禁都会三路留痕：
1. `host.append_event(session, "midlong_cooldown_block", "[中长线冷却] ...")` → 写入 `session.event_log`（`full_auto_trading_service._append_event`：**持久化到 DB**，数组上限 200 条，含 `{time,event,detail,severity?,trace_id?}`）；
2. 事件名含 `block/cooldown/rebound_gate/...` 的**同时汇入 `BlockReportAggregator`**（内存 Top-N，`GET /api/system/block-report-top` 已可查）；
3. `persist_independent_scan_log(agent_source="..._cooldown_blocked")` → 写入 `ai_decision_logs`（analytics 库），`/arena/model-chat` 已可查（含 `agent_source`、reasoning）。

已确认的 midlong 门禁事件名（`append_event` 第二参）：`fixed_symbol_gate_block`、`midlong_1w_missing`、`midlong_mtf_block`、`midlong_funding_block`、`midlong_portfolio_block`、`portfolio_budget_block`、`midlong_cooldown_block`、`midlong_chop_soft`（soft 不算 block 但值得展示）。

### 1.3 前端数据契约错位（现状卡片「看着有数、实际是 —」的直接原因）

| 前端类型/字段 | 后端真实返回 | 结论 |
|---|---|---|
| `TierInfo.active_strategies` | `active_count`（另有 `strategy_count`/`paused_count`） | **字段名不匹配** |
| `TierInfo.budget_used` | `budget_allocated` / `budget_max` / `budget_utilization` | **不匹配** |
| `TierInfo.budget_pct` | 无此字段（有 `budget_utilization`） | **不匹配** |
| `TierInfo.drawdown` / `win_rate` | tier-status **根本没有** | 恒显示 "—" |
| `TierActivityItem`（time/symbol/action/reasoning） | 真实字段还有 `block_reason`（verdict.reason≤80）、`allowed`、`executed`、`confidence`、`source`、`direction`、`lane_note` | **丢字段** |

> 结论：dashboard 三周期卡目前大部分单元格显示 "—"/0，决策时间线不显示 `block_reason`——用户看到的是一片「空转感」。

### 1.4 可复用的现成能力

- `GET /api/full-auto/tier-activity/{sid}`：每条已带 `block_reason`（来自 `DecisionSnapshot.evaluate_verdict_json`，由 `decision_snapshot_writer.py` 写入）——**评估过的提案的门禁原因已经在数据里**，前端只是没渲染。
- `GET /api/system/block-report-top`：门禁拦截 Top3（24h 窗口），可直接复用。
- `session.event_log`（DB、≤200 条）：最完整的有序事件流，但**没有公开端点**（仅 debug/health-check 暴露 count/last_3）。

## 2. 目标与原则

1. **一句话回答「中长线为什么不动」**：每个 tier 卡顶部一行状态摘要（冷却中 N 个 / 等信号 / 数据缺失 / 门禁拦截），点击展开明细。
2. **只读优先**：后端只加「读」能力，不碰任何写路径/风控逻辑；`reopen_blocked` 等判定函数原样保留。
3. **诚实**：无数据就显示「暂无记录」，绝不臆造「正常」。
4. **最小后端改动**：3 个新增只读函数/端点 + 0 个既有端点行为变更。

## 3. 信息架构

```
仪表盘 / 三周期状态
└─ TierCard（每 tier 一张）
   ├─ 头部：tier 名 · 策略数(active) · 持仓数 · 保证金利用率
   ├─ 状态摘要行（本次新增，核心）：
   │   ● 冷却中：N 个标的（近 4h 内平仓/止损 → 同向禁开剩 Xm）
   │   ● 等信号：最近 N 次 hold（score 阈值 / LLM 未建议开仓）
   │   ● 数据缺失：1w/1h K线不足、StrictData 未就绪
   │   ● 门禁拦截：近 24h N 次（MTF/费率/组合/固定币…）
   │   状态为空时显示「等待下一个分析周期（tick=240s）」
   ├─ 明细区（点击展开/默认折叠）：
   │   ├─ 冷却矩阵表：symbol × 方向 × 剩余分钟 × 原因（×连亏倍率徽标）
   │   └─ 拦截原因流：最近 20 条事件（时间 + 门类 + 原文），复用 block-report 词条
   └─ 底部：最近 1 条决策（现有 lastAct 保留）

/strategy 三周期总览
└─ StrategyTierCard 追加同样的「状态摘要 + 冷却/拦截明细」（复用同一组件）

全局：AI 决策时间线（DecisionTimeline）每条增加「允许/拦截」徽标 + 展示 block_reason
```

## 4. 后端改动设计（最小）

### 4.1 `reentry_cooldown.py` 新增只读快照（不改既有函数）

```python
def get_cooldown_snapshot(account_id: int) -> list[dict]:
    """只读快照：account 下所有未过期冷却条目（纯读、无任何副作用/删除）。
    返回 [{symbol, tier, closed_side, remain_min, effective_min, multiplier, reason}]，
    补 DB 耐久冷却（_durable 逻辑）后合并去重。"""
```
- 纯 `with _lock` 读 + 复用现有 `_state`/`_reduce_cooldowns`/`_ai_reverse_last` 与 `_durable_reopen_blocked` 的查询逻辑（抽一个共享只读 helper，**不调用** `reopen_blocked` 以免触发过期删除）。
- reason 复用现有中文文案生成逻辑（同向/反向/连亏倍率/SL 延长/总控全平）。

### 4.2 新增端点 `GET /api/full-auto/cooldowns/{session_id}`

- 输入：session_id；内部解析 `trading_account_id`（paper→`paper_account_id`），调 `get_cooldown_snapshot`。
- 返回：`{session_id, as_of_iso, items: [ {symbol, tier, side, remain_min, effective_min, multiplier, reason} ]}`。
- 空冷却 → `items: []`（诚实）。

### 4.3 新增端点 `GET /api/full-auto/events/{session_id}?limit=50&severity=`

- 直接读 `session.event_log`（DB 已持久化），按时间倒序返回：
  `{session_id, events: [ {time, event, detail, severity, trace_id} ]}`。
- `severity` 过滤可选；不做任何新写入。

### 4.4 （可选，建议做）`tier-status` 增加 `state_summary` 聚合字段

在既有 `tiers[t]` 上追加（**向后兼容**，旧字段不动）：

```json
"state_summary": {
  "cooldown_count": 2,
  "cooldown_items": [{ "symbol": "ETH", "remain_min": 187, "reason": "刚平多仓未满240分钟…" }],
  "last_block": { "time": "08-13 22:10", "event": "midlong_cooldown_block", "detail": "[中长线冷却] ETH buy tier=mid …" },
  "last_hold": { "time": "08-13 22:00", "symbol": "BTC", "reasoning": "score=28 < 32…" },
  "data_gap": ["1w"],
  "status": "cooldown" | "waiting_signal" | "data_gap" | "gate_block" | "idle"
}
```
- 数据来源：① `get_cooldown_snapshot` 过滤该 tier；② `session.event_log` 倒序取该 tier 最近 block/hold；③ 复用 `inject_midlong_indicators` 的 `indicators_1w` 缺失判断（只读，不触发补 K 线）。
- 前端**以 state_summary.status 为主标题、明细展开为辅**，接口 30s 轮询即可（沿用现有轮询节奏）。

## 7. 验收标准

1. **后端**：`get_cooldown_snapshot` 纯只读（单测断言：调用后 `_state` 键数不变、过期条目不清除）；`/cooldowns/{sid}` 与 `/events/{sid}` 返回结构符合 §6；无冷却/无事件时返回空数组而非报错。
2. **契约修正**：dashboard 三周期卡显示真实 `active_count`/`budget_utilization`（不再是恒 "—"/0）；`tsc --noEmit` 0 错误。
3. **透明化达成**：注入一个「刚平仓」场景（用测试账号下单→平仓或 mock `record_full_close`），三周期卡状态摘要显示「冷却中 1 · ETH 剩 187 分钟」；拦截原因流可见 `midlong_cooldown_block` 原文。
4. **hold 可见**：TrendAgent `score<32` 的 hold 出现在状态摘要「等信号」计数与拦截流中（来源 `persist_independent_scan_log` / `tier-activity.block_reason`）。
5. **回归**：既有 `/tier-status` 旧字段不变（向后兼容）；`reopen_blocked` 行为不变（其单测/集成测试全绿）；重启后端后新端点可用。
6. **性能**：三个新端点均为轻查询（内存快照 / 单行 event_log / ≤200 条过滤），前端轮询沿用现有节奏，不新增高频请求。

## 8. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 只读快照误触冷却清理 | 快照函数**不调用** `reopen_blocked`（其内部会删过期条目），只读 `_state`；单测锁死 |
| 契约修正导致 dashboard 三周期卡短暂「数字变化」 | 属预期修正；用截图对比前后（从 "—" 变为真实值） |
| 新增端点增加 DB 读 | `events` 读单行 JSON 字段（≤200 条），`cooldowns` 读内存；无新增表/索引 |
| 状态摘要 status 误判 | 判定优先级写死 `cooldown > data_gap > gate_block > waiting_signal > idle`，且字段缺失时回落 `idle`（诚实） |
| 回滚 | 全部为新增端点/字段/组件，独立可删；`tier-status` 仅追加字段不改旧字段 |

## 9. 范围外（本轮不做）

- 不改任何风控/冷却判定逻辑（`record_full_close`、`reopen_blocked`、门禁顺序原样）。
- 不做「手动解除冷却」按钮（运维需求另立；现有 `clear_all_cooldowns` 仅调试用，不暴露为 UI）。
- 不做冷却的跨进程/DB 持久化（现状内存态已知，本设计只读快照，持久化属另一项架构改进）。
- 不动中线「AI 选币」候选列表的展示（那是另一个数据源，另行设计）。
