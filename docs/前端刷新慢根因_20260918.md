# 前端数据刷新慢（切模块后 20s+ 才刷出）根因取证

日期：2026-09-18　范围：只读诊断，**未修改任何代码/配置，未重启任何服务**
被测实例：后端 pid 19064（`scripts/run_uvicorn_dev.py`，:8000）、数据中心 :9100、前端 dev :5273

---

## 0. 一句话根因

**后端的 GIL 被本进程自己的后台循环长期占满（无任何请求时进程仍中位占用 ≈99% 单核），
而所有数据端点都是同步 `def` 处理器、必须排队等 GIL；
叠加"每请求做了远超必要的 ORM 工作"和"前端每页 4~5 条秒级轮询 + 全局 3 秒 ticker-bar"，
于是每个请求从 25ms 级退化到 0.2~4.6s（数据源异常时 30s 级），
页面切换后需要多轮轮询才能凑齐正确数据。**

根因不在数据库（引擎层查询实测 6~190ms），**也不在 CPU 算力不足**——
是**单进程 GIL 上限 ≈1 核**这一结构性约束被后台负载吃满后的排队效应。

## 1. 证据链（逐跳，每跳一个可复现的读数）

### 1.1 数据库与引擎层不是瓶颈

| 测量 | 结果 | 脚本 |
|---|---|---|
| `get_balance` / `get_positions` / `get_orders` / `get_summary` 墙钟中位 | 8.2 / 23.0 / 105.4 / 16.7 ms | `scripts/profile_readonly_endpoints.py` |
| 上述调用的 **SQL 语句条数** | 5 / 12 / **2** / 4 条 | `scripts/diagnose_orders_n_plus_one.py` |
| `get_orders` 的 SQL 耗时 | 25.2 ms | 同上 |

⇒ 端点秒级耗时**不可能**由查询本身解释。数据库（PG15，`alpha_arena`）没有出现池耗尽或锁等待。

### 1.2 慢请求的真实分布：不是毛刺，是"地板"

`logs/backend.log` 中 `SLOW ≥3s` 共 **242 条**（脚本 `scripts/analyze_slow_structure.py`）：

- 中位 **3.8s**，**79%（192 条）挤在 3~5s**；最大 33.1s；
- **按端点**：`ticker-bar` 61、`paper/positions` 48、`paper/balance` 41、`full-auto/tier-status` 32、`paper/orders` 24、`paper/summary` 15；
- **孤立慢请求中位 3.70s ≈ 成簇（同秒多个）3.90s** ⇒ 不是"全局停顿"，而是**每个请求各自慢**；
- ≥18s 的 14 条**全部**是 `paper/balance|positions` 且集中在 14:31–14:32，
  **那是我重启数据中心的窗口**（DC_ONLY 下取价等待 30s 超时）＝**采样污染，必须剔除**。

### 1.3 "排队"而非"单请求固有成本"（决定性对照）

同端点、串行（空载）vs 并发 20（脚本 `scripts/probe_http_queue_vs_intrinsic.py`）：

| 端点 | 串行 | 并发20 | 放大 |
|---|---|---|---|
| `/api/health`（**async**） | 27 ms | 61 ms | ×2.3 |
| `/api/paper/orders/14`（sync def） | 363 ms | **3593 ms** | **×9.9** |
| `/api/paper/positions`（sync def） | 84 ms | 740 ms | ×8.8 |
| `/api/market/ticker-bar` | 29 ms | 214 ms | ×7.3 |

⇒ 若是 GIL 饥饿，async 端点同样要抢 GIL；实测 async 几乎不退化、同步端点放大 ~10 倍，
**瓶颈是"同步处理器专属的排队"**，而不是 CPU 被外来进程抢走。
`orders` 并发下的 3.59s 与生产 SLOW 中位数 3.5s 吻合。

### 1.4 进程 CPU：无请求时也已饱和（这是根因的物理层）

12 分钟监视（每 2s，`scripts/monitor_cpu_vs_latency.py`，223 样本）：

- 进程 CPU **中位 102% 单核**、**67% 的样本 >80%**、峰值 365%；
- 同一端点**串行**探测：`orders` 中位 **422ms**、**31% 样本 >1s**、峰值 4.6s；
- **高 CPU(>60%) 时 orders 中位 708ms，低 CPU(≤60%) 时 184ms ⇒ 3.8 倍**（r=+0.26）。

A/B/A 复核（`scripts/verify_per_request_cpu.py`，12 个空载窗）：

- **空载窗 CPU 占用：中位 99%、最小 19%、最大 138%** ⇒ **一个请求都不发，进程也常年贴在 1 核上**。

> **纪律性更正**：先前一版混合负载测出"188ms CPU/请求"，因与后台阵发混淆（该值甚至大于部分请求的墙钟中位，物理上不成立），**已撤回**。
> 可靠结论只有一条：**后台负载本身已逼近 GIL 上限**。

### 1.5 为什么"与因子任务计数不相关"

`scripts/correlate_slow_with_load.py` 给出 `SLOW vs 因子计算 r=+0.013`、`vs LLM r=+0.018`。
这**不代表"无关"**：1.4 已证明 CPU 是**近乎持续**饱和（67% 样本 >80%），
离散任务计数在这种"一直满"的状态下本就无法分辨——相关性检验的适用条件不成立，**该否定结论作废**。

### 1.6 前台请求量：76% 来自同一页的 4 条轮询 + 全局 ticker

真实访问日志（15,034 条去重请求，07:02–15:24，`scripts/analyze_frontend_request_pattern.py`）：

| 端点 | 次数 | 占比 |
|---|---|---|
| `/api/market/ticker-bar` | 3,765 | 25.0% |
| `/api/paper/positions` | 1,996 | 13.3% |
| `/api/paper/summary` | 1,917 | 12.8% |
| `/api/paper/balance` | 1,874 | 12.5% |
| `/api/paper/orders` | 1,833 | 12.2% |

- **`/paper/*` 合计 50.7% + ticker-bar 25.0% = 75.7%**；
- 活跃时段 ~100 请求/分（峰值 238/分，后者是我 15:24 起的探测造成）；
- **非 2xx 响应 = 0**；**`/auth/refresh` 调用 = 0**
  ⇒ **"重试放大"与"令牌续期阻塞"两条假设被日志直接排除**。

前端轮询配置（源码）：

`live-trading/page.tsx` **3s / 3s / 5s**；
`components/layout/TickerBar.tsx` **3 秒**（其注释自陈 ticker-bar 曾占全站请求量 48.5%）。

### 1.7 每请求做了远超必要的工作（独立可修项）

`/api/paper/orders/14?limit=50`（`backend/services/paper_trading_engine.py:4773`）：

```python
orders = q.order_by(PaperOrder.id.desc()).limit(limit).all()      # 50 条
positions = db.query(PaperPosition).filter(
    PaperPosition.account_id == account_id
).all()                                                            # ← 全量！含已平仓
```

账号 14 实测（`scripts/anchor_paper_row_counts.py`）：

- `paper_positions` **3,124 行（open 仅 8，closed 3,116）**；`paper_orders` 12,135 行；
- cProfile：一次 `get_orders` 触发 **63,480 ÷ 20 = 3,174 次 `_populate_full`**
  = **3,124 持仓 + 50 订单**，数字精确吻合 ⇒ **每次请求把这 3,124 行全部物化成 ORM 实体**；
- 成本实测：**全量 ORM 84.52ms vs 只取 8 条 open 1.39ms —— 60 倍**；
  即使只取 7 列全量也要 25.54ms。

`/api/paper/positions`（同文件 4703）在缓存未命中时还要：**每持仓一次实时价查询**
+ **每币种一次 `compute_net_position` 净额计算** + **事件溯源对拍**（外层套 5s TTL 缓存）。

### 1.8 切页存在**两级瀑布**（前端结构性等待）

`frontend-next/src/app/paper-trading/page.tsx:28-47`：

```ts
const { data: accounts } = useAccounts();                      // 波1：/api/account/list
const activeAccountId = selectedAccountId ?? paperAccounts[0]?.id ?? null;
const { data: balance } = usePaperBalance(activeAccountId);     // 波2：enabled: !!accountId
const { data: openPositions } = usePositions(activeAccountId, "open");
const { data: orders } = useOrders(activeAccountId);
const { data: summary } = usePaperSummary(activeAccountId);
```

四个数据查询全部 `enabled: !!accountId`（`useTradingData.ts:47/61/71/81`）
⇒ **必须等波1（账户列表）返回后才会发出**。`useAccounts` 的 `staleTime: 30s`，
所以切页间隔超过 30s 时波1 必然重新取数，切页总等待 = 波1 + 波2（而非一次并发）。

按真实瀑布重测（`scripts/reproduce_switch_with_waterfall.py`，浏览器 6 连接口径）：

| 情形 | 波1(账户) | 波2(4 类数据) | **数据齐全** |
|---|---|---|---|
| 纯切页 | 52~283 ms | 191~1385 ms | 中位 **1070ms**，最大 1660ms |
| 切页 + TickerBar/ops 抢连接 | 66~664 ms | 190~1142 ms | 中位 **634ms**，最大 1806ms |

> **纪律性更正（第二次）**：先前一版复现（`reproduce_module_switch_latency.py`）把 5 个请求
> **一次性并发**打出，**未建模波1依赖**，因此低估为 200ms。真实路径是 0.6~1.8s。

### 1.9 前端放大器（已核实，但**不足以单独解释 20s**）

- `components/providers/QueryProvider.tsx`：`retry: 2`（默认退避 1s/2s）、`staleTime: 15_000` 全局；
- `hooks/usePolling.ts:44` **单飞**：上一次未返回则**跳过本次 tick**（其注释自陈"后端接口偶发 3~45s 慢响应"）
  ⇒ 慢响应期间页面刷新被**整拍丢弃**；
- `lib/api.ts:156`：每次请求前 `await ensureFreshAccessToken()`（single-flight，超时 12s）；
- 访问日志显示同一客户端端口在 2~3 秒内连打 5~7 个端点，且**跨 13+ 个 TCP 端口**
  ⇒ 连接未被复用（uvicorn 默认 keep-alive 5s，与 3~5s 轮询边界冲突）。

## 2. 我**没有**做到的（诚实边界）

1. **未能复现"20 秒"**。按浏览器 6 连接上限重放"切模块"批次：
   - 未建模瀑布版（`scripts/reproduce_module_switch_latency.py`）：典型 **0.20s**、最差 **2.93s**；
   - **建模真实瀑布版**（`scripts/reproduce_switch_with_waterfall.py`）：中位 **0.63~1.07s**、最差 **1.81s**；
   - 前端页面加载实测 **74ms~1.3s**（`scripts/probe_frontend_page_load.py`，dev 编译不是元凶）。
   ⇒ 当前状态下我测到的各段加起来是**亚秒~2 秒**量级，**凑不出 20 秒**。
   24 分钟里 `orders` 串行探测最差 4.6s（§1.4），仍未到 20s。
2. 20s+ 的可解释窗口只有三类，均**未在本次复现中命中**：
   - 后台阵发把进程顶到 100%+ 时，同页 5 个请求 + ticker + 其它残留轮询叠加，末位请求落在 10~30s 外（SLOW 日志存在 10~15s 档 7 条、20~25s 档 6 条）；
   - 数据源异常时的 30s 级超时（14:31 那批，是我重启 DC 造成）；
   - `usePolling` 类页面（ops/agent-monitor **15s**、strategy **15~30s**）单飞跳拍 ⇒ 最长 30s 陈旧，
     这类页面**"没有秒级刷新"是设计如此**。
3. 因此"20s+"若要确证，需要在**故障发生的那一刻**抓现场（前端 Performance 面板 + 后端 SLOW 行时间戳对齐）；
   本次为事后取证，只能给出机制与上界。

## 3.5 补齐"20 秒"现场的办法（我做不到的部分）

本次是**事后取证**；要确证 20s+，必须在**故障发生的那一刻**同时抓两侧：

1. 你感到"刷不出来"时**先别动页面**，记下大致时刻（或直接说一声），
   我可同时对齐 `logs/backend.log` 的 `SLOW` 行、进程 CPU、访问日志三者的时间戳；
2. 或由你在浏览器 F12 → Network 录一次切页并导出 HAR（含 queued/waiting/content download 分段）
   —— 可直接分辨"浏览器排队 / 等响应 / 前端渲染"三段各占多少；
3. 若 20s+ 只在**数据中心异常期间**出现（本日 14:31 那批 30s 超时即属此类，且是我重启 DC 造成），
   则它是"DC_ONLY 下取价等待超时"问题，与 §1 的 GIL 排队是**两个独立问题**，需分开治。

| 前端 | `lib/api.ts` 加 `paperApi.getDashboard`；`types/api.ts` 加 `PaperDashboard`；`useTradingData.ts` 用**模块级引用计数的单一轮询器**（`usePaperDashboardPoller`）每 5s 发 1 个聚合请求，四个 hook 变为**派生只读**（`refetchInterval: false`）；`invalidatePaperData()` 统一失效聚合键+旧键（否则"改了余额/平了仓页面不刷新"） |
| 回退 | `status="closed"` 或 `limit≠50` 仍走原端点（语义不缩水） |

**为什么不用"多观察者共享同一 key + 各自 refetchInterval"**：TanStack Query v5 的
`Query.fetch()` 在已有数据且 `cancelRefetch` 为真（`refetch()` 默认）时会取消在飞请求并重发
⇒ N 个观察者 = 每间隔 N 次同端点请求（载荷更大，比现状更差）；
而只给其中一个 hook 设间隔，则只挂其它 hook 的页面（如 strategy 只挂 `usePositions`）
会**静默失去轮询**。引用计数注册表把这两条都排除了。

**实测（单页面 100 秒，只统计本页发出的请求）**：

| 指标 | 改前 | 改后 |
|---|---|---|
| `/api/paper/*` 请求数 | **76**（4 端点 × 19） | **20**（1 聚合 × 20）＝ **-74%** |
| 本页 API 请求总数 | **103** | **51** ＝ **-50%** |
| 聚合节奏 | — | 精确 **5.0s/次**（无乘法：多观察者各自轮询会变 ~16 次/20s） |
| 聚合 1 次 vs 四端点合计（串行） | 203ms | 聚合 **138ms**（省 32%） |

**回归测试**：
- 后端 `test_paper_dashboard_aggregate_20260918.py`（11 项）：单一来源钉桩
  （`paper_engine.get_*` 只允许出现在 4 个 helper 内，出现第 5 处即失败）、
  **聚合四节与四个单端点载荷逐字节 JSON 全等**（真实库逐账户对拍）、未初始化语义、404 语义不变；
- 前端 `e2e/paper-dashboard-aggregate.spec.ts`（2 项）：**单端点 0 次**、
  **聚合次数不放大（3~8 次/20s）**、**只挂派生 hook 的仪表盘页仍在轮询**（防静默失去刷新）。

> **一处必须写明的口径辨析**：HTTP 层对拍**不会**得到逐字节相等 ——
> 聚合与单端点是**两个不同时刻**的计算，实时价一动，`unrealized_pnl`/`total_equity`/
> `total_pnl`/`max_drawdown_pct`/`updated_at` 就会差（实测两次调用相隔 3.85s，
> 相对差 1e-4~1e-2），而**计数与结构性字段完全一致**。
> 因此"口径一致"的证据取**同进程毫秒级对拍**（单元测试，全等），
> 而不是跨时刻的 HTTP 比对 —— 后者会做出错误的"口径漂移"结论。
