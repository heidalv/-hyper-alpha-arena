# LLM 配置统一重构设计 2026-08-15

## 一、审计结论（当前真实状态）

### 1. 运行事实：pro 并没有被实际调用
`llm_usage_logs` 近 24 小时 1549 次调用 **100% 是 deepseek-v4-flash**（全量 36k 次也是 flash），
无一笔 pro。用户看到的 "deepseek-v4-pro" 来自三处**非运行时**痕迹：
- `llm_usage_service.DEEPSEEK_OFFICIAL_PRICING` 计价表里保留的 v4-pro 档（仅历史账单归类）；
- `_resolve_deepseek_tier()`：模型名含 "pro/reasoner" 就归到 v4-pro 档——**归类规则会让历史账单显示 pro**；
- `backend/data/opencode_reports/` 两份 2026-06-29 的旧报告（历史产物）。

### 2. 但"绕过"确实存在——三个真实漏洞
| # | 漏洞 | 证据 |
|---|---|---|
| A | **旧字段直读**：`Account.model/base_url`（旧表字段）被 6 个服务直接拿去拼 LLM payload，完全绕开 llm_configurations | ai_decision_service.py:2383/2430、ai_prompt_generation_service.py:164/405、ai_signal_generation_service.py:303/1385、kline_ai_analysis_service.py:523/657、asset_snapshot_service.py:97、hyperliquid_snapshot_service.py:82 |
| B | **env 可覆盖 DB**：`qaa/llm_config.py` 的 `QAA_QUICK_MODEL`/`QAA_DEEP_MODEL` 环境变量可覆盖数据库默认；`opencode_bridge._model()` 也有 `OPENCODE_MODEL` env 后门 | qaa/llm_config.py:22/30、opencode_bridge.py:79-83 |
| C | **无白名单校验**：`call_llm_api` 收到什么 model 就发什么，任何人改一行代码就能调 pro | llm_config_service.py:1271/1301 |

### 3. 重复配置的来龙去脉（id=17 vs id=79）
```
id=17 DeepSeek V4 (Flash)   tenant=326  is_default=true  usage_scope=trading,factor_mining,assistant,evolution,coin_select,journal,kline_analysis,news_intel
id=79 VIP选币 DeepSeek        tenant=326  is_default=false usage_scope=coin_select,assistant,kline_analysis
        ↑ 同 key（sk-832f...）、同 URL、同 flash 模型 —— 完全重复
```
- id=79 由一次性脚本 `backend/scripts/ensure_admin_coin_select_llm.py` 创建；
- 该脚本的假设「选币需要单独一条 LLM 配置」已经过时：id=17 的 usage_scope **已含 coin_select**；
- 路由 `get_llm_config_for_usage("coin_select")` 优先命中 scope 匹配的 id=79 → 于是出现两条重复配置同时被用的假象。

### 4. 密钥存储不一致
- id=17 的 api_key 是**明文**（DB 里可见 `sk-832f31127...` 前缀）；
- id=79 的 api_key 是 **Fernet 加密**（`gAAAAA...`）。
- 同一张表两种存储格式，`decrypt_llm_key` 对明文行也"兼容通过"——加密形同虚设。

## 二、目标架构：单一权威 + 单一入口

```
┌─ 调用方（任何模块）────────────────────────────┐
│  resolved = resolve_llm(usage="trading",        │   ← 唯一解析入口
│                         account_id=..., tier=)   │
│  resp = call_llm_api(resolved, messages,        │   ← 唯一调用入口
│                       caller="...")              │
└─────────────────────────────────────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │ LLMResolutionService（权威）     │
   │ 解析链（固定顺序，禁止自定义）：  │
   │ 1. usage_scope 绑定（同租户）    │
   │ 2. 账户绑定 llm_config_id(/deep) │
   │ 3. 租户 is_default 配置          │
   │ 4. 无 → 返回 None（拒绝，不兜底）│
   │ 模型白名单 = 激活配置的 model 值 │
   └─────────────────────────────────┘
                    │
        llm_configurations（唯一数据源）
```

- `get_llm_config / for_account / for_usage / for_analysis / qaa.llm_config / opencode._model`
  全部收敛为该服务的薄包装（兼容层保留函数名，内部统一走 resolve_llm）。
- `call_llm_api / call_llm_api_sync` 增加**模型白名单断言**：payload 模型不在
  激活配置白名单内 → 打 ERROR 告警日志（不阻断，先观察后收紧）。

## 三、数据治理（一次性迁移脚本）

1. **删除 id=79**（VIP选币 DeepSeek），coin_select 由 id=17 的 usage_scope 覆盖；
   `ensure_admin_coin_select_llm.py` 重写为：先按 usage 解析，**只有解析失败且确实缺配置**才建，
   且按 (tenant, provider, base_url) 幂等去重——不会再产生第二条相同配置。
2. **密钥加密统一**：迁移脚本把明文 key 行加密为 Fernet；`decrypt_llm_key` 改为
   严格模式（新写入必须加密，明文只读兼容并告警）。
3. **seed 幂等**：`startup._seed_deepseek_config` 增加 (provider, base_url) 级去重，
   不只看「是否存在 deepseek 记录」。

## 四、接入契约（防绕过，评审关卡）

新模块需要 LLM 能力时：
1. 在 `LLM_USAGE_REGISTRY` 注册用途（如 `usage="news_intel"`），**不新增任何配置行**；
2. 只能调用 `resolve_llm(usage=...)` + `call_llm_api`；
3. 禁止项（code review 红线）：
   - 直接读 `DEEPSEEK_API_KEY` / `*_MODEL` 环境变量；
   - 硬编码模型名 / 自拼 openai 兼容 URL；
   - 直读 `Account.model/base_url`（旧字段全部废弃迁移）；
   - 新增 provider/model 配置项。
4. 默认模型 = 租户默认配置的 model，**唯一开关**；谁想用 pro，只允许改 DB 默认配置。

## 五、pro 的处置

- 计价表保留 v4-pro 行，标注「历史账单归类，运行时已停用」；前端成本面板同样标注。
- `_resolve_deepseek_tier` 仅用于历史账单归类（注释说明）。
- 彻底移除所有可能注入 pro 的路径：QAA_*_MODEL、OPENCODE_MODEL env 后门删除。
