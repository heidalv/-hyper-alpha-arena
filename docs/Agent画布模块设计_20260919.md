## 0. 一句话设计

新增一个**无限画布页 `/agent-wall`**：把 24 个 agent 节点按 **5 个边界分组**摆在一张可缩放/可拖拽的画布上，
**每个节点自带独立滚屏**（该 agent 自己的分析流），节点按重要性分 4 档尺寸，
节点之间用**有向边**表示真实的数据/调用关系，边的颜色即**链路健康**（正常 / 陈旧 / **断链** / 未生效）。
一句话：**把"每个 agent 的分析流 + 它们之间的链路"变成一张可缩放、可拖拽、可巡检的活图。**

## 1. 为什么要画布而不是「一个大滚屏」

现状（已实测，见 `docs/Agent运行排查_20260919.md`）：
- 现有 `agent-monitor` 页的「实时日志」Tab 是**单一 300 行大滚屏**（`/api/system-logs/tail?lines=300`），
  里面混着所有组件；**无法回答"某个 agent 在做什么"**。
- 观察型 6 个 agent 的**分析正文（单次 3~22KB）在 `/api/agents/latest/{id}` 里躺着，前端零消费**；
  主脑的 LLM 分析正文只在 `logs/brain_subprocess.log`（94.6 万行）里滚动，前端同样零消费。
- 因此问题不是"日志太少"，而是**没有按 agent 边界组织、也没有链路视角**：
  一个 agent 停跑 16 天（`timing`）、一个 agent 从未产出（`param_search`）、
  一整族 9 张卡片整体未启用（QAA）——**在现有 UI 上完全看不出来**。

画布 + 分组 + 独立滚屏 + 连线，正是为了让"哪个 agent 静默了、哪条链路断了"**一眼可见**。

## 3. 边（关系）与其健康判据

边**必须来自代码事实**，不许凭感觉画。每类边都有可查询的判据：

| 边 | 含义 | 健康判据（可查） |
|---|---|---|
| DC → kline → factor_engine → brain_* | 数据流 | DC health + K线新鲜度清单（本轮 DC 优化已落地 `[FreshnessWatch]`） |
| coordinator → brain_mid/brain_long | tick 触发 | 调度器 next_run / 主脑日志间隔 |
| brain_* → thesis_store → midlong_executor | **决策权威链** | `mid_open_authority=llm_thesis` + 论题 `updated_at` + `[MidLong]` 行 |
| 观察型 Agent → 预测账本 → 评分 → 可信度门 → 实验卡 | 建议链 | `/api/agents/predictions`、`/api/agents/credibility`（已知 `anomaly/trading_state` n=1526、avg_score 0.97） |
| 观察型 → 决策 | **观察模式：不生效** | `configured_mode=observe`、`effective_mode=observe` → 画**灰色虚线**并标注"建议未生效" |
| QAA P0/P1/P2 依赖 | 卡片调用链 | `phase3_enhancements.py` 链定义 + `event_bus` 熔断器状态 |
| 车道 → paper_engine → 持仓/订单 | 执行结果 | `/api/paper/dashboard/{id}`（本轮已聚合） |

**边的四种状态**（颜色即结论）：
1. **正常**（青色流动动画）：最近流动 < 2× 期望间隔；
2. **陈旧**（黄）：2~5× 期望间隔；
3. **断链**（红色虚线 + ❗）：>5× 期望间隔 / 生产端从未产出 / 消费端 404；
4. **未生效**（灰色虚线）：链路存在但被开关或 observe 模式短路（**这类最容易被误认为"在跑"**）。

点击任一条边 → 右侧详情：生产端、消费端、最近流动时间、**判定依据（哪个字段/哪行日志/file:line）**、以及"如何修复"。

## 4. 画布交互规格

### 4.1 画布
- 无限画布：`transform: translate(x,y) scale(k)`；缩放范围 **0.25× ~ 2.5×**（滚轮以光标为中心）；
- 平移：空白处拖拽 / 空格+拖 / 中键拖；
- 网格与吸附：8px 网格，拖拽节点时吸附；分组框可整体拖动（带动框内节点）；
- **无窗口尺寸限制**：节点尺寸不受容器约束，可拖出初始视口；画布边界自动扩展。

### 4.2 分组
5 个分组框（G0~G4）：带标题栏 + 底色 + 内边距；框内默认按**拓扑列**排列（数据→主脑→观察→执行）；
分组框可折叠（折叠后显示该组的健康摘要，如 `G2 观察型 4✓ 1⚠ 1✗`）。

### 4.3 节点（每个 agent 一个独立滚屏）
- 结构：`头部`（名称 / 分组徽标 / 状态灯 / **期望 vs 实测** / 最近成功时间）、
  `主体`（**该 agent 自己的滚屏**）、`尾部`（最近 N 次耗时与成败 sparkline）；
- 滚屏行为：等宽字体；**自动跟随**（贴底才跟）；**悬停暂停**；显式【暂停/继续】按钮；
  级别过滤（INFO/WARN/ERROR）；关键字高亮；行数 ring buffer ≤ **200 行/节点**；
- 尺寸：四档（§2），**支持拖拽节点右下角自由缩放**（"没有窗口的大小限制"）；
- 点击头部：聚焦（其余淡化）；点击"展开"：进入单节点大视图（该 agent 的全屏分析流，仍保留返回画布）。

### 4.4 边
有向曲线（贝塞尔）+ 箭头；健康着色见 §3；悬停加粗并显示 tooltip；点击打开右侧详情。

### 4.5 工具条与快捷键
- 工具条：`重置布局` `自动排布` `只看断链` `只看活跃` `组过滤` `缩放比例` `暂停全部滚动` `数据源健康`；
- 快捷键：空格+拖=平移、滚轮=缩放、双击节点头=聚焦、`/`=搜索节点、`Esc`=取消；
- 持久化：节点位置/尺寸/缩放/过滤/暂停状态存 `localStorage`（按用户），刷新后恢复。

### 4.6 性能（吸取本轮 GIL 教训，硬约束）
- **一个轮询端点**（不是每节点一个请求）：`GET /api/agent-wall/tail?nodes=a,b,c&cursor=...` 一次拿回多个节点的增量行；
- 只订阅**视口内 + 活跃**的节点（默认上限 8 个），其余显示状态但不出流；
- 节点内日志只保留 200 行；渲染用 `IntersectionObserver` 控制；
- 后端读日志**必须增量**：按文件维护 offset（`brain_subprocess.log` 有 **945,923 行**），
  每次最多读 64KB/节点，**禁止每请求全文件扫描**（否则会重演"端点拖垮 GIL"的老问题）。

## 5. 后端接口（新增，全部只读）

| 端点 | 返回 | 说明 |
|---|---|---|
| `GET /api/agent-wall/state` | 节点数组（id/group/size/期望间隔/最近成功/最近失败/近 N 次计数/状态判定）+ 边数组（from/to/kind/last_flow_ms/health）+ 分组摘要 | 一次请求拿全画布骨架；2s 轮询 |

**事实来源（复用已有，不另造真相）—— 这一节初稿写错过，已更正**：

  （`registered 47 / scheduler_only 85`），其中就含 `agent_anomaly`、`agent_signal_review`、`agent_event_impact`、`agent_execution_qa`、`experiment_advance`。
  ⇒ **画布的节点状态直接映射 `stale`**：`None→正常`、`warn→陈旧`、`critical→断链`、`never_ran→从未运行`；
  节点头部显示 `cadence` 与 `last_end`。**一套口径，禁止另算。**
- 心跳/最近成功：同上（`heartbeat_at`、`last_end`）+ 产物 mtime（`backend/data/agents/latest_*.json`）；
- 节点流：**每节点一个 stream adapter**（`file+filter` / `API` / `DB 表` / `JSON 产物`），

`agent_param_search`/`agent_timing`/`analysis_timing`/`analysis_weekly_review` 四条 `never_ran` 且 `enabled=True`。
**Agent Wall 就是这份健康数据的第一个消费者。**

## 7. 这张画布顺手完成的"查错"（`/api/agent-wall/audit`）

设计目标之一就是让**逻辑错误显形**，audit 端点输出以下六类（每条带 file:line 或运行态证据）：

1. **注册但从未运行**：`agent_param_search`（开关 `AGENT_PARAM_SEARCH_ENABLED=false`）、
   `agent_timing`、`analysis_timing`、`analysis_weekly_review` —— 四条的 `stale` 都是 `never_ran` 且 `enabled=True`（`/api/ops/jobs` 实测）；
2. **停跑未告警**：`capital_allocate`（cron 05:20）、`e5_shadow_scan`（900s）、`e5_shadow_kpi`（cron 09:10）
   三条 `stale=critical`，最后运行均为 **2026-09-05**（停跑 14 天）；
3. **停用但仍出现在册/接口中**：`timing`（09-05 停用，`jobs.py:268`），
   但 `/api/agents/status` 仍列它、`/api/agents/latest/timing` 仍返回 16 天前数据 → **静默陈旧**；
4. **整族未启用**：QAA 9 张卡片（`/api/qaa/health` = unavailable，`/agents|context|latency` = 503）；
5. **命名空间错配**：`/api/monitor/agents/{id}` 只认 9 个"运行时 agent"（`agent_runtime_monitor.py:398`），
   对 6 个分析 agent（anomaly 等）恒 **404** —— 两套 agent 命名空间互不相通；
6. **产物无消费者**：观察型 6 agent 的分析正文、主脑 LLM 正文、`/api/ops/jobs`、`/api/monitor/agents/*`
   全部零前端消费者；
7. **observe 模式导致"分析了但不会生效"**：6 个 agent 全部 `effective_mode=observe`
   （`signal_review` 的 advice 里已有 `disable_source` 建议、`applied=false`、`apply_note="observe 模式：仅记录不执行"`）
   → 画布以灰虚线明确标注，避免误判为"决策已采纳"；
8. **频率漂移**：实测间隔 vs `expected_interval_sec` 偏离 >2× 即列入（本项已由 `job_registry` 的 `stale` 覆盖）。

## 7. 技术选型（两条路，附取舍）

| 方案 | 优点 | 代价 | 建议 |

## 9. 可验收标准（每条可测）

1. 打开 `/agent-wall` 能看到 **≥20 节点、5 个分组框、边全部有向且连接正确**；
2. 每个**活跃**节点在自己的滚屏里能出现 **≤5 分钟前**的行；
3. **停用节点**显示"已停用"并给出依据（如 `jobs.py:268` / 开关名），**不再静默显示旧数据**；
4. 画布"断链"边的数量 == `/api/agent-wall/audit` 里断链条数（两侧一致，禁止两套口径）；
5. 缩放/拖拽/改尺寸后刷新页面，布局与过滤状态保持（localStorage）；
6. **单页请求数**：2s 内 ≤2 个请求（state + tail），与"打开了几个节点"无关；
7. 后端 `tail` 在 `brain_subprocess.log`（94.6 万行）上单次耗时 **<50ms**（增量读，非全扫）。

## 10. 风险与未决

1. **QAA 族未启用**：画布只能显示"未启用"；是否要恢复 QAA 属于产品决策，不在本设计范围。
2. **边健康的判据需要"消费端证据"**：某些边（如"观察型→评分→实验卡"）需要消费端日志或账本字段才能判"最近流动"，
   若某条边无法取得证据，设计上**宁可不画**，也不画一条永远绿的假边。
3. **主脑日志量**：`brain_subprocess.log` 94.6 万行且持续增长，需要轮转策略（当前无轮转）；P0 先用 offset 增量读 + 单次 64KB 上限。
4. **不改动现有 `agent-monitor` 页**：新页并存（它是"按会话看执行统计"，画布是"按 agent 看分析流与链路"），
   若评审认为应合并，再单独立项。
