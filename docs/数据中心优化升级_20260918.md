## 2. 查实的问题（按影响排序）

### P-1【高】P0 采集长期半瘫：**成功率 49.3%，整轮全失败 47.4%**

`logs/data-center.log` 全量统计（**1383 轮**）：

| 指标 | 读数 |
|---|---|
| 累计 ok / err | **211,251 / 217,479** |
| **成功率** | **49.3%** |
| **整轮全失败（0 ok）的轮次** | **656 / 1383 = 47.4%** |
| 近 30 轮 ok 序列 | `0,0,…,0,291,291,0,291,0,…,0,288,0,…` |

**根因（代码级）**：`_collect_symbol_kline`（`kline_realtime_collector.py:1446`）
调 `collector.fetch_current_kline()` **既无请求级超时、也无重试** ⇒ 底层一旦挂住
（本地代理抖动），任务一直等，直到**轮级** `KLINE_P0_TIMEOUT_S`(90s) 到期，
`asyncio.wait_for` 把整轮 306 个任务**一起取消** ⇒ `0ok/306err`。

**为什么长期没被发现**：任务是被 `CancelledError`（**BaseException**）取消的，
原 `except Exception` **捕不到** ⇒ 日志里 `Failed to collect kline` **0 条**，
故障**完全无痕**（日志只有轮级的 `timed out` 与 `0ok/306err`）。

**反证"这不是环境偶发"**：同一个文件里 **P1 早有请求级超时**
（`:1260 asyncio.wait_for(_fetch(), timeout=25)`）⇒ p0 只是**漏了同款保护**。

### P-2【高】采集宇宙 ⊉ 分析宇宙（长周期覆盖缺口）

- `_depth_symbols()`（`kline_history_sync.py:699`）在 `KLINE_DEPTH_BACKFILL_SYMBOLS` 为空时
  **只取 `get_trade_universe_symbols()`** ⇒ 实测回填宇宙仅 **~13–18 个**（`p2_depth` 心跳 `symbols=13`）。
- 而主脑还会分析**看板里的 AI 候选**：实测看板 7 个（`ADA/APT/ATOM/FIL/SUI/TIA/WIF`），
  加上交易宇宙里的 `MU/PLAY/ICP/…`。
- ⇒ 看板币的 4h/1d **永不回填** ⇒ 陈旧 ⇒ `get_aggregated_klines` fail-closed 返回空
  ⇒ `_kline_ok` 报硬缺项 ⇒ `consensus_is_tradeable` **第一行短路 False** ⇒ 论题被自动拒。

### P-3【中】心跳语义会误导：`last_success_at` 实为"最后一次尝试时间"

`record_heartbeat` 每轮都写 `last_success_at=now`（**含 0 ok 的失败轮**）⇒ 读表的人看到
`ok=0` + "刚刚" 会得出"**整池永久失败**"的错误结论（我本人在本轮侦察里就先这么误判了一次，
后经 14:23:00 `291ok/15err` 的日志纠正）。**语义与命名不符**，属可观测性缺陷。

### P-4【中】已死池仍在表里：`aggregate`（44 天）、`asterdex p0/p1`（31–48 天）

心跳表里这些池的最后更新停在 8 月；`aggregate/*` 是另一套（`market_aggregation/persist._touch_heartbeat`）。
不清理会持续干扰"池健康度"判读。

### P-5【低】日志噪音：`[KlineSyncMeta] 拒绝写入非加密 ticker` **2146 条**（bybit 的股票/ETF：DIA/EWY/IWM/MSTR/QQQ…）

过滤器本身工作正常，但每轮每标的都告警 ⇒ 噪音。应降为 debug 或按交易所聚合。

### P-6【低】`kline_collection_tasks` 表**无人读写**（只有模型 `models.py:1296` + 迁移 + split-db 清单）

一张"看起来是按需回填队列"的死表 —— 容易误导后来者以为存在按需通道。

## 7. 第 2 轮（2026-09-18 14:5x–15:1x）

### 7.1 D-2 心跳语义修正（已实施，6 条回归锁）

**问题**：`record_heartbeat` **每轮无条件**把 `last_success_at` 刷成 `CURRENT_TIMESTAMP`
（含 `symbols_ok=0` 的失败轮）⇒ 名字说"成功"、实际是"最后一次尝试"。代价：
P0 共 1383 轮里 **656 轮（47.4%）整轮全零**，而两处消费方**始终判"正常"**：

| 消费方 | 其注释的本意 | 旧实现下的实际效果 |
|---|---|---|
| `data_center_gate._eval_p0_stale` | "P0 心跳最新**成功**时间距今 >300s 即告警" | 永远不告警（时间戳每轮被刷新） |
| `market_intelligence_routes` | "asterdex p0 心跳 5 分钟内**成功** = 数据中心在线" | 同上 |

**改法**（幂等 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，老库自动升级）：
- `last_attempt_at`：每轮都写（=旧 `last_success_at` 的真实含义）；
- `last_success_at`：**只在 `symbols_ok > 0` 时前移**；
- `consecutive_fail_rounds`：连续整轮失败计数（成功清零）。

**安全性核查**：改语义前先确认消费方不会被误伤——`_eval_p0_stale` 结果只进报告
（源码注释明写"**只报告，不阻断启动**"，`all_ok` 只看 catalog 数）⇒ 不拦交易；
`market_intelligence_routes` 是状态汇报。**修正后这两处才第一次真正能看见失败连胜。**

**回归锁 6 条**：`backend/tests/unit/test_heartbeat_semantics_20260918.py`
（成功轮前移 / **失败轮不前移** / 连败累加与清零 / 首跳即失败 ⇒ `NULL` 而非"刚刚成功" /
消费方语义 / 清理工具默认 dry-run 且只按年龄删）。

### 8.1 D-4 日志降噪（已实施，5 条回归锁）

在 4 个交易所 × 多轮采集里反复打印。

**已下架交易对**的告警（防"目录自读自写复活"的安全信息）**未动**。

**写测试时抓出我自己的一个设计缺陷**：第一版在"**首次调用**"就报警——那时窗口内只有 1 条，
之后一小时静默 ⇒ **聚合永远统计不到有意义的量**。已改为"首次只登记起点；窗口到期后的
第一次调用汇报累积量"。回归锁 5 条（逐条非 warning / 窗口到期聚合且计数正确 /
窗口内不重复 / `=0` 回滚 / 下架告警不受影响）。

> 生效范围：后端进程立即生效；**DC 进程需下次重启**（`_filter_catalog_symbols` 在 DC 侧调用）。

### 8.2 D-5/D-6 **前提纠正**：按需回填通道**是通的**（我先前漏了）

**撤回 D-5 的"死表"结论**：`kline_collection_tasks` 被
`backend/main.py`、`backend/api/kline_routes.py`、`backend/services/kline_backfill_manager.py`
引用 —— `BackfillManager` 是一个**真实的任务队列**（`process_task` / `process_pending_tasks` /
`get_task_status` / `cleanup_old_tasks`）。我上一轮只按表名 grep，漏了模型类名。

**实测这条通道在 DC_ONLY 下可用**（`scripts/probe_ondemand_backfill_dconly.py`）：

```

调用 collect_historical_klines(COTI, 近 2 天, 1d) → 返回条数 = 2
```

⇒ **后端进程可以按需补任何标的的 K 线**（不必依赖数据中心的静态宇宙）。这正是 D-6 的"根本方案"：

### 9.1 ③ 收官：陈旧清单**常态可见**（已实施 + 7 条回归锁）

**为什么要做**：本轮之前"哪些标的 K 线陈旧"**只能靠临时脚本查**，而事故教训正是

**实现**：新增 `backend/services/kline_freshness_watch.py`

### 9.4 ⚠️ 诚实性更正：**"交易后端取数不中断"没有完全成立**
